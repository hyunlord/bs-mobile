# World API Editor capture (#648)

This harness uses an actual prototype bearer and the public map UI navigation. It never fabricates city, tile, resource stock, combat, or account responses. It is Editor evidence, not a phone, native key-store, or C05 measurement.

With the shared Mac lock, outside the night measurement window, prepare `wave-1a`, then run Unity with `-projectPath unity -executeMethod Game.WorldCapture.WorldCapture.Start --server-url http://127.0.0.1:5084`. Provide `WORLD_CAPTURE_TOKEN_FILE` pointing to a private local bearer file and `WORLD_CAPTURE_DIR` pointing to a new owned artifact directory. Never include the bearer in arguments, logs, repository, or Release. Leave `SOW_ACCOUNT_SERVER` unset for this explicit prototype contract run.

The harness connects through the actual settings input, opens the same public navigation route used by the estate tab, then clicks the map tab and requests the city. It captures map, navigation, selection, and tall viewport. A separate client instance verifies city POST idempotency, chunk GET, invalid-chunk rejection preserving the last confirmed cache, and authentication clearing. `api-proof.txt` records only outcomes. Screenshots and their text labels contain no bearer.

The visible maximum 7×7 cells are a viewport projection of the fetched server chunk; they are not the world or chunk dimensions. Tile geometry derives from the complete validated response. Missing stock remains `재고 확인 불가`, never an invented grade or quantity. City, terrain, and target illustrations reuse existing approved estate art as display markers; new world artwork and full launch map interactions are outside this bounded integration.

Read `result.txt`, inspect all PNGs, and record the exact client and server SHAs separately. Preserve failures. This harness is additional to the full two-profile Unity record and its supplemental tests.


The march scenario first trains one troop using the UI and the normal server training timer, recruits through the UI if no hero is owned, then selects a resource from the actual home chunk, dispatches, observes gathering, requests recall, and observes returned troops plus increased wallet/held materials. The 65-second gathering observation is a QA dwell time, not a game rule or displayed duration. The scenario timeout is 30 minutes; it does not accelerate server time. A prepared account must have normally constructed barracks prerequisites. The development server uses the existing account-QA `Prototype__RecruitGems=3000` initial-currency fixture so an owned hero can be recruited. Record that configuration with the server SHA: this proves actual HTTP/UI integration, not production economy or normal-play balance. The harness only reads coordinator transport state for assertions; all mutations go through visible UI actions.

Native credential storage remains independently blocked on the unchanged Unity host entitlement. Process-restart and response-loss retry runtime evidence are separate gates; journal unit tests alone do not prove them.

For the actual post-commit response-failure scenario, run `tools/world-client/retry-proxy.mjs` with `WORLD_PROXY_UPSTREAM=http://127.0.0.1:5084`, `WORLD_PROXY_PORT=5085`, and a new owned `WORLD_PROXY_LOG`. Point the capture's `--server-url` at port 5085 and set `WORLD_CAPTURE_EXPECT_RETRY=1`. The proxy forwards the first gather command to the actual server, consumes and hashes its successful receipt, then injects one HTTP 503 instead of forwarding it. Explicit 503 is required because Unity transparently retried a socket disconnect in the separate alliance QA; the injected status is a harness fault, not a server failure. The UI must expose its pending request, then send the same command identity and exact body through `March.Retry`. The proxy asserts the original server receipt bytes are identical and records only hashes/command identity, never Authorization. This is injected-503/retry evidence within one Editor process, not process-restart evidence.
