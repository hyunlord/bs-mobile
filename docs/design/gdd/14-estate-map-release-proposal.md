# 14 · 신규 정식 계정의 r8 지도·서버 저장·건물 효과

상태: **축소안 사용자 승인 대기**. 추적 [#546](https://github.com/hyunlord/bs-mobile/issues/546), PR [#547](https://github.com/hyunlord/bs-mobile/pull/547). 2026-10-30 사용자 추가 결정으로 이전 로컬 저장 이관안을 대체한다. 이전 승인과 병합 예약은 이 축소안의 승인으로 간주하지 않으며, 다시 승인받기 전에는 병합하지 않는다. 게임 코드·데이터 변경 없음.

## 1. 사용자 결정과 범위

- [확정: 사용자 결정] 신규 정식 계정은 r8 지도 영지로 시작한다. 타이틀→첫 출정→카드→귀환은 유지하고 **첫 영지 진입**부터 지도 첫 건설을 보여 준다. [첫 접속 시안](https://github.com/hyunlord/bs-mobile/releases/tag/onboarding-first10-542-20261030) 07~09(터 선택→비용 확인→착공)가 기준이다. 첫 전투를 건너뛰거나 건설 완료까지 두 번째 출정을 막지 않는다.
- [확정: 사용자 결정] 정식 계정의 저장 정본은 **서버**다. C# 서버의 구체 구조·인증·계정 생성·API·DB·저장 계약은 Codex의 별도 서버 ADR에서 설계한다. 이 문서는 서버가 이미 있거나 연결됐다고 주장하지 않는다.
- [사용자 전제] 아직 출시 전이며 실제 사용자 저장이 없다. 기존 자동 장원 저장은 개발 자료이므로 정식 계정으로 이관하지 않는다. 개발 빌드에서만 **읽기 전용**으로 보존한다. 정식 서버 계정은 개발 파일의 지갑·가신·공사·효과·장부를 가져오지 않는다.
- [확정된 배치] r8 13구역·총1,664칸·중앙 시작12×12·시작 건물10채와 r3~r7 동결은 [r8 배치 설계](../m3a-r8-layout-proposal.md)를 따른다. 기존 개발 파일이나 아트 원본을 삭제/덮어쓰라는 결정이 아니다.

[가설: 신규 경제] 현행 r8 시제품의 초기 곡물120·목재180·철재60, 곡창 L1 목재30·60초 등은 출시 수치가 아니다. 첫 판 보상이나 개발 저장 이관 보너스로 지급하지 않는다. 최종 신규 지급·공사 비용·생산속도는 #126 경제 검토와 별도 구현 관문을 따른다. 새 보상·상품·무료 가속·튜토리얼 보너스는 추가하지 않는다.

## 3. 신규 지도 건물과 장원 효과 대응

[현행 근거] [progression.json](../../../data/meta/progression.json)의 장원 4종 최대 효과 레벨은 모두 10이다. `MetaEngine.EffectLevel`은 같은 효과 ID의 `ManorLevels`를 읽는다. 아래에서 **E는 시각 레벨과 다른 효과 장부 값**이다. 기존 공식과 상한은 유지하며, **L1→E3 / L2→E6 / L3→E10 대응만 [가설]**이다. L0는 E0이다. 경험치 획득량/가신 경험치 보너스는 이 네 장원 효과에 없으며 새 XP 효과를 추가하지 않는다.

| 기존 장원 ID·효과 | 대응 지도 건물 ID | 지도 L1 [가설] | 지도 L2 [가설] | 지도 L3 [가설] | 유지하는 현행 공식·상한 |
|---|---|---|---|---|---|
| `meta:forge` · VassalLevelCap | 대장간 `meta:forge` | E3 → 가신 레벨 상한 11 | E6 → 17 | E10 → 20 | `min(가신 MaxLevel=20, 5+2E)`; 가신 현재 레벨을 무료로 올리지는 않음 |
| `meta:scriptorium` · Research | 기록소 `meta:scriptorium` | E3 → 연구 조건 ≤3 | E6 → 연구 조건 ≤6 | E10 → 연구 조건 ≤10 | 연구는 E 그대로. 현행 도전 요구는 0~4이며, 연구 충족만으로 도전 완료·보상 자동 지급하지 않음 |
| `meta:granary` · IdleCapacity | 곡창 `meta:granary` | E3 → 보관 시간 9,360초 | E6 → 11,520초 | E10 → 14,400초 | 현행 상한식 `min(14400,7200+720E)`를 신규 지도 보관시간의 하한 후보로 사용; 구형 생산 재개 금지 |
| `meta:barracks` · VassalSlots | 병영 `meta:barracks` | E3 → 1칸 | E6 → 2칸 | E10 → 3칸 | `min(3,1+floor(E/4))`; 슬롯에 가신을 자동 편성하지 않음 |

**적용 범위는 신규 정식 서버 계정의 r8 효과 연결뿐**이다. 개발 저장과 r2~r7의 동결 설정에 이 표를 소급하지 않는다. 구형 계정의 보관 한도 보상을 약속하는 이관 정책이 아니라 신규 지도 곡창의 시간 후보로 사용한다.

곡창 [가설] 연결식은 `max(현행 지도 StorageSeconds, 위 구형 상한식)`이다. 현행 r8의 기본 보관시간 L0~3은 7,200/7,200/10,800/14,400초이고 장기보관 분기는 +3,600초, 지도 최종 상한은 18,000초다. 이 지도 분기·상한을 먼저 현행대로 계산한 뒤 효과 하한과 max를 취한다. 시간끼리 더하거나 이미 지난 구간을 새로 생산하지 않는다. 재고 수량 상한·생산속도는 기존 지도 규칙대로이며, 이 표는 구형 생산량/헌장 생산까지 유지한다는 약속이 아니다. 정식 계정에는 구형 자동 장원 생산기를 연결하지 않는다.

### 신규 효과 장부와 완료 시점

[권고] 신규 서버 계정의 네 효과 장부는 E0이고 네 효과 건물은 L0다. 현행 r8의 startsComplete는 효과 없는 집뿐이므로 E0이다. 효과 건물을 무료 완공 상태로 시작시키는 변경은 별도 경제 결정이며, 표시 그림만 보고 효과를 지급하지 않는다.

실제 건설 완료 상태 전이에서만 ID별 `E_next = min(10, max(E_current, target[완료 레벨]))`를 계산한다. target은 L0/L1/L2/L3에 0/3/6/10 [가설]이다. 효과 읽기와 UI의 현재 보너스는 장부만 읽고 `장부 + 지도 효과`로 합산하지 않는다. 로드·표시·이동·전문화·착공·예약·취소는 완료 효과 지급 시점이 아니다. 한 건물의 완료 레벨과 효과 장부는 서버의 동일한 확정 상태를 나타내야 하며, 중복 완료 처리도 같은 max 결과여야 한다. 구체 트랜잭션/동시성/재시도 구현은 서버 ADR이 소유한다.

| 신규 진행 예시 [가설] | 효과 E | 가신 상한 / 슬롯 / 연구 | 곡창 기본 보관시간 후보 |
|---|---|---|---|
| L0 | 0 | 5 / 1 / 0 | 7,200초 |
| L1 실제 완료 | 3 | 11 / 1 / 3 | 9,360초 |
| L2 실제 완료 | 6 | 17 / 2 / 6 | 11,520초 |
| L3 실제 완료 | 10 | 20 / 3 / 10 | 14,400초 |
| L3 완료가 중복 처리됨 | 10 그대로 | 20 / 3 / 10 그대로 | 시간 합산·소급 생산 없음 |

현행 `ManorLevels`는 이 효과 계산의 기존 입력 이름일 뿐, 서버가 같은 필드/codec을 반드시 쓴다는 결정은 아니다. Core 계산·검증·출정 snapshot은 하나의 정합한 효과 장부를 사용해야 한다. 연구 조건만으로 도전 보상을 자동 지급하지 않으며 기존 메트릭·미수령·수령 경계를 유지한다. 가신 능력별 판 안 cap·편성·현재 보유 레벨도 기존 규칙을 따른다.

## 4. 서버 후속 설계 책임

[Codex Core·저장 검토](https://github.com/hyunlord/bs-mobile/pull/547#issuecomment-6505712165)는 당시 로컬 이관안에 대한 정적 검토다. 그 검토에서 확인된 설정 의미 검증·동시 쓰기·내구 커밋·복구·중복 지급 위험은 후속 서버 설계에서 다뤄야 한다. **로컬 계정 경로 lock, primary hash/readback, progress/terminal 복구 세대 manifest, v5 체크포인트, Migrate 재시도를 이 PR의 제품 구현 계약으로 요구하지 않는다.**

Codex의 별도 C# 서버 ADR은 계정 쓰기 직렬화/동시성, 설정 버전과 의미 검증, 시간 입력, 재시도·중복 요청, 저장 원자성, 백업/복구 세대, 장애 주입 및 롤백을 서버 구조에 맞게 정한다. 단일 writer가 적절한지와 복구 세대의 구체 형태도 그 ADR의 책임이다. 서버 저장 실패를 클라이언트 개발 파일 복원으로 우회하지 않는 경계는 유지한다. 서버 설계가 확정되기 전에 SDK·서버 코드·게임 코드·데이터를 이 문서 작업에서 구현하지 않는다.

## 5. 폐기된 이관안과 보존할 역사

이전 #547의 로컬 v1~5→v6 일회 이관, 구형 방치 마지막 정산/미관측 보상 정책, imported 시각 레벨 역매핑, 기존 효과 floor 복사, 기존 v6 L3/낮은 E의 호환 출시 차단, 로컬 원장 복구·역변환/전진 복구 절차는 **이번 사용자 결정으로 제품 설계에서 폐기**한다. 실제 사용자 저장이 있다는 전제에 대한 설계였으며 더 이상 신규 서버 계정 출시의 이관 관문이 아니다.

이전 설계·승인·검토는 Git 이력(이전 문서 커밋 `301cac91`)과 PR 토론에 보존한다. 실패 기록이나 원본을 삭제하지 않으며 기존 저장 지원 코드를 이 문서만으로 제거하지 않는다. 역사 메타 저장/리플레이/골든도 그대로 둔다. 이후 실제 사용자 저장이 생긴 뒤의 서버 스키마 변경·롤백은 새로운 서버 운영 계약으로 다룬다.

## 6. 구현·검증 관문

이번은 문서 축소이며 다음 검사는 **NOT_RUN**이다.

1. 신규 정식 계정의 서버 생성→첫 출정→귀환 지도→첫 착공→재접속 공사 상태를 실제 게임에서 확인한다. 개발 저장 없이도 동작하고 개발 파일이 존재해도 이를 수입하지 않아야 한다.
2. 신규 E0→3→6→10, 읽기/취소 무지급, 완료 중복 max·상한, 장부와 Core validation·출정 snapshot 정합을 검사한다. 숫자의 페이싱/밸런스는 [가설]로 측정 후 조정한다.
3. 개발 자동 장원/지도 자료는 읽기 전용이며 원본 바이트가 바뀌지 않는다. 개발 재화·시간 가속·가신 진행을 정식 서버 계정에 보내지 않는다.
4. 서버 ADR의 동시성·내구성·복구·장애·롤백 검증을 별도 구현 PR에서 보고한다. 해당 설계/검증 완료를 이 문서로 대신하지 않는다.
5. format7 schema1/2·기존 리플레이/골든 보존. 가신 format8/독립 블록은 [ADR0075](../../adr/0075-independent-vassal-replay-format-eight.md)를 따르고 판 시작 snapshot 뒤에는 소급하지 않는다. FP01은 가신 블록 없는 역사 해시·성능 회귀, 가신 효과 없음/최대 비교는 wave 정상 입력·C05에서 한다.

정식 지도 방향과 서버 저장은 사용자 결정이다. **이 축소 문서의 검토·병합 승인은 다시 대기**하며, 가설 수치·게임 적용·서버 구현·실기 검증 승인을 대신하지 않는다.
