## 1. 확정된 화면과 아직 제안인 전환 정책

[확정: 사용자 결정] 정식 영지 화면을 r8 지도로 바꾸고 신규 계정의 첫 영지 진입부터 지도를 쓴다. [첫 접속 시안](https://github.com/hyunlord/bs-mobile/releases/tag/onboarding-first10-542-20261030)의 07~09(터 선택→비용 확인→착공)가 기준이다. 첫 타이틀 탭→첫 출정→카드→첫 판 종료·귀환의 순서는 유지한다. “지도로 시작”은 타이틀 다음에 첫 전투를 취소하고 지도부터 보여 준다는 뜻이 아니다. 첫 판 종료·건설·재출정을 10분 안에 강제로 발생시키지 않는다.

[제안] 신규는 영지가 포함된 저장 v6을 처음부터 생성한다. 영지가 없는 기존 계정은 안전한 비전투 시점에 한 번 변환하고, 구형 장원을 별도 활성 계정으로 병행하지 않는다. 변환 전 원본은 복구용으로 보존한다. 두 지갑·두 생산기를 독립적으로 계속 쓰는 정책은 재화 중복과 진행 분기를 만들므로 거절한다.

[확정된 배치 계약] r8의 13구역·총1,664칸·중앙 시작12×12·시작 건물10채·r3~r7 동결은 [r8 배치 설계](../m3a-r8-layout-proposal.md)를 따른다. 건물45~55px 축소/75px 기본 등의 시각 배율은 승인 그림 계약이며 경제 보상이 아니다.

[가설: 출시 경제 후보] 현행 r8 시제품의 초기 지갑 곡물120·목재180·철재60, 곡창 L1 목재30·60초 등은 화면 검토용 후보다. 이를 첫 판 보상으로 지급하거나 기존 계정에 추가하지 않는다. 신규 초기 지급의 최종값·보호 경로·생산속도는 #126의 경제 검토와 아래 관문을 통과해야 한다. 저장 버전6·리플레이 버전7/8·설정 ID 숫자는 형식 식별자이며 밸런스 가설이 아니다.

### 기존 v6 계정의 생산 정책 전환

기존 v6 r8과 호환 예외 r2~r7도 **정식 지도 경로에서는 새 legacy 방치 생산을 중단**한다. 위 표의 ‘정상 재개/원래 규칙 유지’는 지도 설정·공사·재고·시계를 보존한다는 뜻이며 두 생산기의 병행을 허용하지 않는다. 현재 `MetaProgression` 생성자의 무조건 `AdvanceIdle` 호출을 그대로 통과시키면 이 계약을 어기므로 호스트 연결 전에 분기해야 한다.

[권고: 별도 표식 없는 보수적 전환] 기존 v6에는 v5용 `Migrate`나 ‘마지막 legacy 구간 정산’을 다시 실행하지 않는다. 이미 저장된 legacy pending claim·나머지는 보존하고 한 번 받을 수 있는 장부만 유지한다. 아직 저장/관측되지 않은 legacy 방치 시간은 추가 지급하지 않으며, 지도 시계도 다시 초기화하지 않는다. 정상 지도 Advance가 원래 검증된 구간만 적용한다. 이 정책은 미관측 legacy 보상을 기대한 사용자의 수령량에 영향을 줄 수 있으므로 이번 문서의 사용자 승인 정책이며 실제 이관 검증은 남아 있다. r8/r2~r7 모두 같은 정책을 적용하고 ConfigVersion에 따라 중단 여부를 바꾸지 않는다.

이 권고는 ‘Estate 존재 + 정식 단일 생산 정책’으로 매번 결정되어 일회 지급 표식이 필요 없다. 반대로 기존 v6의 미관측 legacy 시간을 한 번 더 지급하기로 바꾸면 이미 지도에서 생산한 구간과의 겹침, 완료 표식의 내구 저장·재시작 정합을 먼저 설계해야 한다. 현행 v6 필드로 증명할 수 없으면 새 형식/호스트 원장 ADR을 승인받기 전 출시를 막으며 Origin 문자열이나 최초 실행 preference로 추측하지 않는다. 롤백 호환 빌드도 동일한 legacy 중단 정책을 유지해야 한다.

`Origin = new-prototype`/`migrated-v5` 문자열만으로 테스트 저장 여부를 판정할 수 없다. 저장 디렉터리·호스트 실행 프로필·검증된 계정 파일을 기준으로 개발 경로와 제품 경로를 분리하며, 출처 불명 v6은 임의 수입하지 않는다. 기존 v6 호환 예외는 기존 사용자 진행을 지키기 위한 경계이고, 신규 정식 기본값 r8 결정을 뒤집지 않는다.

## 4. 기존 자동 장원 → r8 전환의 불변량

- 변환 직전 지갑, 가신 레벨/승급/조각/해금/편성, 챕터, 완료 도전·해금 콘텐츠·메트릭, 판/받기 순번·완료 판 수, pending claim, 보상 영수증, 결과 보상 기준을 그대로 복사한다. 변환 보상을 새로 지급하지 않는다.
- 대장간·기록소·곡물창고·병영은 종류 ID로 대응한다. 기존 완료 레벨은 아래 이관 표시 대응표로 r8 단계에 대응하며, 이관 자체에 비용·시간을 다시 청구하지 않는다. 현재 구현의 `min(기존 레벨, 3)` 표시를 정식 전환에서 그대로 쓰지 않는 변경 제안이다. **ManorLevels 원본은 절대로 L3으로 잘라 저장하지 않는다.** 높은 기존 효과와 업적을 보존한다. 나머지 시설은 r8 초기 상태이며 임의 완공·구역 개방 없음.
- 자동 장원에는 진행 중 공사/예약이 없으므로 미완료 공사 시간을 만들어 환급하지 않는다. 기존 v6의 공사·예약·구역 준비는 이 전환 대상이 아니며 원래 설정에 고정한다.
- legacy 우선 깃발은 저장에 남기되 자동 성장/자동 지출은 정지한다. 새 공사의 자동 착공은 동의 전 꺼짐이다. 완공을 기다리지 않고 두 번째 출정을 할 수 있다.
- 전환 시각에 구형 방치의 검증된 구간을 마지막으로 정산하고, pending claim과 나머지를 보존한다. 그 뒤 **새 구형 방치 적립은 중단하고 지도 생산만 진행**하는 것을 권고한다. 기존 pending claim은 동일 순번으로 한 번 받을 수 있다. 이전 구간을 지도 생산에 다시 소급하지 않는다. 잔여 구형 나머지는 소급 현금화하지 않고 보존한다. 향후 보상 정책 승인 없이 지도 나머지에 합치지 않는다.
- 지도 시계는 첫 관측을 기준으로 잡는다. 두 시계 역행·불일치 처리, 생산/재고 상한, 공사 순서를 유지한다. 구형 방치 정책 변경은 [ADR0071](../../adr/0071-account-estate-state-and-save-version-six.md)의 미정 병행 생산 부분을 명시적으로 대체하는 **사용자 승인된 전환 설계**다.

### 기존 효과와 새 건설 효과의 경계

기존 `ManorLevels`는 가신 레벨상한·슬롯·연구·방치 효과를 정한다. r8 시각 L1~L3과 기존 효과 레벨은 같지 않다. 변환 순간의 효과 장부·가신 칸수·레벨상한·연구값을 그대로 유지하고 이미 완료한 건물의 효과를 다시 더하지 않는다. 곡창은 생산 단일화에 따른 기능 전환이므로 생산량까지 동일하다고 주장하지 않으며, 아래 가설은 최소한 기존 보관 한도를 지키는 제안이다.

### r2 · 장원 효과 ↔ 지도 건물·레벨 대응표

[현행 근거] [progression.json](../../../data/meta/progression.json)의 장원 4종 최대 효과 레벨은 모두 10이다. `MetaEngine.EffectLevel`은 같은 효과 ID의 `ManorLevels`를 읽는다. 아래에서 **E는 시각 레벨과 다른 효과 장부 값**이다. 기존 공식과 상한은 유지하며, **L1→E3 / L2→E6 / L3→E10 대응만 [가설]**이다. L0는 E0이다. 실제 장부가 낮은 이관 건물은 완료 그림만으로 이 값을 얻지 않는다. 경험치 획득량/가신 경험치 보너스는 이 네 장원 효과에 없으며 새 XP 효과를 추가하지 않는다.

| 기존 장원 ID·효과 | 대응 지도 건물 ID | 지도 L1 [가설] | 지도 L2 [가설] | 지도 L3 [가설] | 유지하는 현행 공식·상한 |
|---|---|---|---|---|---|
| `meta:forge` · VassalLevelCap | 대장간 `meta:forge` | E3 → 가신 레벨 상한 11 | E6 → 17 | E10 → 20 | `min(가신 MaxLevel=20, 5+2E)`; 가신 현재 레벨을 무료로 올리지는 않음 |
| `meta:scriptorium` · Research | 기록소 `meta:scriptorium` | E3 → 연구 조건 ≤3 | E6 → 연구 조건 ≤6 | E10 → 연구 조건 ≤10 | 연구는 E 그대로. 현행 도전 요구는 0~4이며, 연구 충족만으로 도전 완료·보상 자동 지급하지 않음 |
| `meta:granary` · IdleCapacity | 곡창 `meta:granary` | E3 → 보존 시간 9,360초 | E6 → 11,520초 | E10 → 14,400초 | 구형 상한식 `min(14400,7200+720E)`를 지도 보관시간의 하한으로 보존; 구형 생산 재개 금지 |
| `meta:barracks` · VassalSlots | 병영 `meta:barracks` | E3 → 1칸 | E6 → 2칸 | E10 → 3칸 | `min(3,1+floor(E/4))`; 슬롯에 가신을 자동 편성하지 않음 |

**적용 범위는 신규 및 v1~5에서 정식 이관한 r8 효과 adapter뿐**이다. 기존 v6 r2~r7의 동결 설정에 이 표나 새 보관 공식을 조용히 적용하지 않는다. 기존 v6 r8도 아래 호환 예외 검토를 먼저 통과해야 하며, §3의 단일 생산 정책과 이 새로운 효과 매핑은 별도 경계다.

곡창 [가설] 연결식은 `max(현행 지도 StorageSeconds, 위 구형 상한식)`이다. 현행 r8의 기본 보관시간 L0~3은 7,200/7,200/10,800/14,400초이고 장기보관 분기는 +3,600초, 지도 최종 상한은 18,000초다. 이 지도 분기·상한을 먼저 현행대로 계산한 뒤 구형 효과 하한과 max를 취한다. 시간끼리 더하거나 이미 지난 구간을 새로 생산하지 않는다. 재고 수량 상한·생산속도는 기존 지도 규칙대로이며, 이 표는 구형 생산량/헌장 생산까지 유지한다는 약속이 아니다. 그 중단은 §3~4의 별도 승인 정책이다.

### 이관 표시 기준과 v6 효과 장부

[가설: 이관 표시 기준] 다음은 **아직 Estate가 없는 v1~5의 최초 정식 이관에만** 적용한다. L3를 먼저 줘서 후속 효과 성장이 막히는 현행 `min(old,3)` 대신, 완료 효과에 맞는 단계로 옮긴다. 비용 환급·이관 비용·신규 보상은 없다. 이관 후 다음 공사는 해당 지도 단계의 정상 비용·시간을 따른다. 기존에 지불한 구형 레벨 비용과 지도 비용의 총액이 같다는 뜻은 아니며 페이싱 검증 대상이다.

| 기존 장원 레벨/초기 장부 E | 이관 직후 지도 단계 [가설] | 이관 직후 E | 이후 실제 완료로 도달하는 E |
|---|---|---|---|
| 0 | L0 | 0 | L1 완료 3 → L2 완료 6 → L3 완료 10 |
| 1~5 | L1 | 원래 1~5 그대로 | L2 완료 `max(E,6)` → L3 완료 10 |
| 6~9 | L2 | 원래 6~9 그대로 | L3 완료 10 |
| 10 | L3 | 10 그대로 | 이미 최종 상한; 중복 효과 없음 |

[권고: v6 필드 추가 없이] `ManorLevels[id]`를 **단조 증가하는 권리 장부**로 사용한다. 최초 정식 이관은 기존 장부를 그대로 복사하고 지도 레벨을 위 표로 배치한다. 신규 계정의 네 장부는 0이며 네 효과 건물은 L0로 시작한다. 현재 r8의 startsComplete는 효과 없는 집뿐이므로 E0이다. 향후 네 효과 건물을 startsComplete로 바꾸는 것은 무료 효과 지급 정책 변경이며, 별도 승인 없이 로드 시 대응표로 초기화하지 않는다. 이후 **실제 건설 완료 상태 전이에서만** `E_next = min(10, max(E_current, target[완료 레벨]))`를 적용한다. 화면 표시·로드·이동·전문화·공사 시작/예약/취소·시계 실패·이관 시에는 투영하지 않는다. 효과 읽기와 UI의 현재 보너스 표시는 장부만 읽고 `장부 + 지도 효과`로 합산하지 않는다. 같은 L1이라도 신규 E3과 이관 E1/E5가 다를 수 있으므로 시각 단계 표의 명목값을 현재 효과로 표시하지 않는다.

건물 완료 레벨·공사 종료/다음 예약·효과 장부를 같은 MetaState 후보에 포함해 한 번의 저장으로 커밋한다. 재시작은 저장된 장부를 그대로 읽는다. 완료 직전 장애면 기존 미완료 상태에서 다시 계산하고, 완료 직후 재시도면 같은 max 결과이므로 중복이 없다. 건물만 완료되고 장부가 누락된 부분 커밋은 유효 상태로 취급하지 않는다. 별도 UI preference나 외부 파일에 기준치를 숨기지 않는다. 초기 구형 값은 불변 전환 백업에 남으며 활성 장부는 권리의 현재 최대값을 담는다. 구형 원본과 지도 효과를 나중에 분해해 통계/환급해야 하는 새 요구가 생기면 이 단일 장부만으로는 불가능하므로 별도 저장 설계가 필요하다.

이 방식은 Origin을 계정 출처·보상 자격의 증명으로 사용하지 않는다. 신규 생성/최초 이관/검증된 완료 전이의 명시적 명령 경계로 처리한다. r8 배치·기존 설정 파일을 수정하는 것이 아니라 후속 Core의 효과 연결 정책으로 제안하며, 설정으로 분리할 때에는 새 명시적 정책 버전을 써야 한다.

**기존 v6 호환 예외:** 이미 `min(old,3)`로 L3가 된 낮은 장부의 저장에는 위 최초 이관 표시표를 소급하지 않는다. 완료 레벨·공사·설정·장부를 보존하고 로드 시 `target[L3]`를 지급하지 않는다. 이런 계정은 신규/v1~5와 같은 최종 성장 경로가 아직 없으므로 **정식 효과 연결의 출시 차단 사례**다. 레벨을 몰래 낮추거나 무료 E10을 주어 해결하지 않는다. 알려진 v6별 상태 분류와 별도 전환 정책의 사용자 승인이 선행되어야 하며, 호환 화면에서 재개 가능하다는 사실을 성장 경로 해결로 보고하지 않는다.

### 계산 예시·검증 범위

다음 숫자는 위 [가설] 표의 산술 검산이며 게임 실행 결과가 아니다. 네 효과를 같은 E로 놓은 설명용 예시다.

| 입력 | 최초 이관(지도/E) | 슬롯 / 가신 상한 / 연구 / 구형 시간 하한 | 다음 완료 후 | 반복 로드·완료 재적용 |
|---|---|---|---|---|
| 낮음 E1 | L1 / E1 | 1 / 7 / 1 / 7,920초 | L2 → E6: 2 / 17 / 6 / 11,520초 | E1은 로드로 E3이 되지 않음; 완료 E6 재적용도 E6 |
| E3 | L1 / E3 | 1 / 11 / 3 / 9,360초 | L2 → E6, L3 → E10 | 이관·반복 로드 E3 유지 |
| 중간 E5 | L1 / E5 | 2 / 15 / 5 / 10,800초 | L2 → E6, L3 → E10 | E5+E6=11로 합산하지 않음 |
| E6 | L2 / E6 | 2 / 17 / 6 / 11,520초 | L3 → E10 | 이관·반복 로드 E6 유지 |
| 높음 E8 | L2 / E8 | 3 / 20 / 8 / 12,960초 | L3 → E10: 3 / 20 / 10 / 14,400초 | 이관 L2의 E6 때문에 E8이 줄지 않음 |
| E9 | L2 / E9 | 3 / 20 / 9 / 13,680초 | L3 → E10 | 이관·반복 로드 E9 유지 |
| 최대 E10 | L3 / E10 | 3 / 20 / 10 / 14,400초 | 변화 없음 | 상한 초과·재보상 없음 |

구현 관문은 네 ID 각각 E0~10 전수, 신규 L0→L3, 이관 전후 장부·슬롯·가신상한·연구 동일, 곡창의 기존 시간 하한 보존(생산량 동일 아님), 각 완료 전/후 장애·중복 명령, 기존 v6 L3/E1 예외를 포함한다. 기록소의 연구 해금은 기존 도전 메트릭·pending claim·수령 장부 경로를 거쳐 한 번만 처리한다. 가신 능력별 판 안 cap·현재 편성·보유 레벨은 별도 기존 규칙을 유지한다. **문서 최종 승인은 가설 수치의 밸런스 검증이나 효과 연결의 출시 관문 통과를 대신하지 않는다.**

## 5. 호스트 트랜잭션과 장애 복구

승인된 구현 순서(아직 구현 안 됨):

1. **첫 쓰기 전 진입 검증:** 계정 경로 단위 단일 writer 소유권을 확보하고 read→command→publish 전체를 직렬화한다. 두 호스트 인스턴스·재진입을 거절하며, `AtomicSaveStore`의 인스턴스별 lock이나 공유 Mac의 Unity 작업 잠금을 계정 잠금의 대체물로 보지 않는다. 판/카드/정산 중 전환을 막는다. 로드한 v6는 ConfigVersion의 정확한 설정을 resolve하고 **terminal 복구를 포함한 첫 startup Publish 전에** 의미 검증한다. Estate 없는 v1~5는 기존 계정 검증과 대상 r8 설정 검증을 먼저 수행한다. unknown ConfigVersion은 미지원 설정으로 분류해 쓰기를 막으며 기본 r8 대입·일반 손상 취급·낡은 backup fallback으로 우회하지 않는다.
2. **정산과 체크포인트:** 설정/계정 검증 후 `terminal.bin`의 기존 exactly-once 복구를 완료한다. pending 판은 기존 정책대로 정산/포기 처리하며 새 보상 사실을 만들지 않는다. 구형 규칙의 마지막 방치 정산을 한 번 반영한 v5 체크포인트를 `Publish`한다. 모든 legacy 생산 진입점(생성자와 public `AdvanceIdle` 포함)에 동일한 단일 생산 정책을 적용한다. 정산 전 사본으로 재시도해 같은 구간을 재지급하지 않는다.
3. **불변 복구 세대:** 검증된 체크포인트 progress와 대응 terminal을 한 세대로 복사한다. 호스트 manifest에 세대 ID, 각 파일의 존재 여부(terminal 원래 없음 포함), 내용 hash, progress/terminal 정산 순번, 체크포인트 hash 및 완료 상태를 묶는다. 파일 쓰기·flush·실제 재읽기 hash 검증을 마친 뒤 완료 manifest를 마지막으로 내구 커밋한다. 완료 표식 없는 부분 사본은 복구 세트가 아니다. 완성 세대는 덮어쓰지 않는다. 같은 체크포인트 hash/파일 존재·내용이 모두 일치하면 검증된 완성 세대를 재사용하고, 미완성 세대만 있거나 최신 체크포인트가 달라졌으면 새 세대 ID로 다시 작성한다. 실패/이전 세대는 보존한다. 성공한 v5 체크포인트 이후 사본 생성만 실패한 재시도는 디스크의 최신 체크포인트부터 시작하며 마지막 정산을 되감지 않는다. 일반 `.bak`은 다음 저장에 교체되므로 불변 세대를 대신하지 않는다.
4. **이관 후보 의미 검증:** 동일 r8 설정을 고정한 메모리 사본에서 위 [가설] 이관 표시 기준을 반영한 후속 `Migrate` 경로를 호출한다(현행 `min(old,3)` 구현 그대로가 아님). v6 encode→decode→계정 검증에 더해 정확히 resolve한 설정으로 건물 Kind·레벨 상한·좌표/점유·열린 구역·공사와 예약 target·branch·생산 remainder 계약을 검사한다. 기존 v6 로드와 후보 모두 같은 의미 검증 경로를 사용한다. codec의 구조 검사나 Run의 ConfigVersion 문자열 일치만으로 통과시키지 않는다. 전후 보존 필드도 비교한다. `MetaValidation`의 가신 상한·편성·도전 장부는 같은 효과 장부와 일치해야 한다. ConfigVersion/설정 hash·전후 save hash·사용한 복구 세대 ID는 호스트 진단 기록에 두며 Core에 파일 I/O나 시스템 시각을 넣지 않는다.
5. **커밋 확인:** 기존 원자 저장 경로로 v6 후보를 커밋한 뒤 **실제 primary 파일을 직접 다시 읽어** 예상 후보 hash·decode·설정 의미 검증과 읽기 출처 `Primary`를 확인한다. 메모리의 전달 bytes를 다시 decode하는 현행 Publish 검사는 이 관문의 대체물이 아니다. 일반 로더의 backup fallback 성공도 새 v6 커밋 성공으로 보지 않는다. 확인 전까지 지도 명령·새 판 출정을 막는다. replace는 성공했으나 재읽기가 실패하는 등 커밋 여부가 불명확하면 계정 명령과 쓰기를 중단하고 디스크 상태를 다시 로드·검증한다. **낡은 메모리 v5로 계속 Publish하지 않는다.** primary가 확인되지 않으면 복구 상태로 남고, backup 복원은 별도 명시적 복구 절차로 처리한다.
6. **재시작:** 유효 primary v6면 같은 설정으로 재개하고, 유효 v5면 최신 체크포인트부터 재시도한다. `Estate != null`과 ConfigVersion 및 검증된 primary가 성공 정본이며 UI flag는 정본이 아니다. 임시 파일·부분 복구 세대·backup fallback만으로 이관 성공을 판정하지 않는다. 원본/백업/manifest가 충돌·손상되면 중단하며 새 계정을 만들지 않는다. terminal 순번이 앞선 경우 삭제하거나 낡은 progress로 되돌려 우회하지 않는다.

시간은 호스트가 관측한 monotonic/wall 값을 Core에 입력한다. **동일 관측 입력**으로 재시도하는 결정성 검사는 같은 후보/장부/hash를 요구한다. **시간이 지난 재접속**은 새로운 검증 구간만 인정하므로 최종 bytes까지 동일할 필요는 없으며, 이전 인정 구간과 겹치지 않는지·보상이 한 번만 지급되는지를 검사한다. 계정 writer 잠금과 이 시간 입력 계약은 서로 다른 책임이다.

복구 사본·진단 파일은 호스트 로컬 운영 자료다. 신규 Release 증거 ZIP/CRC/영수증 패키지를 만들라는 요구가 아니다.

## 7. 롤백

- **아직 v6 커밋 전:** v5 정산 체크포인트를 계속 쓴다. 지도 라우트만 끄며 이미 한 번 정산된 보상을 되감지 않는다.
- **v6 커밋 후, 지도 표시 문제:** v6을 읽을 수 있는 호환 패치로 지도 표시만 이전 메뉴/안전한 읽기 화면으로 전환한다. `Estate`와 최신 지갑·받기·재고·공사·가신·판 진행을 보존하고 자동 장원 성장은 재개하지 않는다. UI 롤백이 생산기를 둘로 만들면 안 된다.
- **변환 직후 데이터 결함:** 전환 후 어떤 판/공사/받기/강화/시간 생산도 커밋되지 않았고 최신 hash가 최초 v6 후보와 같을 때에만 검증된 변환 직전 사본 복원을 검토할 수 있다. 복원은 지원 도구의 명시적 절차이며 앱 자동 로딩 경로가 아니다. 원본과 실패 후보를 모두 보존한다.
- **이미 새 진행이 있음:** 구형 사본 복구는 새로 얻은 자재·조각·해금·건설을 잃으므로 금지한다. 최신 v6을 보존하는 수정 패치/전진 복구를 한다. 범용 v6→v5 역변환은 제공하지 않는다.
- **옛 앱 바이너리 다운그레이드:** v6 미지원 앱은 unsupported-version으로 쓰기 중단해야 한다. 낡은 `.bak`을 읽어 새 진행 위에 쓰지 않는다. 되돌릴 호환 빌드의 v6 읽기·효과·단일 생산 경계가 확보되지 않으면 바이너리 롤백 대신 기능을 잠그고 전진 수정한다.

## 8. 구현 승인·전달 관문

아래는 향후 실행할 검사이며 이번 문서 PR의 통과 실험이 아니다.

1. **저장 행렬:** v1~5 각각, 높은/낮은 장원 레벨, 0/상한 지갑, 가신·조각·미수령 도전/방치·보상 영수증, pending/terminal 복구 표본에서 보존량과 exactly-once를 비교한다. 시제품 초기 지갑 덮어쓰기 0건.
2. **실패 주입:** 사본 쓰기/정산 publish/후보검증/원자 replace/재읽기 전후에서 종료·디스크 실패를 넣는다. 동일 시간 입력의 재시도는 동일 상태이며, 시간이 지난 재접속은 새 인정 구간만 반영한다. 중복 지급·초기화·이중 변환 0건. 첫 startup Publish 전 의미 검증, unknown 설정 fallback 금지, terminal 없는 복구 세대, 사본 절반 작성, primary 재읽기 실패/backup fallback, 두 writer·재진입을 포함한다. 미래버전/설정불일치/손상백업은 fail-closed.
3. **시간·생산:** 전환 경계에서 legacy의 마지막 인정 구간과 지도의 첫 관측이 겹치지 않음. 기존 pending claim과 지도 claim 독립 exactly-once. clock 역행·부팅 기준변화·장기 방치에서도 기존 방어 유지.
4. **효과:** 모든 이관 장원 레벨의 슬롯/가신상한/연구가 변환 전후 동일. 곡창은 기존 보관 한도 이상인지 확인하고 생산량 동등성으로 확대하지 않음. 새 건설의 승인 효과표·cap·단일 투영을 확인하고 신규/이관 장기 진행의 막힘을 비교한다. 미승인 대응표로 출시는 금지.
5. **기존 v6:** r2~r7 샘플은 자기 설정의 지도·좌표·공사·재고로 재개. 비저장 개발 사본은 제품으로 수입되지 않음. r8 계정은 반복 접속/이관 시 초기화 없음.
6. **롤백:** 새 진행 없는 전환 실패와 새 진행 있는 UI 롤백을 분리한다. 후자의 최신 지갑·조각·공사·순번 손실 0, legacy 생산/자동 성장 재개 0을 증명한다.
7. **화면:** 정식 빌드 신규 첫 타이틀→첫 판→귀환 지도→비용 확인/착공/닫기→재출정, 기존 계정 전환 후 지도, 재시작 공사 유지. 개발 표시 없음·48pt 터치·승인 r8 배율을 실제 게임 화면으로 점검한다. 10분 완주나 게임 재미는 정적 검사로 대체하지 않는다.

이 문서는 사용자 최종 승인됐지만 경제/효과 수치 가설의 검증·실제 저장 전환 검증까지 완료된 것은 아니다. 코드 구현 PR은 사용자 결정을 참조하고 위 관문 결과를 별도로 보고한다.
