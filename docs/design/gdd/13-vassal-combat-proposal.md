## 2. 능력별 수치와 판 안 상한 [가설]

신규 식은 `raw_i = B_i + S_i×(L−1) + R_i×rank`, `bonus_i = min(cap_i, sum(raw_i))`, `multiplier_i = 1000+bonus_i`이다. 단위는 permille(10‰=1%). 선택ID는 중복 불가, 최대3명이다. 동일 능력의 미래 가신이 추가돼도 합산 후 cap을 적용한다. 현재6명은 서로 다른 능력이라 중복 능력은 없다.

| 가신/능력 | B / 레벨당 S / 승급당 R (‰) | L1/R0 | L5/R0 | L20/R5 계산 | 판 안 cap |
|---|---:|---:|---:|---:|---:|
| 고랑 방패수 · 공격 | 10 / 3 / 6 | 1.0% | 2.2% | (10+57+30)=97‰, 9.7% | 100‰, 10% |
| 황금밭 호위 · 최대체력 | 20 / 5 / 10 | 2.0% | 4.0% | (20+95+50)=165→150‰, 15% | 150‰, 15% |
| 귀환 대장 · 이동 | 5 / 1 / 3 | 0.5% | 0.9% | (5+19+15)=39‰, 3.9% | 50‰, 5% |
| 비옥도 측량관 · 농지 성장속도 | 10 / 3 / 5 | 1.0% | 2.2% | (10+57+25)=92‰, 9.2% | 100‰, 10% |
| 징집 조장 · 아군 피해/체력 | 15 / 4 / 8 | 1.5% | 3.1% | (15+76+40)=131‰, 13.1% | 각150‰, 15% |
| 수확 서기 · 판 안 경험치 | 5 / 2 / 4 | 0.5% | 1.3% | (5+38+20)=63‰, 6.3% | 80‰, 8% |

이 값들은 기존 +32%를 wave에 그대로 넣지 않기 위한 첫 실험안이다. 승급·레벨 비용/보상은 이번 설계에서 조정하지 않는다. 체력처럼 cap에 먼저 닿는 경우 이후 레벨의 전투 증가분이0일 수 있음을 UI에 숨기지 않는다. 이런 성장 정체가 적절한지도 실험 항목이며 계수 재승인 전 출시하지 않는다.

### 정수·누적 계약 [제안]

새 경로는 정수 permille만 사용한다. 체력/이동/피해의 기본식은 `floor(base×multiplier/1000)`, 유효한 양수 피해만 최소1로 보존한다. 기존 FP의 올림 계산은 그대로 둔다. 작은 수치에서 효과가 사라지는 경우는 문서화하고 임의 매 타격 +1로 부풀리지 않는다. 농지 진행·XP처럼 반복 누적하는 값은 소수 나머지를 정수 accumulator로 보존하고 snapshot/runtime state hash에 포함한다. accumulator가 필요 없는 구현을 선택하려면 작은값 편향 검사를 먼저 제시한다. 아래 순서를 이 PR의 검토안으로 제안하며, 실제 함수 연결 및 wire codec은 승인 후 ADR과 구현 검증으로 확정한다.

### 배율 순서·아군 범위·나머지 수명 [가설·검토안]

- **피해:** 기존 영웅/아이템/특허장/무기레벨/진화 파이프라인이 산출한 피해 `D_existing`에 마지막으로 유효한 `D_existing>0`일 때만 `D=max(1,floor(D_existing×(1000+bAttack)/1000))`를 한 번 적용한다. `D_existing<=0` 또는 기존 무효/완전 차단 판정은 원래0/무효로 유지하여 피해를 새로 만들지 않는다. 기존 파이프라인 내부 반올림을 이동하지 않는다. 아군 피해는 같은 마지막 단계에서 Attack 대신 Allies만 적용한다.
- **체력/이동:** 기존 영웅·아이템 등으로 계산한 해당 시점의 가신 제외 값 `H_existing`, `V_existing`에 각각 한 번 floor 곱을 한다. 가신 계수는 snapshot 상수이며, 기존 정상 판 안 성장으로 기본값이 바뀌면 원래 값에서 재계산한다. 이전 가신 적용 결과에 다시 곱하지 않는다. 현재체력 증가·회복·부활 규칙은 기존 경로를 따르고 새 최종 최대체력을 넘지 않는다. 계정 변화로는 재계산하지 않는다.
- **아군 적격성:** 첫 구현 후보는 [WorldState](../../../core/src/SowSiege.Core/WorldState.cs)의 `PersonState.Role == "vassal"`에만 제한한다(`person.vassal`은 표현 역할명이며 별도 타입이 아님). [EstateSystem](../../../core/src/SowSiege.Core/EstateSystem.cs)의 `peasant`, `militia`, `guard`, `returning`은 제외한다. 민병/징집병, 주민, 귀환 중 사람, 전환된 적, 건물, 영주에는 확장하지 않는다. 현행 wave는 [Simulation](../../../core/src/SowSiege.Core/Simulation.cs)의 estate.Initialize/Tick 경로를 실행하지 않아 이 역할이 없으므로 Allies는 no-op이다. 새 개체를 생성하지 않는다. 따라서 wave에서 징집 조장의 실제 전투 기여는0이며, 이 능력의 활성화는 별도 전장 아군 설계/승인 없이 약속하지 않는다. 현재 및 판 중 새로 생성되는 적격 개체 모두 생성 시 최대체력에 한 번 적용한다. 피해는 타격마다 기존 최종값에 한 번, 회복/부활은 적용된 최대체력으로 clamp하며 재부활 때 중복 배율을 금지한다. 현행 자연 귀환 전환은 militia/guard에만 있고 vassal에는 없다. 다음은 향후 역할 전환을 위한 방어적 제안이다: 역할이 vassal에서 비적격 역할로 바뀌면 피해 배율을 즉시 제외하고 최대체력은 가신 제외 기본값으로 복원하여 현재체력을 clamp한다. 반대 전환은 원래 기본값에서 최대체력을 재계산하되 전환만으로 현재체력을 회복하지 않는다. 구성원 수를 HP에서 환산하는 코드도 해당 개체의 적용된 1인당 체력을 사용해야 하며 역사 경로는 수정하지 않는다. 이 역할 전환/구성원 수 계약을 구현 테스트에 고정한다.
- **Growth 나머지:** 키는 판 안 농지의 안정적인 entity ID다. `numerator=기존 진행량×(1000+bGrowth)+remainder`, 지급량은 `numerator/1000` 정수몫, 새 나머지는 `%1000`이다. 같은 농지의 성장단계 전환에서는 보존하고 수확/재파종의 새 주기 시작 또는 농지 제거 때 폐기한다. 새 entity에는 이전 ID의 나머지를 재사용하지 않는다. 영주 사망만으로 살아 있는 농지의 나머지를 지우지 않는다.
- **XP 나머지:** 키는 영주 entity ID와 지급 범주(enemy/harvest/tax/event)의 쌍이다. 같은 몫/나머지 식을 사용하고 범주 사이 나머지를 합치지 않는다. 레벨업·시즌 전환·동일 판의 사망/부활에서는 보존하며 판 종료/새 출정에서 초기화한다. 동일 보상 이벤트 중복 지급 방지는 기존 이벤트 처리 책임이며 나머지로 중복 지급을 정당화하지 않는다.
- **복구/해시:** Growth/XP 키를 안정적으로 정렬한 나머지0..999를 runtime state와 hash에 포함한다. 복구는 저장된 값을 그대로 되살린다. phase 전환 중 유지할 entity와 제거할 entity를 동일 규칙으로 처리하며, 사라진 농지의 고아 키는 거부한다. snapshot은 계수와 버전, runtime state는 변화하는 나머지를 소유한다.

필수 경계 테스트는 기존 배율2종과 가신 배율의 순서/단1회 floor, 판 중 적격 아군 생성·사망·회복·부활, 비적격 민병/전환적 제외, 농지 단계전환/수확/제거/ID재사용, XP 범주별 작은 지급의 누적, 사망·phase·저장복구 전후 동일 나머지·hash다. 타입 매핑이나 기존 판 안 성장 경로가 이 계약과 충돌하면 구현자가 임의 확장하지 않고 설계 차이를 보고한다.

## 3. 시작 snapshot과 변경 불가 경계 [제안]

1. 출정 확정 직전 Core가 해금·선택ID 중복·최대칸·레벨/승급·BM 자격을 검증한다. 검증 실패를 자동으로 최대값/0으로 고치지 않는다.
2. 선택ID를 ordinal 순서로 정렬하고 ID/level/rank, 유효칸과 상한 근거, 가신규칙버전·content hash, 계산된6개 bonus, 판에 필요한 반올림/accumulator 버전을 snapshot으로 고정한다. 정의와 계산값 불일치는 거부한다.
3. UI는 시작 snapshot의 읽기 전용 복사본을 표시한다. 시작 이후 live catalog/지갑/편성으로 다시 계산하지 않는다. 필요한 정의는 content hash로 고정된 판 소유 카탈로그 사본을 사용하고 누락·불일치 시 복구를 거부한다.
4. 시작 후 계정 강화·승급·공사완료·보석/권 사용·출전편성 변경은 진행 중 판에 소급하지 않는다. 새 snapshot은 다음 출정에만 사용한다. 초기 snapshot은 복구/재생에서도 동일하다.
5. 계정 재화를 매 틱 읽지 않고 외부시각·네트워크·호스트 상태를 Core 규칙에 넣지 않는다. snapshot은 새 영웅/영지 ID를 하드코딩하지 않고 명시적 opt-in으로 전달한다.
6. 이탈/복구는 시작 snapshot을 복원한다. 새 메타 상태로 재계산해 더 강한 판으로 이어가지 않는다. 중간 업그레이드 허용 여부 자체도 기존 계정 명령 검증을 따른다.

## 4. replay format7·영지 opt-in 호환 검토

[ReplayCodec](../../../core/src/SowSiege.Core/ReplayCodec.cs)의 현재 format7은 estate schema1, 근접조준 포함 시 schema2를 쓴다. 가신 snapshot 필드는 없다. [WaveEstateContract](../../../core/src/SowSiege.Core/WaveEstateContract.cs)의 EstateRunOptions는 Version/LoadoutId/LoadoutCatalogHash이며 가신 정보가 아니다. 기존 `wave-estate-effects-v1`/clock 블록의 뜻을 몰래 넓히지 않는다.

| 선택지 [미정] | 이점 | 위험/권고 |
|---|---|---|
| format7에 새 명시적 schema3와 별도 가신블록 | 영지+가신 같은 실험 입력 묶음 | 기존7 reader의 알 수 없는 schema 거부·header 길이·hash계약 확인 필요. 현재 schema1/2 rewrite 금지 |
| 새 replay format과 별도 optional 가신블록 | 구형 reader가 명확히 거부, 새 효과 선택 경계 분명 | parser·state codec·복구 확장 필요. **분리 가능성이 명확해 우선 권고**하되 번호를 이 문서에서 예약/확정하지 않음 |

### 우선 wire 후보 [승인 필요·미구현]

후속 ADR의 우선안은 **새 format8 후보**와 독립 `vassal-run-v1` 블록이다. 8은 제안 번호이며 현재 reader가 지원한다거나 예약됐다는 뜻이 아니다. format7 schema1/2는 손대지 않는다. 새 envelope의 구체 저장 순서는 ADR에서 현행 옵션 블록과 함께 검증하되 가신 블록 내용은 다음 후보로 고정한다.

| 필드 | 제안 계약 |
|---|---|
| tag/schema | `vassal-run-v1`, schema=1; 알 수 없는 tag/schema 거부 |
| flags | unsigned32; bit0=enabled, bit1=earned-eligibility-hash 포함. bit2–31은0만 허용, unknown bit 거부. 가신 블록 존재 시 bit0 필수 |
| rules/content | 규칙ID·버전, canonical content SHA256, 계산/나머지 버전. 출정 중 다른 catalog 재조회 금지 |
| eligibility | bit1일 때 earned 원장/자격 snapshot SHA256 필수; 없을 때 필드도 없음. BM 대안B 승인 전 bit1은 실험전용이며 실제 적격성을 보장하지 않음 |
| roster | count0..3, ID ordinal 정렬·유일, 각 level1..20/rank0..5, eligible=true만 허용. count≤effective slots, level≤effective cap 검증; 선택당시 effective slot/level cap과 검증근거 hash 포함 |
| effects | 고정 능력ID Attack/Health/Movement/Growth/Allies/Experience 각각 정수 raw/capped bonus, 해당버전 cap·적용범위. 누락·중복·재계산불일치 거부 |
| restore | 원래 snapshot bytes/hash 및 농지·XP 나머지 state를 저장. 빈 나머지도 버전 정의대로 처리; live 계정으로 복구하지 않음 |

블록 absent이면 기존 format/헤더/옵션/종결 bytes 그대로다. enabled+빈 roster는 명시적 실험 on 상태로 absent와 다르며0효과를 명확히 기록한다. format8을 모르는 reader는 unknown version 오류로 실패해야 하고, 조용히 가신효과를 버려 format7로 재생하면 안 된다. 새 format8 내부에서 estate absent/present 및 melee 옵션의 조합을 검증하며 기존 estate schema의 의미를 재사용·변경하지 않는다.

둘 중 하나를 승인·ADR로 확정하기 전 구현하지 않는다. `null/absent`는 과거와 동일 바이트/실행경로여야 하며, 효과가0인 명시적 enabled snapshot은 absent와 구분한다. 알 수 없는 버전·중복ID·범위 밖 값·hash불일치는 거부한다. 기본 프로필/datahash에 실험값을 섞지 않고 `data/opt-in/` 경계를 유지한다.

- old format1–7, schema1/2, 기존 golden·종결해시는 그대로 보존한다. 새 효과를 켠 결과는 새 fixture/hash로 추가하며 기존값을 재고정하지 않는다.
- 현재 C05/FP01에는 가신 snapshot이 없으므로 원본 재생에 새 계정 snapshot을 주입하지 않는다. 후속 비교 입력은 원본의 불변 복사와 새 메타데이터로 분리한다.
- 새 상태 필드/나머지가 없을 때 기존 catalog/state bytes를 그대로 유지하는 음성 대조가 필요하다. 새 on 경로만 두 Core 타깃/Editor/재생 일치를 별도 검사한다.
- save format6 계정과 replay format7은 다른 계약이다. 새 snapshot 저장을 이유로 과거 계정 데이터를 무조건 이관하거나 초기화하지 않는다.

## 5. BM: 직접 판매와 우회 경로 [미정/승인 필요]

가신·조각·판 안 능력은 판매하지 않는다. '직접 보석 강화 버튼 없음'만으로 전투력 판매 금지가 충족되지는 않는다. BM r2의 상품/가속 화면 승인은 그림 흐름 승인이고 실제 경제·결제 승인과 다르다. 시간당 보석 공통 기준과 권의 소폭 할인 방향은 기록하되 구체 가격/환율/할인율은 미정이다.

| 유료 경로 후보 | 전투력으로 환원되는 경로 | 제안 승인 게이트 |
|---|---|---|
| 곡물·목재·철재 구매 | 공통지갑→가신 레벨업→snapshot bonus | earned-only 자격을 검증할 자료가 없으면 전투 적격 강화에 사용 금지 |
| 직접 공사 가속/성장가속권 | 대장간 상한·병영칸→더 높은 가신/편성 | 외형/비전투 편의 공사로 제한하거나 전투적격 레벨을 별도 증명하기 전 연결 금지 |
| 연구/생산 가속 | 연구조건 도전수령→가신 해금, 생산재화→강화 | '영지 성장만'이라는 명칭만으로 허용하지 않음; 간접경로까지 검증 |
| 무료/플레이 보상 | 현행 플레이 보상→계정 성장 | 현재 유료 경로는 미구현이므로 무료 성장의 전투 연결은 설계 승인 후 가능. 향후 유료 혼합을 허용하기 전에 분리 규칙 필요 |

현행 #122 유료 결제·판매는 미구현이며 과거 계정에 유료 재화가 있었다고 가정하지 않는다. 현행 지갑은 재료별 합계이며 paid/earned provenance가 없다. 현재 상태에서 “유료 재료를 제외한 강화”를 계산할 수 있다고 주장하지 않는다.

| 대안 [승인 필요] | 설계 비용/제약 | 판단 |
|---|---|---|
| A. 무료 플레이·영지 성장에 의한 가신 전투 연결은 승인 후 가능, 유료 자원·가속의 전투성장 경로 연결은 보류 | 현행 무료 계정 성장부터 검증 가능. 유료 상품을 도입할 때 전투 연결 경로 배제/분리 필요 | **단기 권고**. 가신 설계 자체를 무기한 보류하지 않으며 유료 우회 경계는 유지 |
| B. earned-only 전투자격 원장·상한/슬롯/해금 별도 gating | 구매재화·시간·연구까지 추적, save/replay 이관·중복/복구 검증 필요 | **중기 권고 후보**. 사용자가 원장/이관·공정성 규칙을 승인한 뒤 별도 구현 |
| C. 무료/유료 무관 동일 전투상한까지 허용 | paid faster도 동일 시점의 전투력을 바꾼다 | 현재 힘 판매 금지와 충돌하므로 기본 채택하지 않음 |

B의 시작 snapshot은 earned-only 해금/level/rank와 전투적격 대장간·병영 조건만 읽는 방향이다. 기존 계정의 혼합 재화를 모두 earned로 인정하거나 모두 paid로 몰수하는 이관을 임의로 정하지 않는다. 신규 데이터·원장·가속 적용 대상은 미승인/미구현이며 **이 문서만으로 경제 결정을 내리지 않는다**. #122, #126 보류 유지.

## 6. 최대 편성의 영향 예상과 검증 경계

최대3명이므로6효과를 동시에 곱한 수치를 내지 않는다. 아래는 L20/R5가 해금된 테스트 계정의 산술 상한이지 실제 첫 계정·현재 제품 상태가 아니다.

| 가설 조합/가정 | 산술 결과 | 실제 의미의 한계 |
|---|---|---|
| 공격+체력+이동 | 피해×1.097, HP×1.15, 이동×1.039 | 같은 적HP/맞는빈도라면 TTK×(1/1.097)=0.9116, HP소진시간×1.15. 이동효과는 별도이며 승률 배율로 곱하지 않음 |
| 공격+체력 | 단순 HP×피해 지표1.26155 | 약26.2%는 이 두 값의 곱일 뿐 실제 생존율+26.2% 또는 피해감소를 뜻하지 않음 |
| 성장+XP+공격 | 성장×1.092, XP×1.063, 피해×1.097 | XP가 전부 농지에서 온다는 과장된 한계모형에서 성장XP흐름×1.160796, 같은XP 도달시간×0.8615. 적/이동/완료조건 때문에 실제는 다름 |
| 아군+체력+공격 | 아군피해/HP 각×1.131, 영주HP×1.15, 영주피해×1.097 | 아군피해와 영주피해를 같은 피해에 중복 곱하지 않음. 아군 생존 변화가 적수/성능을 바꿀 수 있음 |

**정상 플레이 생존율 예상 [가설]:** 효과가 없는 경우 대비 개선 방향을 예상하지만 현재 정상입력 A/B 자료가 없어 수치 추정의 신뢰도는 낮다. 초기 실험 계획 범위는 최대편성의 완주율 차이 **0~+10%p**로 두되, 행동/성장 피드백으로 **−5~0%p** 악화도 배제하지 않는다. 이는 신뢰구간·측정값·밸런스 통과 기준이 아니다. 기준 생존율을 모르는 상태에서 절대생존율은 **UNKNOWN**이며 시뮬레이션 **NOT_RUN**이다. 범위를 벗어나면 결과를 실패/예외로 기록하고 승인 없이 계수를 조정하지 않는다.

| 프로필/증거 | 실행 길이와 실제 용도 | 신규 최대편성 예상/미확인 |
|---|---|---|
| C05 원본 | 종료14400틱=8분 Quit 역사 replay. 적400–599/600–799/800+ 성능 구간 | 원본8분/Quit·종결hash 유지, 입력 종료시간 변화0. 생존율 N/A(정상 완주율 표본 아님). 새효과 성능/생존 측정 NOT_RUN |
| FP01 원본 | 27000틱=15분, SetInvulnerable/GrantLevel 스트레스. 19891–20790틱30초 측정, 실제199–283적 | 입력 종료시간 변화0(15분 고정), 생존율 N/A(무적 스트레스). 무적 생존을 가신 효과로 주장하지 않음. Native3회 기준선 미측정, 새효과 p95/ms UNKNOWN |
| 별도 정상 A/B [제안] | 무적·자원부여·가속 없이 동일seed/입력/프로필·계정snapshot 비교 | off/최소/최대3명 조합을 분리. 시간제한과 성공조건은 선택한 프로필 원본 유지 |

**프레임시간 예상 [가설]:** 추가 소환체 없이 시작 snapshot의 상수 계산을 사용하므로 직접 계산비용은 작을 것으로 예상한다. 새 max 조합의 fresh 기준 대비 p95 **0~+5%** 범위를 작업 가설로 두지만, 적수·수확·아군 생존량 변화로 더 커질 수 있다. 이 범위는 측정이나 성능 보장이 아니다. C05의 기존20% 회귀 계약을 약화하거나 FP01 미측정값을 추정 ms로 채우지 않는다. 역사 C05 d71be4d→e81e44a의 +10.4/+8.0/+9.0% 관측은 별도 변경 결과이며 이번 효과 예상의 근거 수치로 재사용하지 않는다.

## 7. 승인 후 구현·검증 순서

1. 사용자에게 계수/cap, Growth·Allies 범위, BM 대안, replay 확장 방향을 승인받는다. 이 설계 PR은 그 전까지 OPEN으로 둔다.
2. 별도 ADR·이슈에서 opt-in snapshot/schema·save복구·적용순서·earned-only 필요성을 결정한다. GDD 승인만으로 SDK/경제 구현을 열지 않는다.
3. 공식 경계값(L1/L5/L20, R0/R5, 빈칸/1/3/중복4인), clamp·정수나머지, 구매/강화 중 snapshot 불변, 잘못된 hash/version 거부를 Core에서 검증한다.
4. old replay/golden/format1–7 absent 경로 bytes/hash를 먼저 확인하고 새 on 경로를 별도 fixture로 추가한다. 영지효과 off/on과 가신 off/on 4조합을 검사한다.
5. 정상 A/B 동일seed 최소32개와 실제 종료조건을 고정해 완주율·사망틱·피해몫·농지완료·XP도달·아군수·효과별기여를 보고한다. 32개로 좁은 신뢰구간을 주장하지 않고 실패도 보존한다.
6. C05/FP01 원본 회귀와 새 max 스트레스는 분리한다. 동일기기/설정 Native3회·원본종결hash·적수분포를 기록한다. Editor/IL2CPP·실기 관문은 실제 수행한 것만 보고한다.

현재 완료한 것은 소스 대조와 문서 산술뿐이다. 새 코드·시뮬레이션·플레이·성능 측정·리플레이 실행은 모두 NOT_RUN이다.
