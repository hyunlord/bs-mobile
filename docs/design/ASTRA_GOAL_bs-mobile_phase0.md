## 너의 역할
새 모바일 게임(가제 Sow & Siege)의 **기획 검토자 + 조사자 + 콘텐츠 설계자 + 코어 개발자**. 0단계를 끝내고 1단계(회색 상자)를 바로 시작할 수 있는 상태를 만든다.

## 게임 한 문장
뱀파이어 서바이벌·탕탕 특공대류 모바일 액션. 무기뿐 아니라 영지·건물·부하를 키우는 **도구**를 함께 고르고, 도구는 무기처럼 화면에서 발동하며 세상에 무언가를 남긴다. 판타지 세계. Unity, F2P(광고·과금·유저 획득). 상세는 첨부 01·02.

## S0. 개발 기반 (가장 먼저)
- **목표**: 앞으로 몇 달간 여러 에이전트가 이슈를 처리하고 기능을 더해도 구조가 무너지지 않는 저장소. **규칙은 문서가 아니라 CI가 지킨다.**
- **만들 것**:
  1. **저장소 구조**: `core/`(순수 .NET: Core·Sim·Tests·Bench), `data/`(JSON 콘텐츠 + `schema/` + `test/` 더미), `tools/`(검사·리그 스크립트), `docs/`(`design/` `adr/` `runbooks/` `research/` `review/` `league/`), `unity/`(1단계에서 생성, 지금은 README만), `.github/`.
  2. **에이전트 안내**: `AGENTS.md`(Astra·Codex)와 `CLAUDE.md`(Claude Code)는 **같은 정본 한 파일**에서 나오게(한쪽은 다른 쪽을 가리키는 짧은 파일). 내용: 게임 목적 한 문단, 아키텍처 경계, 대전제 P1~P8 요약, 검증 명령, 금지 목록, 이슈·PR 규칙, 문서 위치.
  3. **ADR**: `docs/adr/0001-...md` 형식. 지금까지의 결정(Unity·F2P, 순수 C# 코어, 데이터 주도, 기본 영웅·영지 1, 판타지)을 0001~0005로 기록. 이후 구조 결정은 ADR 없이 병합 금지.
  4. **런북(스킬)**: `docs/runbooks/` 에 반복 작업 절차 — 도구·무기 추가, 콘텐츠 검사, 봇 리그 실행·해석, ADR 작성, 이슈 처리. Claude Code용 `.claude/skills/<이름>/SKILL.md` 는 해당 런북을 가리키는 얇은 껍데기로.
  5. **이슈·작업 관리**: 라벨 체계(`type/` feature·bug·balance·content·tech-debt·research, `area/` core·data·unity·ui·art·meta·bm·infra, `phase/0~5`, `needs-decision`), 마일스톤 = 03 로드맵 단계, 이슈 템플릿(버그·기능·밸런스 발견·콘텐츠 제안·결정 요청), PR 템플릿(연결 이슈·관문 결과·검증 방법·화면). GitHub Projects 보드 1개. **이슈 번호 없는 TODO 주석 금지.**
  6. **작업 흐름**: main 직접 푸시 대신 짧은 가지 → PR → CI 통과 시 자동 병합, 병합 후 가지 자동 삭제(고아 가지 방지). 커밋 메시지는 Conventional Commits.
  7. **코드 품질**: `.editorconfig`, `dotnet format` 검사, nullable 켬, 경고를 오류로, Roslyn 분석기. 콘텐츠 ID는 `core:seed_bag` 같은 네임스페이스 ID.
  8. **아키텍처 적합성 테스트**(CI에서 실패해야 함): Core가 UnityEngine·외부 엔진을 참조하지 않음 / Core에 영웅·영지 ID 문자열 없음 / 숫자 상수 대신 데이터 / 스키마 위반 데이터 / 결정론(같은 seed 3회 해시 동일).
  9. **CI(GitHub Actions)**: PR마다 빌드·테스트·형식·스키마·적합성·짧은 봇 리그 연기 시험. 야간 작업: 긴 봇 리그 + 성능 벤치(BenchmarkDotNet).
  10. **지표 축적**: 커밋마다 성능(틱 p95)·리그 균형 지표를 JSON으로 쌓고, 시간축 그래프 HTML 1장(`docs/metrics/index.html` 또는 Pages). 일회성 합격 판정이 아니라 추세로 본다.
  11. **보안·의존성**: 비밀 스캔과 푸시 보호, Dependabot(NuGet·Actions).
  12. **선택(작동 확인 후 채택)**: PR 자동 리뷰어로 Claude Code GitHub Action / 코드 그래프 Graft의 C# 지원 여부 확인 후 적용.
- **기반 조사(짧게, 설치하면서 확인)**: `docs/research/S0-tooling.md` — 현재 Unity LTS 버전, Unity CLI·Pipeline 패키지 상태(베타 여부, MCP 모드), GameCI 최신 주 버전과 Personal 라이선스 절차, Unity 에디터가 리눅스 ARM64(DGX)에서 도는지, Graft C# 지원. 각 항목 출처·확인일. 결과는 ADR로.
- **만들지 않을 것**: Unity 프로젝트(1단계), 운영 SDK(광고·분석·결제·크래시 — 2단계 전 별도 조사).
- **관문**:
  1. 깨끗한 클론에서 명령 하나(`./tools/check.sh` 등)로 빌드·전체 검사 통과.
  2. **일부러 깨뜨린 PR 5개**(Core에 엔진 참조 / Core에 영웅 ID 문자열 / 스키마 위반 데이터 / 형식 위반 / 결정론 깨짐)가 **전부 CI에서 막히는 것**을 보이고 닫는다. PR 링크를 보고에.
  3. 라벨·마일스톤·템플릿·보드가 실제로 존재(스크린샷 또는 `gh` 출력).
  4. 새 에이전트가 AGENTS.md만 읽고 "도구 하나 추가" 런북을 따라 할 수 있는지, 런북대로 더미 도구 하나를 추가하는 PR로 검증.
- **사용자 권한이 필요한 것**: 브랜치 보호·자동 병합·비밀 스캔 설정에 저장소 관리자 권한이 필요하다. `gh` 인증이 관리자 권한이면 직접 설정, 아니면 `needs-decision` 이슈로 정확한 설정 목록을 남긴다. **저장소가 공개 상태면 자체 호스팅 러너(DGX)는 연결하지 않는다.**

## S2. 순수 C# 코어 골격
- **목표**: Unity 없이 한 판이 헤드리스로 돌아가는 결정론 시뮬레이션.
- **만들 것**:
  - `src/SowSiege.Core`(UnityEngine 참조 없음): 고정 틱(30Hz), seed RNG, 영주 이동, 적 무리(공간 해시 충돌), 경계 있는 지도와 터, 계절 4개, 경험치·레벨업(카드 3장, 희귀도 굴림, 레벨 무제한).
  - 무기 3 + 도구 3(땅: 씨앗 자루 / 건물: 목수 망치 / 사람: 뿔나팔). 도구는 **발동 면 + 성장 면** 둘 다 구현(01 §5).
  - 성장물: 땅(4단계 성장·수확), 건물(터·폐허·재건), 사람(가신 1, 징집병 부대, 백성, 식량 상한).
  - 사람 규칙 **A 군대형 / B 일꾼형 / C 징집·귀농형**을 설정 값으로 전환(01 §7).
  - 적 목표 분화: 영주 / 씨앗 / 익은 밭 / 건물(01 §10). 출현량 = 시간 + 번영.
  - 콘텐츠 정의는 **JSON 데이터**에서 읽는다(코드에 숫자 박지 않기).
  - **확장성 감시**: 기본 영웅·영지 레코드 외에 검사용 더미 영웅 1·더미 영지 1(시작 도구가 다르고 규칙 값 하나가 다름)을 `data/test/`에 둔다. 테스트는 두 조합 모두로 한 판을 돌린다.
  - `src/SowSiege.Sim`: 콘솔 러너. 입력 = seed + 봇 정책 + 설정, 출력 = 결과 JSON.
  - `tests/`: xUnit.
- **만들지 않을 것**: 그래픽, Unity, 메타, BM, 서버.
- **관문**:
  1. 결정론: 같은 seed·정책·설정 3회 → 결과 해시 동일.
  2. 성능: 적 1,000 + 땅 칸 300 + 건물 20 + 사람 60에서 틱 p95 측정치 보고(목표 5ms 이하, 임시 기준. 못 미치면 원인과 병목 위치).
  3. 깨끗한 클론에서 `dotnet test` 통과.
  4. 도구 3개 각각 발동 면 피해와 성장 면 산출이 결과 JSON에 따로 집계됨.
  5. 더미 영웅·영지 조합으로도 한 판이 끝까지 돌고, `src/SowSiege.Core` 안에 영웅·영지 ID 문자열이 하나도 없음(검사 스크립트).

## S3. 콘텐츠 풀 v0 (대량 발상 + 데이터)
- **목표**: 1단계 이후까지 쓸 콘텐츠 후보 풀과 데이터 스키마.
- **만들 것**:
  - `data/schema/*.json`(JSON Schema): 무기, 도구, 특허장, 물품, 영웅, 영지 전통, 가신, 적, 진화, 스킨(외형 전용).
  - 후보 수량: 무기 30, 도구 40, 특허장 16, 물품 60, 가신 16(모두 기본 영웅 아래), 적 24, 진화 30(무기×도구 / 도구×도구 / 도구×성장 상태 고르게).
  - **기본 영지·영웅 후보 3안**(01 §12 선택 기준 ①~④로 평가): 안마다 영지 순환 고리, 시작 도구, 백성 종류, 영웅 능력, 궁합 효과, **광고 첫 3초 장면 묘사**. 권고 1안 표시. 사용자가 고른다.
  - 확장 후보: 영웅 8·영지 6은 **이름과 한 줄 콘셉트만** 표로(데이터 레코드 만들지 않음).
  - 도구 레코드 필수 필드: 태그, 발동 면(형태·피해 계수), 성장 면(대상·산출·주 경로), 바닥값 근거, 반시너지.
  - 영지 전통마다 **고유 순환 고리 1개**(01 P7), 영웅마다 궁합 영지 1개 이상.
  - `docs/content/S3-pool.md`: 사람이 읽는 표 + 태그 분포 표.
- **관문**(자동 검사 스크립트로):
  1. 모든 레코드가 스키마 통과.
  2. 성장 면 없는 도구 0개.
  3. 모든 태그가 3개 이상 레코드에서 쓰임.
  4. 진화가 참조하는 ID가 전부 존재.
  5. 반시너지 쌍 8개 이상.
  6. 스킨 레코드에 수치 필드 0개.
  7. 도구·무기·물품이 기본 영지의 순환 고리와 맞물리는 것이 15개 이상(기본 영지 하나로도 판의 다양성이 나오는지).
