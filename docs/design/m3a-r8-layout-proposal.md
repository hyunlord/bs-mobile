## 적용 문서와 현행 제약

`docs/design/m3-account-estate.md`는 main에 없고 열린 [PR #360](https://github.com/hyunlord/bs-mobile/pull/360)에 있다. 그 초안을 복제하거나 병합하지 않고 현행 [r7 배치 계약](m3a-r7-layout-contract.md)에 본 제안을 연결한다. #360이 나중에 반영될 때 중복 설계가 생기지 않게 이 제안을 참조한다. D8 수호자 조건을 새 개방 조건으로 추가하지 않는다.

현행 [`AccountEstateZone`](../../core/src/SowSiege.Core/AccountEstateContract.cs)은 ID당 `(x,y,width,height)` 하나만 가진다. [스키마](../../data/opt-in/schema/account-estate.schema.json)는 복수 사각형 필드를 허용하지 않으며, [Core](../../core/src/SowSiege.Core/AccountEstate.cs)는 중복 ID와 겹치는 사각형을 거부한다. 따라서 이번 제안은 **각 구역은 사각형 하나, 전체 영지는 13개 사각형의 합집합**으로 모서리를 줄인다. 한 구역을 여러 ID로 쪼개거나 저장에 구역 그룹을 추가하지 않는다. 구역 하나를 복수 사각형으로 만드는 것은 이 제안에 포함하지 않는다.

논리 외곽은 계단 근사이고 View에서는 승인된 풀·강둑·숲·안개와 빛 번짐으로 경계를 숨긴다. 번짐은 닫힌 칸을 열지 않는다. B 회화의 픽셀별 윤곽이나 지난 비교판의 임시 구역 크기를 실행 가능한 좌표로 간주하지 않는다. 특히 이전 B의 시작 62칸은 여기서 폐기하고 r7의 **144칸**을 복원한다. 64×32 등각 투영을 유지하므로 정확한 도식은 세로 회화보다 가로로 넓다. 이 차이까지 포함해 검토한다.

## 13구역과 시작 배치

좌표는 정수 셀의 좌상단이며 범위는 `[x,x+w) × [y,y+h)`다. `x` 증가는 화면 오른쪽 아래, `y` 증가는 왼쪽 아래다. ID의 north/east 등은 기존 ID를 보존한 이름이며 화면의 나침반 방향을 새 규칙으로 삼지 않는다.

## 인접 관계와 되찾기

전체 24개 공유 변과 각 구역의 모든 이웃은 [생성된 인접표](m3-estate-r8/GEOMETRY.md)에 명시한다. **이웃 중 하나라도 열려 있으면 인접 조건을 만족한다(OR).** 표는 자동 개방 순서가 아니라 되찾기 요청이 가능해지는 후보 관계다. 생산시설 수·자원·보호 예약·구역 작업 슬롯 조건은 별도로 모두 만족해야 한다. 모서리 접촉과 그림상 강·다리는 인접을 만들지 않는다.

- 시작에서 북·동·남·서 외곽 네 곳을 선택할 수 있다.
- 북 외곽은 마을·숲·휴경지, 동 외곽은 휴경지, 남 외곽은 마을·휴경지·폐허, 서 외곽은 마을로 이어진다.
- 마을은 언덕·풍차, 숲은 언덕·밭, 휴경지는 밭·강가, 폐허는 풍차·강가로 이어진다. 이미 다른 이웃으로 접근한 경우에도 같은 OR 규칙을 쓴다.
- 바깥 여러 방향으로 확장할 수 있지만 특정 순서를 강제하거나 모든 이웃을 먼저 되찾는 AND 조건을 넣지 않는다.

### 진행 조건 보정 제안: 생산시설 4 → 3

r7은 외곽 4곳과 마을에 완료 생산시설 2개, 나머지 7곳에 4개를 요구한다. 그러나 `ProductionSitesComplete`는 레벨 합이 아니라 `Produces != null && Level >= 1`인 **시설 수**이며, 고정 건물 중 생산시설은 경작지·벌목장·제철소 **3개**다. 현행 추가 건물 생성 명령도 없다. 4개 조건을 그대로 복사하면 좌표 그래프가 연결되어도 마지막 7곳은 열리지 않는다.

따라서 **r8에 한해 기존 4개 조건을 3개로 낮추는 것을 제안**한다. 기존 2개 조건, 구역당 목재 60·준비 30초, 보호 예약과 단일 구역 작업 슬롯은 유지한다. 이는 기하와 별도의 명시적 진행 조건 변경이며 사용자 승인 전에는 데이터에 반영하지 않는다. 비용·생산량·건물 부모 조건·경제 상한 등 다른 수치는 r7을 유지한다. 이 보정이 승인되지 않으면 전체 13구역 정상 개방은 미해결로 남으며 구현자가 임의로 보정하지 않는다.

## 강과 다리 3곳

강은 시작 땅 전체를 피하여 숲에서 동쪽 외곽·휴경지를 거쳐 강가로 이어진다. 원래 물빛을 바꾸지 않는다. 중심선은 `(26,8) → (26,12) → (42,28) → (44,28) → (44,48)`이며 대각 구간은 4방향으로 이어지는 계단 셀로 정의한다. 각 중심선 셀과 그 오른쪽 `(x+1,y)`를 수면으로 표시해 기본 폭 2칸, 대각 연결 행은 3칸이 된다. **정확한 셀 목록은 [geometry-proposal.json](m3-estate-r8/geometry-proposal.json)의 `river.centerline`, `river.cells`가 기준**이다.

| 다리 | 바닥 좌표·크기 | 수면을 건너는 칸 | 양안 접속 칸 | 소속 구역 |
|---|---|---|---|---|
| 북쪽 숲 다리 | (28,16), 7×1 | x=30~32, y=16 | x=28~29 / 33~34 | 숲 |
| 동쪽 생활 다리 | (42,33), 6×1 | x=44~45, y=33 | x=42~43 / 46~47 | 휴경지 |
| 남쪽 강가 다리 | (42,44), 6×1 | x=44~45, y=44 | x=42~43 / 46~47 | 강가 |

수면과 다리는 **View 전용 위치 제안**이다. 물 셀은 1,664칸에 포함되며 면적에서 빼지 않는다. 물을 Core 통행·건설 금지 셀로 만들거나 다리 건설 비용·저장 상태·개방 선행조건을 새로 추가하지 않는다. 현행 규칙에서는 열린 물 표시 칸에도 건물 이동이 가능하다는 제약을 숨기지 않는다. 물길을 고정 장애물로 만드는 요구는 별도 설계다. 각 다리는 해당 소속 구역과 같은 개방·어둠 상태로 표시하며 독립 공사를 만들지 않는다. 양안의 건조 접속 셀은 모두 논리 구역 안에 있다.

## 구현 인계와 동결 경계

1. **구현은 Codex.** 이 PR의 문서 승인 후 별도 구현 PR에서 `data/opt-in/account-estate/m3a-prototype-r8.json`을 새로 만든다. 문서 JSON은 실행 설정이 아니며 로더가 읽는 위치에 두지 않는다.
2. **r3~r7 동결.** 기존 설정 파일·ConfigVersion·저장·원자료·실패 기록을 바꾸거나 덮어쓰지 않는다. 기본 데이터 트리·판 규칙·리플레이 해시는 변경 범위가 아니다.
3. **저장 형식 유지.** [ADR0071](../adr/0071-account-estate-state-and-save-version-six.md)의 형식 6과 기존 열린 구역 ID·ZoneWork 구조를 유지한다. 형식 유지가 r7/r8 설정 호환을 뜻하지 않는다. Core는 ConfigVersion 불일치를 거부한다. r8은 별도 새 영지·저장 경로로 검증하고 r7 저장의 버전 문자열만 고쳐 이관하지 않는다. 자동 이관은 범위 밖이다.
4. 현행 Core의 사각형·인접 계산을 그대로 사용한다. 새 r8 데이터에 승인된 좌표·진행 조건을 적용한다. 다리·강·유기적 외곽은 View 인계다.
5. `EstateDecor.cs`와 `PortraitMetaPanels.EstateMap.cs`의 r7 전용 문자열 분기를 검토하여 r8에도 승인된 바닥·Lv0·건물 크기·빛·길을 명시적으로 선택한다. 새 JSON 하나만 추가하면 r7 표현이 자동 계승된다고 가정하지 않는다. r3~r7의 분기 결과는 유지한다.
6. 확대판·첫 화면은 같은 등각 비율을 유지한다. 전체 영역을 390×844에 맞추려고 격자나 건물을 비등방으로 늘이지 않는다. 집 앞 큰길은 동쪽 생활 다리 방향으로 연결하되 시작 10부지와 광장을 침범하지 않는다. 실제 경로·시인성 검증은 구현 PR에서 수행한다.
