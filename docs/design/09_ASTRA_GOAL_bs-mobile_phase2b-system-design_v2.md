# Astra 의뢰서 — bs-mobile 2단계 B: 게임 시스템 재설계 (v2)

작성 2026-10-10 · v2: 시스템 지도 도구(D1)는 별도 프로젝트 Lattice로 분리 · 기준 main `90c8ca3` · 공통 규칙은 AGENTS.md 그대로(이슈 → PR → CI, 보고 첫 줄 관문 + 커밋·PR·CI 링크, ZIP 없음, needs-decision 이슈, Charter & Kin 커밋 금지).

## 방향 전환 (사용자 결정)
- **밸런스·난이도·경제 수치 조정은 중단한다.** #126은 "보류(시스템 재설계 후 재개)"로 기록하고 닫지 않는다. 기존 실패 판정과 수치는 보존한다.
- 지금 할 일은 **게임 자체의 모양**이다. 무기는 무엇을 할지, 도구는 무엇을 할지, 시스템이 어떤 구조이고 기능끼리 어떤 영향을 주는지를 먼저 전체적으로 세운다. 콘텐츠·비주얼·게임성의 다각화와 고도화가 목표다.
- 사용자는 이 구조를 **한눈에 보는 시각화 도구**를 원한다. 이 도구는 다른 Astra 세션이 **별도 저장소의 범용 도구 Lattice**로 만든다(코드가 바뀔 때마다 갱신되는 웹 뷰어 + MCP). 완성되면 bs-mobile에 렌즈 설정과 CI가 PR로 들어온다. **이 세션은 지도 도구를 만들지 않는다.**

## 현재 진단 (Claude가 저장소 데이터에서 직접 집계, main 90c8ca3)
시제품 지도: 사용자에게 전달된 "Sow & Siege 시스템 지도"(data/에서 생성한 HTML). 요점:
- 설계 216개 중 첫 플레이 가능판에서 동작 77개, 설계 의도대로 고유한 동작 20개.
- 물품 30개 중 24개가 장비 태그 조건의 수치 덧셈(예: 재 모음패 — 설계 "처치 흔적을 모아 다음 파종에 전달", 실제 "원거리 장비 보유 시 공격력 +3").
- 무기 10개가 공격 형태 4가지(방사 투사체 5, 원형 장판 3, 90°, 180°). 고유 동작은 이삭 낫 하나.
- 도구 8개 중 고유 성장 효과 3개. 나머지는 공통 규칙으로 같은 대상을 같은 방식으로 키움.
- 설계 가신 16명 미구현. 판 밖 가신 6명은 공격·체력·속도 % 수치뿐.
- 챕터 10개의 보스가 전부 겨울 사슴, 지형 구성 1종. 차이는 적 체력·위협 배수뿐.
- 자재를 쓰는 곳 10군데가 전부 자재 4종을 요구 → 자재 개성이 없고 목재가 모든 성장을 막음.
- 영지 고유 고리인 비옥도 단계에 연결된 실제 콘텐츠 4개(전투 20, 성장 16).
- 설계 데이터의 `concept`·`effect`·`behavior`는 풍부하지만 런타임으로 옮길 때 수치 덧셈으로 납작해졌다. **문제는 수치가 아니라 메커니즘의 부재다.**

## D1. Lattice가 읽을 수 있게 데이터 정리 (짧게)
Lattice 렌즈가 설정만으로 의미를 읽을 수 있도록 데이터 규약을 맞춘다. 지도 도구 자체는 만들지 않는다.
1. 콘텐츠 레코드의 공통 필드 이름을 통일한다: `id`, `name`, `kind`(무기·도구 등 종류), `tags`, `designStatus`, 설계 의도(`concept`, `effect.trigger/benefit/cost`), 실제 동작(`runtimeProjection.effects[].operation/subject`), 참조 필드(`inputIds`, `linkedToolIds`, `antiSynergy`, `target`, `growth.target`).
2. 참조는 항상 콘텐츠 id 문자열로(이름·인덱스 금지). 다른 레코드를 가리키는 값이 id가 아니면 고친다.
3. 런타임 `operation` 이름 목록과 그것을 처리하는 Core 코드 위치를 `docs/design/runtime-operations.md`에 표로 둔다(Lattice의 "구현됨/설계만" 판정 기준).
4. 스키마 검사에 위 규약을 넣고 CI 통과. 결과는 기존 동작을 바꾸지 않아야 한다(리그·결정론 해시 동일).

## D2. 메커니즘 레퍼런스 조사 (문서)
수치가 아니라 **메커니즘의 종류**를 모은다. `docs/research/mechanics-catalog.md`.
- 대상: Vampire Survivors, Brotato, Megabonk, Survivor.io, HoloCure, 20 Minutes Till Dawn, Halls of Torment, Atomicrops, Thronefall, Kingdom Two Crowns, Dome Keeper.
- 분류: 공격 형태(최소 12종: 부채꼴 근접, 관통 직선, 부메랑, 궤도, 장판, 연쇄 번개, 낙하 폭격, 추적 탄, 반사, 소환, 덫 설치, 오라 등) / 성장·레벨업 방식 / 진화·합성 규칙 / 물품의 효과 문법(트리거→효과→대가) / 적 행동 원형 / 보스 패턴 / 판 구조(웨이브, 상점, 이벤트) / 판 밖 성장 축.
- 각 항목: 무엇이 재미를 만드는지 한 줄, 우리 게임(도구가 곧 무기, 지도 위에 남는 빌드)에 옮긴다면 어떻게 되는지 한 줄.
- 관문: 출처·확인일. 수치·매출 조사는 하지 않는다.

## D3. 시스템 설계서 v1 (핵심 산출물)
`docs/design/08_system-design-v1.md` + 데이터 레코드 갱신(`designStatus: "designed-v1"`). 구현하지 않는다.

1. **시스템 목록과 구조**: 시스템마다 목적, 입력, 출력, 영향을 주는 다른 시스템, 플레이어에게 만드는 결정. 같은 내용을 표(시스템 × 시스템, 칸 = 영향의 종류)로도 둔다. Lattice가 이 표를 행렬 보기로 그릴 수 있게 데이터나 YAML로 남긴다.
2. **무기 로스터 v1 (16~20개)**
   - 공격 형태 최소 10종, 형태가 같은 무기는 최대 2개이고 서로 다른 고유 동작을 가진다.
   - 역할 축(군중 정리 / 단일 대상 / 제어 / 생존 / 영지 연동)을 고르게 채우는 표.
   - 무기마다: 형태, 레벨업 때 늘어나는 것(수량·범위·관통·빈도 중 무엇), 고유 동작 1개, 영지와 얽히는 점 1개, 시각 언어(실루엣·이펙트 색·소리) 한 줄.
3. **도구 로스터 v1 (14~16개)**: 땅·건물·사람 각 4~5개.
   - 도구마다: 발동 면, **지도에 남기는 것**, 그것이 자라는 방식(시간·처치·인접·계절 중 무엇에 반응하는지), 돌려주는 경로(경험치·전투·금화·버프), 잃었을 때 복구.
   - 같은 대상을 키우는 도구끼리도 남기는 것과 자라는 방식이 달라야 한다.
4. **물품 문법**: 모든 물품은 "트리거 → 효과 → 대가" 형태로 행동을 바꾼다. 수치 덧셈만인 물품은 전체의 20% 이하. 30~40개.
5. **특허장 12, 진화 16~20**: 진화는 화면에서 모양이 바뀌는 변신이어야 한다(예: 파종 검무 = 베는 선을 따라 밭이 생김). 교차 진화(무기×도구) 절반 이상.
6. **적 v1**: 일반 12~14, 정예 4, 보스 4~5. 적마다 행동 원형 1개(위장, 훔쳐 달아나기, 돌진, 원거리, 분열, 방어막, 소환 등)와 대응법.
7. **챕터 v1 (10개)**: 챕터마다 고유 장치 1개(예: 강이 범람하는 봄, 밤에만 익는 작물, 안개로 시야 제한, 약탈단 진영, 저주받은 땅). 보스는 2~3챕터마다 바뀐다.
8. **가신 v1**: 설계 가신 16명 중 판 밖 6~8명을 골라, 판 안에서 역할과 능력, 대가가 있는 존재로. 수치 % 강화는 그 위에 얹는 것.
9. **자재·장원 v1**: 자재 4종마다 고유한 출처(판에서 무엇을 키웠는지)와 고유한 소비처. 장원 건물 6~8개. 판 안 선택이 판 밖에서 다른 결과로 이어지는 표.
10. **시각 언어 표**: 종류별로 실루엣 규칙, 이펙트 색, 소리 규칙. 현재 아트 바이블(잉크·과슈)과 판독성 층(적 > 내 공격 > 아군 > 익음/완성)을 지킨다.
11. **구현 순서안**: 웨이브 3~4개로 나누고, 웨이브마다 무엇을 넣으면 판이 가장 크게 달라지는지 기준으로 정렬.

- 관문: 위 수량·분포 규칙을 검사 스크립트로 자동 확인(Lattice가 들어오면 그 발견 규칙으로 옮긴다)(형태 다양성, 수치만 물품 비율, 대상별 도구 수, 챕터 고유 장치 수, 자재 출처·소비처 고유성). 설계서 맨 앞에 10줄 요약.
- **사용자 검토가 관문이다.** 설계서를 보고에 넣고(Lattice 지도가 그때 있으면 그 링크도), `needs-decision` 이슈로 "로스터 v1 승인 / 수정"을 연다. 승인 전에는 대량 구현을 시작하지 않는다.
