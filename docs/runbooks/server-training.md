# 서버 병영 훈련

버전: r2, 2026-10-30. 상태: 구현 초안. [#583](https://github.com/hyunlord/bs-mobile/issues/583),
[GDD15](../design/gdd/15-slg-troops-proposal.md)의 훈련 범위만 구현한다.
병종 비용·시간·상한은 [opt-in 가설 데이터](../../data/opt-in/slg-training-v1.json)이며 #126 확정 경제값이 아니다.
변경 요약: 사용자 승인 환불 보관 계약을 반영한다. 아래 계약의 문서 반영은 구현·검증 완료를 뜻하지 않는다.

## 계약

- 공통 `POST /v1/account/commands` 봉투의 `domain`은 `training`이다.
- `operation: start`, `payload: {"unitId":"slg:levy","count":1}`은 완공 병영·해금·대기 칸·총 점유량·재화를 검사한다.
- `operation: cancel-waiting`, `payload: {"jobId":"대기 작업 UUID"}`는 대기 묶음만 취소한다. 작업 ID는 시작 명령 ID다.
- `GET /v1/account`와 다른 계정 명령도 같은 단일 writer에서 먼저 훈련을 정산한다. 클라이언트의 완료/재접속 요청으로 병사를 추가하지 않는다.
- 실제 차감 비용은 예약 때 저장한다. 대기 작업의 속도·시각은 활성으로 넘어가는 때 고정한다. 활성 종료 시각부터 다음 작업을 시작하며, 긴 미접속이면 두 작업이 같은 정산에서 완료될 수 있다.
- 훈련 지출도 기존 `AccountEstate.ProtectedReserve`가 남겨 둔 첫 생산 경로 자원을 소비하지 않는다. 재화는 있지만 이 보호분을 침범하면 `protected-reserve`로 거부한다. Core 규칙과 r8 설정은 바꾸지 않는다.
- 현재 승인·연결된 속도 효과 공급원은 없으므로 서버 보너스는 0이다. 클라이언트 `bonusPermille` 필드는 거부한다. 향후 효과는 서버만 계산한다.
- 시간 계산은 GDD15의 초 단위 `ceil(baseSeconds × 1000 / (1000 + min(bonus, cap)))`를 한 번 적용한 뒤 UTC 밀리초로 환산한다. 예: 20초, 30%이면 16초다. 생산 보관 상한으로 훈련 경과를 잘라내지 않는다.
- `R/D/W/Q`는 각각 준비/출전/부상/예약이다. 이번 단계는 예약·완료·취소만 변경하고 출정·치료·병력 판매·월드 전투는 추가하지 않는다.

## 승인된 환불 보관 경계

2026-10-30 사용자 결정으로 `refund-policy-pending` 임시 거부를 대체한다. 대기 취소 시 Q는 즉시 해제하고,
지갑 상한 안의 금액만 즉시 반환하며 초과액은 서버의 자원별 환불 대기 잔액 하나에 합산한다.
차감액은 즉시 반환액과 새 환불 대기액의 합과 같아야 한다. 환불 대기는 만료·삭감하지 않는다.

공간이 생기면 서버 정산이 환불 대기부터 자동 전입한다. 재화 지출 직후와 생산 재고를 받기 전에 환불을 먼저 처리한다.
자원별 보관 상한은 `대기 칸 수 × 해당 병영 단계의 최대 묶음 비용`이다. 자동 충당을 포함한 반복 등록·취소에서
이 상한을 지키는지 검사한다. 취소 단계에서 환불을 잘라내거나 정상 훈련에 새로운 거부 규칙을 추가하지 않는다.

환불 보관·전입, 지갑·Q, 영수증과 원장은 같은 계정 트랜잭션에서 기록한다. 별도 Core 필드나 v6 저장 형식을
추가하지 않는다. 기존 거부 구현이 남아 있으면 이 승인 계약은 미구현으로 보고하며, 통과로 표시하지 않는다.

훈련 도메인 버전 1을 유지한다. 이전 시제품 JSON에 `pendingRefunds`가 없으면 빈 잔액으로 읽는다.
기존 R/Q·작업 ID·완료 시각·지갑을 그대로 유지하는 회귀 검사로 이 추가 필드의 호환성을 확인한다.
공통 PostgreSQL schema 버전 2와 Core v6는 바꾸지 않으며 기존 계정 데이터 삭제·자동 이관은 없다.

## 화면 계약

`domains.training`은 병영 단계, 상한, 묶음 상한, 총 점유량, 서버 UTC와 병종별 네 수량을 반환한다.
비용과 `pendingRefunds`는 `[{materialId,amount}]` 배열이다.
`waitingCancellationRefunds`는 `[{materialId,immediateAmount,pendingAmount}]`로 취소 확인 전 분할액을 보여 준다.
활성 작업에는 시작/완료 UTC가 있고 대기 작업에는 없다. 대기의 시간은 기본 시간이며 실제 활성 시점의 속도로 다시 고정한다.
`TrainingHandler.View`는 최종 계정 상태를 읽기만 하므로, 같은 명령으로 병영이 완공된 뒤에도 이전 단계 표시를 반환하지 않는다.
취소 확인에는 총 환불액을 즉시 반환액과 환불 대기액으로 나눠 예고한다. 병영 화면에는 자원별 대기 잔액과
“지갑 공간이 생기면 자동 반환” 안내를 표시한다. 대기 잔액은 사용 가능한 지갑 재화에 더해 표시하지 않는다.

## 검증

`server/tests/SowSiege.Server.Tests/TrainingTests.cs`는 단계·병종·수량·재화·상한·대기 칸, 정확한 완료 경계,
긴 미접속의 연속 완료, 실제 차감액 환불, 수량 보존, 잘못된 payload와 저장 예약 불일치를 검사한다.
HTTP 재전송·계정 행 잠금·원자 DB 저장은 공통 서버 검사와 실제 계정 훈련 흐름에서 별도로 확인한다.
단위 테스트의 완공/재화 fixture는 정상 플레이 지급 경로가 아니며 실제 HTTP 검증에서는 기존 건설·생산 명령으로 진행한다.

환불 보관 추가 관문은 지갑 공간 충분/일부/0, 여러 자원의 공간 차이, Q 즉시 해제, 동일 취소 재전송,
소비 뒤 자동 전입, 생산 수령 전 환불 우선순위, 재시작·응답 유실 후 잔액 보존,
반복 등록·취소와 자원별 상한 ±1이다. 장애 주입으로 지갑·Q·환불 잔액·영수증·원장 전체의 원자 rollback을
확인하고, 기존 Core/v6/리플레이·골든 해시 불변을 별도 기록한다.
