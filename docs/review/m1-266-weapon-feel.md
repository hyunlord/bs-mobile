# #266 무기 손맛 수정: 검토 기록

상태: **부분, 사용자 영상 승인 전**. 기준 브랜치 `feat/258-frame-hero-impact`(초안 PR #261) 위의 View 전용 수정이다. Core 판정·피해·스폰·사건·재생 해시는 바꾸지 않았다. 영웅은 기존 컷아웃 기준선(`a-knight-live`)으로 촬영했다.

## 원인

| 문제 | 원인 | 수정 |
|---|---|---|
| 처치 깜빡임 | Core는 처치 틱에 적을 목록에서 지운다(`WaveRuntimeSystem.cs` 153·160행). 보스 표시 시계는 그 틱의 사건을 표시 시계가 틱에 닿을 때 전달한다(`BossPresentationTimeline.cs` 153행). 30Hz/60fps에서 2표시프레임 동안 적·효과가 모두 없다. 8종 모두 같은 경로 | 현재 스냅샷에 처치 사건이 있는 적의 마지막 렌더 자세를 유지하고 번쩍임→밀림→쓰러짐 재생 |
| 거대 검 | 반지름=Core 사거리(진화 6000)라 화면 밖, 0.18초 동안 계속 흐려짐 | 화면 안 기본 반지름, 화면 안 처치 위치를 모두 감싸는 최소 반지름까지 확장, 0.15초 유지 |
| 영웅 피격 | 0.2초 전신 붉은 tint가 연속 피격으로 재시작 | 흰 번쩍임 2프레임(재발동 0.25초)+그림만 0.25 몸 너비 밀림 |
| 뿔나팔 | 무리당 1~2명, 원래 크기 | 런타임 장비/정본 최대 레벨 배율로 인원·크기(상한 7명·1.5배 → 2차 5명·1.3배, 영웅과 겹침 0), 진화 연출은 런타임 진화만 |

세부 수치는 [피드백 GDD #266 절](../design/gdd/06-feedback.md#266-무기-손맛-수정-구현값-사용자-영상-승인-전)에 있다.

## 실제 실행 증거

캡처 앱: `f093839` ARM64 Mono Release, `UNITY_WAVE_BENCHMARK=1 UNITY_CONTENT_PROFILE=wave-1a`. 입력은 M1-4와 같은 24개 사례 `m1-258-combat-candidate1/net8`(replay·sidecar SHA는 각 `production-plan.json`에 기록)과 같은 오프라인 60fps·실제 소리 경로다. `tools/m1-production-review.mjs validate`가 24개 모두 통과했다.

| 장면 | 화면 안 처치 / 궤적 밖 | 부채꼴 전체가 화면 안인 타격 | 동시 처치 연출 최대 / 초과 |
|---|---|---|---|
| 철날 검 Lv1 | 18 / 0 | 11/11 | 3 / 0 |
| 철날 검 최대 | 104 / 0 | 7/13 | 25 / 0 |
| 철날 검 진화 | 148 / 0 | 3/11 | 33 / 0 |

처치가 화면 가장자리까지 퍼진 타격은 포함 관계를 우선하므로 부채꼴 일부가 화면을 넘는다. 휘두르는 검은 항상 화면 안에서 끝난다.

뿔나팔 검토 로그(`m1-combat-review.json` `musterPresentation`): Lv1 `GearRatio` r=1.88·3명·1.09배, 최대 r=8·5명·1.3배, 진화 r=32·7명·1.5배. 사용자 검수(영웅 가림·원 무늬) 후 `a8aa9f2`: 상한 5명·1.3배, 영웅 그림 상자와 겹침 0·중심에서 최소 1.2 몸 너비, 얇은 원 테두리; 재촬영 3/5/5명·1.05/1.18/1.3배. 검토 진화 단계는 런타임 진화가 아니므로 진화 전용 연출은 켜지지 않는다.

정상 플레이 경로: PlayMode `NormalPlayRallyKitchenEvolutionIsTheOnlyPathToTheEvolutionLook`(first-playable, seed 30002, 무적·레벨 부여 없음)에서 6630틱 무렵 `core:rally_kitchen` 활성 시에만 `RuntimeEvolution`·상한 인원(2차 수정 후 5명)이 되고 기록은 1회다. 같은 seed의 Mac 자동 플레이(`d95c282`, `a8aa9f2`)도 7802·8324틱에 같은 경로를 기록했다. 그러나 이 PR 스택의 first-playable Mac 앱은 `HeroVisual`이 매 프레임 `Missing art role: hero.preview-b.idle` 예외를 던져 월드를 그리지 못한다(#255 2bf5295부터, main에는 없음). 따라서 실시간 캡처 1회차(24.8fps)·2회차(59.68fps, 누락 20슬롯) 모두 월드가 빈 화면이라 쓰지 않는다. 원인은 [#268](https://github.com/hyunlord/bs-mobile/issues/268)(스택 병합 전 필수)에 기록했고, 34–50ms 관찰의 정정도 그 이슈에만 남겼다. `cd8647c`의 임시 대체(역할이 없으면 기존 영웅 그림, 경고 1회) 뒤 3회차 캡처는 예외 0건으로 월드가 그려지며 진화 틱 8325를 담았다. 실측 18.63fps·60Hz 슬롯 4,083개 누락으로 **60fps 미달 실시간 표본**이며, 그 표기를 넣어 제출했다.

## 8종 결합 장면 비용 (캡처 끔)

`m1-256-combined-v3` 결합 재생(SHA `8ae45858…`), 창 900–1500, 전경 프레임만, 같은 기계·같은 날 각 2회.

| 앱 | p95 (ms) | 최대 (ms) | >25ms | 프레임 |
|---|---:|---:|---:|---:|
| 수정 전 `1db05f0` 1회 | 33.3632 | 50.2901 | 38.308% | 851 |
| 수정 전 `1db05f0` 2회 | 33.0361 | 50.8632 | 12.147% | 1,062 |
| 수정 후 `f093839` 1회 | 32.8205 | 50.7577 | 6.893% | 1,117 |
| 수정 후 `f093839` 2회 | 32.5009 | 50.8390 | 7.175% | 1,115 |

수정 후 프레임 비용 증가는 측정되지 않았다. >25ms 비율은 같은 앱에서도 크게 흔들려 개선으로 해석하지 않는다. 결합 성능 관문(p95 33ms 실패)은 이번 범위가 아니며 여전히 실패다. 결합 장면 동시 처치 연출 최대 26개(상한 64)·초과 0.

## 무기 연출 2차 시범: 번개·뿔나팔 (사용자 영상 승인 전)

사용자 판정 "번개 안 보임, 부하는 서 있는 스티커"에 대한 View 전용 시범이다. Core·재생 해시는 바꾸지 않았고 6개 사례 모두 `validate`를 통과했다. 캡처 앱 `cfdebb2`(같은 빌드 조건·입력). 세부 수치는 [피드백 GDD 2차 시범 절](../design/gdd/06-feedback.md#무기-연출-2차-시범-번개뿔나팔-사용자-영상-승인-전).

원인:

| 문제 | 원인 | 수정 |
|---|---|---|
| 번개 안 보임 | 1~2px 직선 연결선. 진화에서도 연결선만 늘었다. 가장 가까운 희생자가 대개 영웅 아래에 있어, 하늘 기둥을 더하자 그 기둥이 영웅 그림 뒤에 숨었다(P5로 영웅이 위) | 지그재그 기둥(노랑흰 심+보라 번짐, 더하기 혼합), 예고→타격→사라짐, 맞은 적만 정지·흔들림. 기둥은 영웅에 가리지 않고 화면 가장자리에서 떨어진 희생자에, 가려진 단일 희생자는 영웅 반대쪽에서 비스듬히 |
| 플레이어 빌드에서 번개 0 | 새 더하기 셰이더의 instancing 변형이 머티리얼 참조가 없어 빌드에서 제거됨(에디터에서는 보임) | `WorldSpriteAdditiveMaterial.mat`(instancing 켬) |
| 부하 = 스티커 | 소집 무리 위치에 그림만 고정 | 등장·추적·공격·복귀·해산 상태와 달리기·찌르기 동작, Core 타격 프레임에 찌르기 |

자동 검사(`tools/m1-weapon-pilot-check.mjs`, 사전 선별일 뿐 판정 아님). 렌더러가 표시한 프레임 로그(`m1-lightning-strikes.csv`, `m1-minion-thrusts.csv`)와 JPEG 프레임 화소로 잰다. 폭은 기둥 길이의 25~85% 구간(대상·하얗게 번쩍이는 영웅과 겹치는 아래쪽 제외)에서 보라 번짐에 둘러싸인 흰 심의 행별 최대 교차를 기울기 보정해 중앙값으로 낸다.

| 장면 | 대비(≥40) | 심 / 번짐 px (≥4 / ≥16) | 예고 프레임 (2–4) | 사라짐 프레임 (≤11) | 반응 지연=표시 | 영웅에 가린 기둥 |
|---|---|---|---|---|---|---|
| 번개 Lv1 (10회) | 44.6–54.0 | 6.8–7.0 / 21.7–23.6 | 2–3 | 5–9 | 예 | 10/10 (연결 1개, 비스듬히 대체) |
| 번개 최대 (12회) | 49.7–73.4 | 7.0–9.2 / 21.7–33.2, **1회 3.7 / 16.9** | 2–3 | 5–9 | 예 | 2/12 |
| 번개 진화 (5회, 기둥 26) | 44.8–50.7 | 7.7–13.9 / 29.4–50.3 | 2–3 | 8–9 | 예 | 1/26 |

번개 최대의 3.7px 1회(프레임 413)는 연결 8개가 영웅 바로 옆에서 화면 오른쪽 끝까지 이어져, 영웅에 가리지 않으면서 가장자리에서 떨어진 희생자가 없었다. 규칙대로 가장자리 희생자에 떨어져 기둥이 화면 끝에 잘렸다. 측정 방식을 바꿔 맞추지 않고 그대로 실패로 남긴다.

| 장면 | Core 무리 타격 / 같은 프레임 찌르기 | 정지 비율 (<20%) | 깃발 기수 프레임 / 돌격 밀어냄 |
|---|---|---|---|
| 뿔나팔 Lv1 | 40 / 40 | 15.1% | 0 / 0 |
| 뿔나팔 최대 | 61 / 61 | 2.6% | 0 / 0 |
| 뿔나팔 진화 | 99 / 99 | 0.45% | 2340 / 92 |

진화 전용 요소는 Lv1·최대에서 꺼지고 진화에서만 켜졌다(위 기수·폭풍 수치, EditMode 데이터 테스트). 영웅 겹침 0은 PlayMode `MusterFormationNeverOverlapsTheHero`가 검사한다. 기둥이 영웅을 피하는지는 PlayMode `LightningPillarAvoidsAVictimUnderTheHero`가 검사한다.

검토에서 본 남은 위험(사용자 판정 대상): 폭풍 타격 2프레임 동안 화면 전체가 밝아짐, 뿔나팔 병사가 모이면 옅은 파랑 덩어리로 보임.

### 사용자 검수 반영 (번개 섬광·병사 외형)

- 번개: 화면 전체 섬광은 폭풍(진화) 타격에서만, 알파 0.065(이전 0.13의 절반). Lv1·최대는 대상 주변 섬광만. 표시 로그 `screenFlash`로 자동 검사(Lv1·최대 0, 진화 0.065). 캡처 앱 `3f69410`.
- 뿔나팔: 옅은 반투명 덩어리의 원인은 흰색 섞음(0.3)과 어두운 곱셈 색이었다. 원화 갑옷을 알파 1로 약하게 차갑게만(채도만) 그리고 어두운 외곽선 1~2px를 더했다. 해산은 투명해지지 않고 작아지며 먼지. 찌르기 창은 축소된 대각선 아이콘(실제 화면 약 1px)을 버리고 외곽선 있는 나무 자루(최소 3px)와 강철 창날을 직접 그린다. 준비 때 당기고 찌르기 2프레임에 병사 키 1.35까지 뻗는다. 창끝은 P5 순서(적 > 자기 공격 > 아군)상 찔린 적 뒤로 지나간다. 깃발은 불투명·외곽선. 캡처 앱 `38731a0`.
- 행동 검사는 이전과 같다(같은 프레임 찌르기 40/40·61/61·99/99, 정지 비율 15.1/2.6/0.45%). 결합 장면 비용은 이번에 다시 재지 않았다(병사당 그리기 2~6개 추가).

### 결합 장면 비용 (캡처 끔, 3회씩 번갈아)

같은 결합 재생(SHA `8ae45858…`)·창 900–1500·전경 프레임만, 2026-10-15 같은 기계. 수정 전과 중간 빌드는 1회씩 번갈아 3회, 최종 `cfdebb2`는 그 뒤 연속 3회다. 중간→최종 차이는 번개 기둥 대상 선택뿐이다.

| 앱 | p95 (ms) | 최대 (ms) | >25ms |
|---|---|---|---|
| 수정 전 `a8aa9f2` | 33.36 / 33.25 / 33.32 | 55.66 / 55.03 / 54.13 | 35.9% / 20.4% / 13.6% |
| 중간 `78f7527` | 33.34 / 33.09 / 33.32 | 56.22 / 50.20 / 53.81 | 33.1% / 8.0% / 24.2% |
| 수정 후 `cfdebb2` | 33.34 / 32.95 / 33.24 | 55.70 / 52.27 / 52.62 | 27.0% / 12.8% / 13.9% |

같은 앱 안에서도 >25ms가 13~36%로 흔들려 전후 차이는 이 잡음 안이다. 비용 증가는 측정되지 않았다. 이전 절(같은 기계, 다른 날)의 최대 약 50ms보다 이날 두 앱 모두 54~56ms로 높다. 결합 성능 관문은 여전히 실패이며 이번 범위가 아니다.

## 재생성

```sh
UNITY_WAVE_BENCHMARK=1 UNITY_CONTENT_PROFILE=wave-1a UNITY_MAC_OUTPUT=<새 폴더> bash tools/build-mac.sh
node tools/m1-production-review.mjs combat-plans <새 폴더> <24개 case 폴더>
node tools/m1-production-review.mjs run <plan> "<앱>"
node tools/m1-production-review.mjs weapons <plan> <새 출력>
node tools/m1-knight-measure.mjs run <결합 plan> "<앱>"   # 계획 형식은 m1-256 retry2와 같음
node tools/m1-weapon-pilot-check.mjs <번개·뿔나팔 캡처 폴더...>   # 2차 시범 자동 사전 선별
```

영웅 피격 비교는 같은 `benchmarks/m1-254/dense-approach-candidate2.ssreplay`를 `--knight-review --camera-scale 1.4 --camera-scale-window damage --knight-damage-replay --offline-replay-capture --offline-replay-audio`로 두 앱에서 촬영했다. 두 실행의 실제 영주 피해 기록 160건은 같다.
