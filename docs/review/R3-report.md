# R3 — 선택 A안의 최소 공간 잔재 고리

[이슈 #62](https://github.com/hyunlord/bs-mobile/issues/62), [PR #63](https://github.com/hyunlord/bs-mobile/pull/63), [ADR 0015](../adr/0015-local-remains-loop.md), [검증 런북](../runbooks/verify-remains-loop.md). 실행 소스는 `d9653353f0c17fcea756910d9b1db28d400680b6`이며 [CI 37725210436](https://github.com/hyunlord/bs-mobile/actions/runs/37725210436) PASS를 연결한다. 최종 보고·보관 커밋과 포장 후 CI·ZIP 식별자는 [PR #63](https://github.com/hyunlord/bs-mobile/pull/63) 및 별도 전달 영수증에서 확인한다. 보고서 자신의 최종 커밋·ZIP 해시를 본문에 재귀적으로 삽입하지 않는다.

## 구현한 범위와 보존

기본 영웅 `core:frontier_knight`, 영지 `core:sprout_march`를 데이터로 선택한다. Core에는 이 이름으로 분기하는 규칙을 넣지 않는다. 농지가 없을 때도 처치 위치의 잔재를 남기며, 다음 simulation tick 이후 반경 내 농지가 한 번 흡수한다. 만료를 먼저 처리하고 거리 동률은 농지 ID로 정한다. 기존 entity ID와 RNG를 소비하지 않는 별도 순번을 사용한다.

기본 설정은 보관 1,000개·수명 900틱·반경 600 world-unit이다. 상한에 닿으면 새 잔재를 거부하고 기존 잔재를 보존한다. 기존 비옥도 소비·성장 보너스를 실제 적용한 양만 기록한다. 비옥도를 사용한 작물 주기의 수확 표식은 수확·파괴에서 정리한다. 이는 **공간에 남은 잔재의 농지 흡수**이며 영웅이 잔재를 주워 운반하는 고유 능력이 아니다.

역사 데이터는 `bcaa00f763ec6950707635569befb558e8de1731`에서 보존한 243파일·376,167bytes가 원본과 바이트 일치한다. 기존 S2/S4/S4b 회귀는 명시적 fixture를 사용하며 과거 golden을 활성 ID로 다시 받지 않는다. 선택적 잔재 설정·상태·결과가 없는 과거 직렬화에는 새 null 필드를 넣지 않는다.

tuning 3파일과 프로필 4파일은 원본/활성 해시가 다르지만 승인된 기본 ID 치환만 정규화한 비교에서 **7/7 의미 일치**다. 원시 해시가 같다는 뜻이 아니다. 이 비교는 잔재 기능의 동작이 과거와 같다는 주장도 아니며, R2의 위협·XP 등 동결 숫자를 다시 보정하지 않았다는 증거다. 활성 JSON 202파일에서 정확히 일치하는 ID 문자열 값 227곳을 치환했다. 이는 레코드 개수가 아니다. 정본은 219레코드이고 검증기는 테스트 11레코드를 포함해 230레코드를 검사한다. 기본 영웅·영지 각 하나를 유지하고 더미 `test:scout`·`test:moor`는 별도 테스트 데이터다.

**프로필 경계:** 동결 밸런스 재실행은 `s4b-02`와 그 tuning/catalog를 사용한다. `s2-baseline`·`s4-stage-one`의 수동 기술 실행은 기존 tuning을 사용하므로 아래 기본 실행의 레벨 80을 S4b XP 목표 판정에 섞지 않는다. Unity 인계에서도 루트 `tuning.json`이나 CLI 기본값이 자동으로 보정 프로필을 뜻한다고 가정하지 않는다.

## 증거와 후속 인계

[외부 Release](https://github.com/hyunlord/bs-mobile/releases/tag/phase0-r3-sprout-march-20261008), [파일 매니페스트](../evidence/R3/R3-source-manifest.csv), [자산 매니페스트](../evidence/R3/R3-assets-sha256.csv)를 통해 원자료와 요약을 연결한다.

Release 업로드 후 새 경로로 다운로드하고 빈 경로에 추출해 **2,057파일·3,903,061,790bytes의 정확한 집합·전체 SHA-256·크기 일치**를 확인했다(추가 파일 0). 압축 자산은 284,540,585bytes, SHA-256 `cbe3637b394f3c2035c5638587442a171f46e62d4401b927a967c067e3d9b1ea`다. 자산 매니페스트의 압축 파일·원자료 매니페스트 두 항목도 확인했다. 매니페스트 자신의 해시는 자기 목록에 포함하지 않는다. 운영상 덮어쓰지 않으며 플랫폼 WORM 보장을 주장하지 않는다.

최종 CI·병합 커밋·ZIP 경로/파일 수/크기/SHA-256·CRC·추출 검증은 별도 전달 영수증에 기록한다. 원본 S4 및 [R2 FAIL(c)](R2-report.md)을 덮어쓰지 않는다. 후속 진단 [#61](https://github.com/hyunlord/bs-mobile/issues/61), 공동 1위 해석 [#57](https://github.com/hyunlord/bs-mobile/issues/57), Unity 계획 [#65](https://github.com/hyunlord/bs-mobile/issues/65)는 별개다. 사람형의 생존 기여·이동과 수확의 상호작용은 추가 통제 실험의 가설이며 현재 관측만으로 원인을 확정하지 않는다. UI·기기 성능·사람의 재미·광고/결제·리텐션은 이번 헤드리스 구현의 검증 범위 밖이다.
