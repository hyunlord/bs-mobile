# ADR0040: 설계 카탈로그와 런타임 지도의 분리

- 상태: 승인 (#141 사용자 요청의 설계와 런타임 분리)
- 날짜: 2026-10-10
- 연결 이슈: [#141](https://github.com/hyunlord/bs-mobile/issues/141)
- 관련 결정: [ADR0037](0037-lattice-map.md), [ADR0039](0039-versioned-design-catalog.md)

## 맥락

D3 카탈로그는 런타임과 같은 ID를 사용할 수 있지만 설계 카탈로그다. 승인된 설계도 런타임 구현 증거는 아니다. 두 소스를 합산하거나 설계 관계를 런타임 구현 증거로 해석하면 지도의 의미가 달라진다. ADR0037의 초기 지도에 독립 설계 층과 비교 기능을 추가한다.

## 결정

`.lattice/lens.json`이 `data/system-design-v1.json`을 designed-v1 층으로 읽고 런타임·이전 후보 층과 구분한다. 그래프 ID에는 카탈로그 revision을 붙이고 원래 ID를 별도로 보존한다. designed-v1은 안정된 층 이름이며 designed-v1.1 같은 실제 revision과 구분한다. 대응 간선은 유효한 designRef를 우선하며, 없으면 같은 종류와 ID를 사용한다. 대응 자체는 구현·발동·승인 증거가 아니다.

카탈로그의 content·systems·implementationWaves·influenceMatrix를 스키마 구조로 읽는다. 영향 행렬은 행에서 열로 향한다. 도메인 간선·발견 조건은 bs-mobile 렌즈가 소유하고 Lattice 엔진에는 범용 표현과 보기를 둔다. 설계 발견은 warning이며 사용자 승인 전에는 gate로 바꾸지 않는다.

Pages 워크플로는 검증된 Lattice main 커밋eb2aba6e20521b634e5a0540d09465ee43ff625d를 고정한다. 역사 기준de2a571과 현재 소스를 동일한 현재 렌즈로 다시 계산해 현재 렌즈 투영임을 표시한다. 같은 층·종류·원본 ID를 대응시켜 노드·발견·간선·facet의 변화와 층별 개수를 비교하며 원본 JSON을 변경하지 않는다.

## 결과와 비용

홈·목록·상세·영향 행렬에서 설계를 따로 검토할 수 있다. 이후 카탈로그 변경은 Pages 트리거를 통해 다시 게시된다. 기준 스냅샷을 재계산하므로 전체 Git 이력 checkout이 필요하고 빌드 시간이 늘어난다. 역사 재현값은 기준 커밋에만 검증하며 현재 콘텐츠 수량을 고정하지 않는다.

## 거절한 대안

- 같은 ID를 하나의 노드로 병합: 설계 제안과 런타임 증거를 혼동한다.
- 엔진에 게임 전용 분기 추가: 범용 도구와 도메인 규칙의 경계를 깨뜨린다.
- 현재 발견을 즉시 CI gate로 사용: 사용자 승인 전 warning-only 요청에 어긋난다.

## 검증

실제 기준 그래프에서 요청값6/15/11/7/12/0, 콘텐츠151개의 웨이브 소속, 시스템13개의 방향 영향 간선41개를 대조했다. 브라우저375/768/1280에서 네 화면을 확인했다. 도구 PR16의 Node20/22/24 CI가 통과했다. 후속 revision 대응 PR17도 같은 CI와 브라우저 이력 검사를 통과했다. 소비자 PR CI와 배포 상태는 PR149의 실행 결과를 정본으로 둔다. 별도로 PR151의 4a8de978baac0d2bbc2a31b8fd31adc33971a909 데이터를 읽어 v1.1 재현값0/0/2/2/0/3과 bespoke44건을 확인했다. 이는 PR head 데이터 검사이며 병합·배포 검증과 구분한다.

## 후속 적용: 검증된 L2 뷰어 갱신 (#158)

2026-10-10의 [#158](https://github.com/hyunlord/bs-mobile/issues/158)은 위 층 분리 결정을 유지하면서 Pages의 도구 고정을 `c4920824b2983147030f090f5127901b02fda051`로 갱신한다. 앞서 기록한 `eb2aba6`은 최초 게시의 역사 증거다. 새 도구도 범용 뷰어이고, 게임 규칙은 소비자 렌즈만 소유한다. 홈·탐색·목록·보기·변화·상세에서 현재와 역사 스냅샷의 출처를 확인할 수 있다.

범용 표현식은 누락값을 일반 문자열과 같게 취급하지 않는다. 따라서 `itemScope`가 없던 과거 물품을 배제하지 않도록 렌즈는 `not(eq(itemScope, "universal"))`로 명시적인 공용 물품만 제외한다. 이 조건은 기존 장비별 연결 의미를 보존하며 카탈로그 원본을 고치지 않는다. 누락값 비교를 도구 전체에서 완화하거나 역사 재현 검증기를 낮추는 대안은 다른 렌즈의 의미와 과거 증거를 바꾸므로 채택하지 않는다.

버전 고정은 Node20·22·24 CI와 실제 저장소 세 곳의 브라우저 검증을 통과한 커밋으로 제한한다. 워크플로는 동일한 현재 렌즈로 두 시점을 읽고 현재 렌즈 투영임을 표시하며, 기준6/15/11/7/12/0과 현재0/0/2/2/0/3을 기존 검증기로 확인한다. 발견은 warning이고 새 gate는 없다. 전체 Git 이력과 두 번의 그래프 계산 비용은 유지된다. 적용은 PR159의 필수 CI 후 이루어지며 배포·공개 URL 확인은 해당 실행 기록으로 별도 증명한다.

## 후속 적용: 재사용 CI와 PR 차이 요약 (#160)

[#160](https://github.com/hyunlord/bs-mobile/issues/160)은 같은 층 분리와 warning-only 정책을 유지하며 검증된 Lattice 재사용 워크플로를 도입한다. 호출 워크플로와 도구 checkout은 Node20·22·24 CI가 통과한 같은 불변 커밋 `b6e65efe6eed4771dcd220897b7ecfe06829c8cc`(Lattice `v0.1.0-l4`)으로 고정한다. PR은 실제 head와 base를 비교하고, 기본 브랜치에서는 Pages를 게시한다. 데이터뿐 아니라 코드와 렌즈 변경도 갱신 대상으로 삼는다.

소스 빌드는 읽기 전용 토큰으로 수행한다. `.lattice/verify-ci.mjs`가 기존 검증기로 현재 그래프와 de2a571의 현재 렌즈 투영을 확인하고, 내보낸 그래프 해시까지 대조한다. 이 검증이 실패하면 배포하지 않는다. 관문이 있는 렌즈의 실패도 지도와 요약 아티팩트를 남긴 뒤 CI 실패로 처리하지만, 이 저장소의 설계 발견을 새 관문으로 승격하지 않는다.

댓글과 Pages 작업은 별도 실행 환경에서 고정한 도구만 checkout한다. PR 코드를 실행하지 않으며, 댓글은 실행·PR·커밋을 대조한 제한된 JSON 요약만 읽어 봇 소유의 같은 댓글을 갱신한다. 포크 PR은 읽기 전용 토큰으로 지도 아티팩트만 제공하며 권한 우회를 쓰지 않는다. Pages가 설정되지 않았거나 명시적으로 비활성화된 소비자는 아티팩트를 내려받아 로컬 HTTP로 본다. 이 대안을 공개 URL 게시 성공으로 보고하지 않는다.

현재와 역사 검증 비용은 유지된다. 소비자 전용 검증을 범용 도구 안으로 옮기거나 권한 있는 작업에서 PR 스크립트를 실행하는 대안은 도메인 경계와 권한 분리를 깨뜨려 채택하지 않는다. 실제 PR·CI·게시 기록은 #160의 연결 PR에서 확인한다.

## 후속 적용: YAML 렌즈와 원본 발견 검증 (#162)

[#162](https://github.com/hyunlord/bs-mobile/issues/162)은 기본 렌즈를 `.lattice/lens.yaml` 하나로 옮기고 원본 시제품의 발견 8개를 실행 층에 반영한다. 앞선 JSON 경로는 당시의 기록이다. 실행·후보·설계 층, 설계 대응과 warning-only 정책은 유지한다. 원본 데이터와 프로필 우선 적용 결과는 별도로 표시하며, 코드 연결은 실제 C# 처리기의 정적 존재만 판정한다. 정적 연결을 게임 실행 증거로 확대하지 않는다.

비용·보상 값은 기존 범용 표 보기로 표현하고 게임 전용 규칙은 렌즈에만 둔다. 검증기는 현재 소스에서 독립적으로 계산한 값과 그래프를 비교한다. 고정 시제품의 216개 분류와 역사 카탈로그 재현값은 해당 고정 커밋을 검증할 때만 적용하고 현재 콘텐츠 수량을 고정하지 않는다. 현재 소스 일치 검증은 발견을 차단 관문으로 승격하는 것과 구분한다.

JSON과 YAML 기본 렌즈를 함께 남기는 대안은 어떤 렌즈를 읽는지 모호해지므로 거절한다. 원본 시제품 정답을 렌즈 입력으로 사용하는 대안도 실제 소스에서 발견을 재현하는 목적에 어긋나므로 거절한다. CI의 역사 비교와 출처 검증 비용은 유지하며, 배포 도구는 워크플로에 같은 불변 커밋으로 고정한다. 도구 성능, 소비자 CI와 공개 화면 확인은 #162의 연결 PR 및 Lattice 검증 기록에서 각각 확인한다.

호출 워크플로와 도구는 Lattice PR47의 Node20·22·24 CI가 통과한 main `b9da44c0f22e0133fff675a9dd4c916b6b716fa9`로 함께 고정한다. 동일 설치 패키지의 C&K·설정 없는 Click 빌드와 브라우저 검증도 통과했다. cold MCP 등 L5 성능의 남은 실패는 Lattice #46에서 유지하며, 이 지도 갱신을 전체 L5 통과로 표현하지 않는다.

병합 전 출처 검토에서 앞선 facet의 읽기 근거가 다음 facet에도 누적되는 범용 오류를 확인했다. Lattice PR48은 값·조건·파생 근거를 보존하며 각 facet의 출처를 분리한다. 간선과 발견 규칙의 동일한 누적 오류도 PR49에서 수정했다. 참조한 파생 값과 코드 연결 근거는 유지하며 규칙마다 출처를 수집한다. 최종 고정은 두 수정의 Node20·22·24 CI가 통과한 main `d8a6890084a338e3504900b87a1b60c5090a9652`다. 게임 의미를 가진 설계 의도 facet은 유지한다. 소비자 렌즈에서는 설계 발견만 사용하는 웨이브 순서 계산과 물품 연결 수만 designed-v1에 제한하여 런타임의 빈 값을 제거한다. 원본 데이터나 정책 관문은 변경하지 않는다.


## 후속 적용: 카탈로그 대응의 직접 판정과 범용 도구 갱신 (#173)

[#173](https://github.com/hyunlord/bs-mobile/issues/173)은 기존 층 분리·designRef 우선·warning-only 결정을 유지한다. 같은 종류와 ID의 설계 항목 존재 여부는 전체 그래프의 노드를 다시 읽는 대신 `vars.catalog.content`의 `kind`와 `id`를 끝까지 필터링해 판정한다. 대응 대상 선택과 유효한 designRef의 우선순위는 바꾸지 않는다. 현재와 역사 카탈로그의 10종 스키마가 ID를 필수로 요구하고, 기존 콘텐츠 검사가 중복 ID를 거부하므로 스키마에 맞는 입력의 대응 의미는 같다. 종류별 개수를 고정하거나 게임 규칙을 Lattice에 넣지 않는다.

전체 그래프를 읽으면서 다른 시스템의 출처까지 대응 간선에 붙이는 비용을 줄이고, 실제로 읽은 카탈로그 종류·ID의 근거는 남긴다. 현재·de2a571 각각의 대응 간선126개를 독립 대조해 필요한 입력 근거 누락이 없음을 확인했다. 노드·간선·발견·보기의 출처 외 값과 노드 contentHash는 같고, facet 내부의 렌즈 진단 출처20개는 편집으로 바뀐 줄 번호와 렌즈 해시만 다르다. 도메인 데이터 내부의 `sources` 값은 비교에서 제외하지 않았다. 역사 재현값6/15/11/7/12/0, 현재0/0/2/2/0/3, 실행 층의 선택77·고유 참조20을 기존 검증기로 확인했다. 이 수량은 검증한 소스의 결과이며 새 고정 콘텐츠 계약이 아니다.

워크플로 호출과 도구 checkout은 같은 불변 Lattice main 커밋으로 함께 갱신한다. 범용 도구는 규칙별 출처 수집, 동일 작업 안의 glob 재사용, 검증·직렬화의 중복 작업과 오류가 없을 때의 경로 문자열 생성을 줄인다. 오류 검사·출처 의미·전체 입력의 변경 확인은 유지한다. Node20·22·24 CI와 동일 설치 패키지의 세 저장소 브라우저 검증을 버전 고정의 근거로 쓰며, 소비자 PR CI와 공개 Pages 확인은 별도 실행 기록으로 남긴다.

전체 그래프 스캔을 유지하는 대안은 관계 없는 근거와 비용을 계속 누적한다. 출처를 일괄 삭제하거나 스키마 검사를 완화하는 대안은 추적 가능성을 깨뜨려 거절한다. 워크플로 변경의 ADR 정책을 우회하는 대안도 채택하지 않는다. 현재 렌즈로 역사 스냅샷을 다시 계산하는 비용은 유지한다. 설치 패키지의 첫 MCP 요청1초 관문 등 남은 L5 성능 실패는 Lattice #46에 그대로 기록하며, 지도 갱신이나 빌드·브라우저 통과를 전체 L5 완료로 표현하지 않는다.

## 후속 적용: 사람이 읽는 지도 (#176)
