# ADR0054: 선택 보상을 재생 명령과 원자적 계정 지급으로 나눈다

- 상태: #227 구현 결정, Unity 통합·화면·네이티브 끊김 관문은 검증 전
- 날짜: 2026-10-11
- 관련: [#227](https://github.com/hyunlord/bs-mobile/issues/227), [#224](https://github.com/hyunlord/bs-mobile/issues/224), [#126](https://github.com/hyunlord/bs-mobile/issues/126), [ADR0053](0053-explicit-meta-claims-and-wave-accounting.md), [화면 흐름 v0](../design/screen-flow-v0.md)
- 번호: 준비 시 origin/main `62a7462`에는0052까지 있고, 선행 #226이0053을 사용한다.0054는 후보 번호이며 공개·병합 직전 main에서 충돌을 다시 확인한다.

## 맥락

사용자는 힘을 판매하지 않는 가벼운 무료형 BM의 자리와 선택 흐름을 승인했다. 광고·결제·분석 SDK, 실제 구매, 미정 수치 확정은 승인 범위가 아니다. 보상을 화면에서 직접 지급하면 중복 수령·저장 실패와 결정론 위반이 생기므로, 실행 중 보상과 계정 보상의 경계를 구분한다.

## 결정

### 실행 보상은 opt-in 재생 v5

`InteractiveOptions.HostRewards`가 있는 판만 재생 v5를 쓴다. `HostGrantRerollV1`은 카드 선택 중 기존 다시 뽑기 잔여0일 때1회를 추가하며 판당2회까지다. `HostReviveV1`은 명시적인 `HostReviveRules`가 있는 종료 상태에 한 번만 적용된다. 회복 체력·무적 시간·보존 상태는 재생 헤더의 규칙이며 외부 광고 콜백이나 시스템 시각으로 결정하지 않는다. 부활 선택을 처리하기 전에 결산을 확정하지 않는다. 부활 여부는 실행 기록·결산에서 구분하고 부활 후 클리어도 인정한다.

옵션이 없는 기존 판은 기존 v1–v4 형식과 상태 해시 경로를 보존한다. 새 명령을 구형 헤더에 끼워 넣지 않는다. 부활 규칙은 #224 미정이다. 명시적 테스트 fixture로 명령을 검증할 수 있지만 그 값을 production 기본값으로 배포하지 않으며, 실제 부활 제안은 설정이 없으면 숨긴다.

### 계정 보상은 schema5의 원자적 영수증

schema5는 `RewardReceipts`와 마지막 판의 `ResultRewardBasis`를 저장한다. 영수증은 완료 ID·종류·원본 sequence로 식별한다. 같은 완료 ID를 다시 보내거나 새 ID로 같은 판/방치 claim을 다시 요청해도 추가 지급하지 않는다. 마지막 판의 기준액은 `SettleRun`에서 실제로 지갑에 들어간 자재이며 요청한 총액·넘친 자재·가신 조각이 아니다.

`ClaimIdleWithBonus`는 기존 방치 claim 제거·기본 자재 지급·추가 자재 지급·영수증을 한 상태로 만든 뒤 `MetaProgression.Publish`로 한 번 저장한다. `GrantResultBonus`는 저장된 실제 결산 기준액만 사용한다. 두 API 모두 명시적 `MetaBonusPolicy`의 추가 배율과 자재별 상한을 요구하고 기존 지갑 상한을 넘지 않는다. 정상 `Claim`의 동작은 유지한다.

v1–v4 저장의 지갑·기존 미수령 내역은 보존하고 과거 보상 영수증이나 추가 보상을 만들어 내지 않는다. 저장 실패 전에는 공개 상태가 바뀌지 않는다. 지급 저장 뒤 host 완료 확인이 실패하면 영수증을 확인하여 완료 처리를 재시도한다. 영수증 저장과 host 광고 정책 저장을 하나의 트랜잭션이라고 부르지 않는다. 영수증은 기존 저장 collection 한도4096개로 제한하며 가득 차면 새 지급을 거부한다.

### 광고 정책은 host의 로컬 원장

host는 광고 제공 가능 여부·첫 판·첫날·일별 횟수·판별 횟수·연속 제안 차단·권한을 판단하고, 완료된 의도만 Core 명령 또는 계정 지급 API로 전달한다. 원장은 안정적인 완료 ID와 지급 확인 여부를 저장한다. 실패·취소·제공 불가는 보상과 성공 횟수를 늘리지 않는다. 완료 저장 실패는 지급을 막고 재시도하며, 지급 확인 전에는 다음 광고를 제안하지 않는다.

첫 판과 첫날에는 광고 제거 권한이 있어도 제안을 숨긴다. 날짜는 주입 가능한 로컬 달력 키이며 날짜 역행에는 제안을 숨긴다. 서버 시각·계정 동기화가 구현됐다고 주장하지 않는다. 연속 제안 차단은 임의의 초 수치 대신 새 출정이나 새 레벨 같은 구분 가능한 플레이 사건으로 해제한다. 화면 열기·닫기만으로 해제하지 않는다. 이 동작은 확인하지 못한 canvas Logic의 인용이 아니라 로컬 v0의 명시적 구현 선택이다.

성공 한도는 결산 판당1회, 부활 판당1회, 다시 뽑기 판당2회다. 방치 하루3회는 사용자 지정 **가설**로 남긴다. 한도·문맥·구성·제공 가능 조건이 맞지 않으면 버튼을 숨긴다. 광고 제거 권한이 있는 fixture는 같은 노출 조건을 지킨 뒤 광고 없이 직접 지급하며 `바로 2배` 등으로 표시한다. 실제 구매로 권한을 얻는 경로는 없다.

### 제품에서 여는 것과 닫는 것

- 상점·시즌 패스는 보기 전용이다. 외형·영지 테마·외형/패스용 보석·광고 제거만 표시하고 미정 가격·고정 보상은 `[n]`으로 둔다. 가신·조각·자재·판 능력·뽑기·에너지는 판매하지 않는다.
- Editor/Development에서만 성공/실패 가짜 광고 제공자를 사용한다. Release 제공자는 사용 불가이며 실제 광고 버튼을 숨긴다. SDK·패키지는 추가하지 않는다.
- 방치2배는 사용자 지정 추가1배와 기존 자재별 지갑 상한을 명시적으로 전달한다. 결산 추가 배율·별도 상한은 #126 미정이므로 production 설정을 만들지 않고 제안을 숨긴다.
- 생산 부활 규칙 #224, 가신·장원의 wave 전투 능력 투영, #98 실기,1b 확장은 이 결정으로 승인되지 않는다. `AccountOnlyWave`를 유지한다.

## 대안과 검증 경계

UI의 직접 체력·다시 뽑기·지갑 변경은 재생과 저장 계약 때문에 배제한다. 방치 기본 지급과 보너스를 따로 저장하는 방식은 중간 종료·재시도 위험 때문에 배제한다. SDK 또는 임의 가격·회복 수치로 화면을 채우는 방식도 채택하지 않는다.

Core의 재생·저장·원장 단위 검사는 화면 판독·폰 진동·네이티브 끊김을 증명하지 않는다. 현재 source 검증과 남은 Unity·화면·네이티브 관문은 [#227 검토 기록](../review/portrait-bm-227.md)에서 분리한다. #223의 기존 긴 프레임 실패를 이 ADR로 해소했다고 기록하지 않는다.
