# ADR0023 — 생산 데이터 정본과 역사 실험의 경계

상태: 채택 — 사용자 U1 요청의 가역적 구현 선택
날짜: 2026-10-08
연결: [#84](https://github.com/hyunlord/bs-mobile/issues/84), [1단계 A](../design/04_ASTRA_GOAL_bs-mobile_phase1a.md)
관련: [ADR0022](0022-weapon-level-tables-and-facing-sectors.md)의 무기 규칙은 유지하고 저작 데이터 위치·계약만 대체한다.

## 맥락

승인된 무기 후보는 `activation`과 별도 성장표의 레벨1에 같은 수치를 가지고 있었다. 루트 tuning은 옛 S2 설정이고 실제 승인 후보는 실험 파일의 튜닝·적 덮어쓰기·비선형 경험치·런타임 설정을 사용했다. Unity 연결 전에 한 실행 정본을 분명히 해야 한다. 수치 보정이나 과거 결과 재판정은 이번 변경이 아니다.

## 결정

- 실제 게임 진입점은 `data/profiles/production.json` (`core:production`)과 `data/tuning.json`이다. 프로필의 `gameplay`가 승인 후보의 적 덮어쓰기와 경험치·이동·정책 순서 규칙을 명시한다. 내부 `gameplay.experiment`라는 필드명은 기존 Core의 규칙 타입을 재사용하는 이름이며 외부 실험 파일을 읽는 뜻이 아니다. 후보의 `.tuning`만 복사해 나머지 규칙을 잃지 않는다.
- 네 기본 무기는 각 레코드의 `growth`에12개 레벨을 소유한다. `activation`에는 형태·설명·설계 계수만 남기고 피해·범위·간격·넉백은 레벨1에서 읽는다. 스키마와 호스트는 성장표와 숫자 activation의 이중 정의를 거부한다. 검90도·낫180도는 바라보는 방향 부채꼴이라는 설명으로 맞춘다.
- 성장표가 있다는 이유만으로 전투 경로를 바꾸지 않는다. `weaponCombat.contractVersion=2`를 명시한 프로필만 정본 성장 정의를 연결한다. Core에 전달하는 전투 정의의 버전은 기존1을 유지한다. 다른 후보 및 역사 입력의 숫자 activation/외부 성장표 버전1은 계속 읽을 수 있다.
- `tuning-s4b-01/02.json`과 `weapon-growth-79.json`은 `data/experiments/`로 이동한다. 후자의 버전2 문서는 무기 ID만 참조하며 수치 복사본을 소유하지 않는다. 역사 S2 기본 튜닝도 이 폴더에서 명시적으로 참조한다. 실험 튜닝은 당시 전체 설정을 보존하는 자료이지 production을 자동 갱신하는 두 번째 정본이 아니다.
- CLI의 역사 기본 프로필을 몰래 production으로 바꾸지 않는다. 실제 게임·새 플레이 검증은 `--profile production`을 명시하고 Unity의 기본도 production으로 한다. 역사 프로필과 새 프로필의 선택은 호출자가 구분한다.
- 동결 fixture `core/tests/SowSiege.Tests/Fixtures/phase0-r2/**`, 역사 golden·리그 CSV·기존 진단 결과는 바이트 그대로 보존한다. 과거의 정확한 입력 바이트는 해당 결과의 고정 커밋에서 읽는다. 현재 경로 이동·설명 수정 때문에 생기는 content/profile 해시 변경을 gameplay 변경으로 혼동하지 않는다.

## 대안과 비용

성장표와 activation을 둘 다 유지하고 값이 같은지만 검사하는 방법은 두 편집 지점을 남기므로 거절했다. 생산 프로필을 실험02 파일에 계속 연결하는 방법은 실제 게임 정본을 모호하게 하므로 거절했다. 옛 프로필을 새 루트 튜닝으로 자동 전환하는 방법은 역사 동작을 바꾸므로 거절했다.

스키마·로더·프로필·출처 수집 도구가 저작 계약2와 역사 계약1을 구분해야 하는 비용이 있다. 중복 필드·알 수 없는 계약·누락 참조·경로 이탈을 음성 테스트로 보호하며 실제 수치를 Core에 중복 정의하지 않는다.

## 검증

U1 PR에서 스키마/호스트의 이중 정의 거부, 신규/역사 프로필 로딩, 승인 소스 `65fd21a`의 정본 입력과 production의 유효 규칙 및 대표 full-run 동등성을 검사한다. 기존 두 Core 대상의 역사 golden 검증과 전체 `tools/check.sh`를 통과해야 병합한다. 실행 출처 해시는 새 값으로 기록하되 기존 결과를 덮어쓰지 않는다. Unity 구현은 이 PR의 CI 통과·병합 다음 단계다.
