# ADR0089 · C05 측정 중 외부 CPU 무효 기준을 300%로

상태: 승인 — 사용자 결정 2026-11-04. 날짜: 2026-11-04. 연결: [#680](https://github.com/hyunlord/bs-mobile/issues/680).
번호: main과 열린 PR 전체에서 쓰인 최대 번호(0088) +1([ADR 작성](../runbooks/write-adr.md)).

## 맥락

[공유 Mac 런북](../runbooks/shared-mac.md) 6절의 C05 무효 조건은 "측정 중에 다른 프로세스 하나가 CPU 150%를 넘으면 무효"다.
이 기준은 2026-10-20에 정했다. 그때 600% `worldsim_probe`가 양쪽 p95를 두 배로 만든 일이 있었고, 그 뒤로 실제 영향을 재지 않았다.
지난 밤들에는 다른 세션의 언어 서버·빌드(`node` 175~299%, Siri AI 158~241%)가 이 기준에 걸려 무효가 반복됐다. 그 때문에 PR 측정이 며칠씩 밀렸다.

## 측정 (2026-11-03~04 낮)

- **앱:** 모든 실행에 같은 앱 `main-e21c249-r2`를 썼다. C05 benchmark Release, uncapped, 1600×900, 14코어 Mac(성능 10 + 효율 4)이다.
- **부하:** 단일 스레드 바쁜 루프 프로세스(`c05-burn`) 0·1·2·3개다. 각각 CPU 약 100%이고, 평소 진정 확인 뒤 띄우고 실행마다 끝냈다.
- **실행:** 수준마다 유효 3회를 돌렸다. 수준을 번갈아 돌려 시간에 따른 차이를 고르게 나눴다. 유효 조건은 기존 C05와 같다.
- **비교:** `tools/check-wave-regression.mjs --contract benchmarks/wave-c05/contract-v2.json`으로 각 수준을 0과 비교했다. 원자료는 `$MV/c05/exp-load/`, 판정 출력은 `$MV/analysis-exp-load/`에 있다.

| 추가 부하 | 400–599 | 600–799 | 800+ | 판정 |
|---|---|---|---|---|
| ~100% | −4.8% | −0.4% | −0.2% | pass |
| ~200% | −4.4% | +0.1% | +1.7% | pass |
| ~300% | −7.5% | −2.5% | −0.7% | pass |

- 순수 CPU 부하는 300%까지 통합 p95를 실행 간 편차(±8%) 이상으로 바꾸지 않았다.
- 별도 관측: 첫날(11-03) 0·100·200% 수준에서 1회씩, 다른 세션의 실제 부하(평균 합계 약 280%)가 겹쳤다. 그 실행들은 실행별 p95가 6~16% 높았다.
  - 실제 부하는 CPU만이 아니라 GPU·메모리도 쓸 수 있으므로, 순수 CPU 실험으로 설명되지 않는다.
  - 이 실행들은 지금 기준(단일 프로세스 150%)에서도 유효였다. 그래서 기준을 올려도 이 경우는 바뀌지 않는다.

## 결정

- 측정 중 무효 기준을 "다른 프로세스 하나가 CPU **300%**를 넘으면 무효"로 올린다.
- **바뀌지 않는 것:**
  - 시작 조건: 다른 프로세스 CPU 100% 이하가 3분 연속이고, 잠금·Unity Editor·blocker(`worldsim_probe`·`rustc`·`save_load`)가 없어야 한다.
  - 사용자 입력·창 전면화 무효.
  - **GPU를 쓰는 다른 앱**(Godot·Chrome 등)에 대한 기존 규칙: 앞으로 오면 무효이고, CPU는 같은 300% 기준을 따른다. GPU 부하 자체는 재지 않았으므로 완화하지 않는다.
- 적용: 이 ADR 병합 뒤 야간 측정 담당이 `c05-lib.sh`의 측정 중 판정값을 바꾸고 night 로그에 적용 시각을 남긴다.

## 결과·비용

- 다른 세션의 언어 서버·빌드가 150~300%로 도는 동안에도 측정이 유효해진다. 하룻밤에 끝나는 측정이 늘어날 것으로 예상한다.
- **위험:** 다중 스레드 실제 프로세스(컴파일러 등)는 메모리 대역폭·캐시를 함께 써서 순수 CPU 실험보다 영향이 클 수 있다.
  - 완화 1: PR 측정은 기준과 후보를 번갈아 재므로, 부하가 한쪽에만 몰리지 않는다.
  - 완화 2: main C05 상시 단계([ADR0088](0088-standing-main-c05-alarm.md))가 누적 추세를 본다.
- 특정 Mac의 결과다. 기기 성능 판정(#98)이나 다른 기기로 일반화하지 않는다.

## 거절한 대안

- **합계 부하 기준으로 바꾸기:** 측정 앱이 아닌 모든 프로세스의 CPU 합계는 평소에도 50~300%로 흔들린다. 실험에서 합계 약 280%의 실제 부하가 실행별 p95를 높인 사례가 있었지만, 기준과 후보에 고르게 나뉘었다. 근거가 더 필요하다.
- **기준을 없애기:** 2026-10-20의 600% 사례처럼 큰 부하는 결과를 크게 바꾼다.

## 검증

- `node tools/check-docs.mjs`가 통과했다.
- 적용 뒤 효과(무효율 변화)는 아침 보고와 night 로그로 확인한다.
