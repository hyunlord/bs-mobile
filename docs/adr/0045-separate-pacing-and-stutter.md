# ADR 0045: 프레임 상한 대기와 실제 끊김의 판정을 분리

- 상태: 승인 (2026-10-10 사용자 #169 판정 정정)
- 날짜: 2026-10-10
- 연결: [#169](https://github.com/hyunlord/bs-mobile/issues/169), [#186](https://github.com/hyunlord/bs-mobile/issues/186)
- 대체 범위: [ADR0044](0044-fixed-native-wave-benchmark.md)의 Mac 상한60fps 프레임 p95≤16.7ms 합격 기준. 원본 입력·해시·유효성·보존 계약은 유지한다.

## 맥락

기존 프레임 시간은 Update 진입 간 간격으로 렌더와 프레임 상한 대기를 포함한다. 사용자 정정에 따라 상한60fps에서 약17ms p95를16.7ms와 비교한 실패는 측정 기준 오류로 남긴다. 시뮬레이션 최적화와 결정론 검증은 유효하다. 과거369ms·167ms 지연은 별개의 끊김 문제이며, 원인 확정 없이 GC나 셰이더 탓으로 돌리지 않는다.

## 결정

[C05 v2 계약](../../benchmarks/wave-c05/contract-v2.json)을 별도로 추가한다. `contract.json`과 v1 분석기는 역사 판정 재생성용으로 의미를 유지한다.

1. 비용 추세는 targetFrameRate=-1·vSync0의 깨끗한 네이티브 Mac Release에서3회 측정한다. 밀도400–599/600–799/800+별 nearest-rank p95를 기록하며 Mac 절대 합격선은 없다. 이후 웨이브는 같은 C05·Mac 모델·OS·Unity·백엔드·화면·품질·GC 모드·측정 설정의 기준3회와 비교한다. 각 밀도의3회 통합 p95 증가가20%를 초과하면 경고한다. 설정이 달라지면 새 기준이 필요하다.
2. 끊김은 실제 상한60fps·vSync0의 Release3회에서 각 반복·각 밀도마다33ms 초과 프레임 비율≤0.1%,100ms 초과 프레임0개를 요구한다. 정확히33ms와100ms는 각 초과 집계에 포함하지 않는다. 통합 평균으로 실패 반복을 숨기지 않는다.
3. 0명령·따라잡기·느린 프레임을 보존한다. 중단·포커스 이탈·소스 오염·종결 해시 불일치·누락 반복은 통과 자료로 채택하지 않는다. 새 메타데이터에 모드·프로파일러 상태·GC 모드를 기록한다. 과거 자료 재판정은 명시적 historical-capped 옵션에서만 허용하며 미기록 값을 만들어 내지 않는다.
4. Development 프로파일러는 별도 원인 조사다. `UNITY_MAC_DEVELOPMENT=1`은 기존 MacDiagnostic 빌드를 선택하고 기본0은 Release다. `--wave-benchmark-profile`은 Development에서만 허용한다. 8900·11100·13500틱의 넓은 탐색 구간은 과거 지연의 재현을 보장하지 않는다. GC.Alloc 할당 바이트·GC 정지·셰이더 첫 컴파일·에셋 로드·격자 재구축·화면 구성 마커를 동일 프레임에 연결해 조사한다.
5. 동일 느린 프레임의 지배적 마커로 명확한 원인을 확인하면 좁게 수정하고 프로파일러를 끈 깨끗한 Release로 끊김 기준을 다시 검증한다. 통과하면 #169를 닫는다. 원인이 불명확하면 후보만 보고하고 중단하며 #169는 열린 상태를 유지한다. 새 구현·진단은 PR1~2개 범위다.

## 결과와 비용

상한 대기와 작업 비용을 혼동하지 않고 이후 웨이브의 회귀 추세를 비교할 수 있다. Development 계측은 자체 오버헤드가 있어 Release 수치와 섞지 않는다. GC.Alloc 메타데이터가 없으면 미측정으로 남기고0바이트로 해석하지 않는다. 프레임 상관·프로파일 경고·버퍼 누락 여부를 기록하며 중첩 inclusive 마커를 합산하지 않는다.

실제 기기 성능 합격선은 Fold7 #98에서 다루지만 기기 보류는 그대로다. #126 수치·스폰·경제를 바꾸지 않는다. 성능은1b 선행 조건이 아니며 사용자 직접 플레이 소감이 여전히1b 시작 조건이다. 이전 보고·Release·CSV는 역사 기록으로 보존하고 별도 정정 안내만 붙인다.

## 거절한 대안

- 상한60fps 간격에16.7ms 합격선을 유지: 타이머와 프레임 대기를 작업 비용으로 잘못 판정한다.
- 상한 없는 수치만으로 끊김 통과: 실제 상한 설정의 간헐적 지연을 검증하지 못한다.
- 프로파일러 실행을 Release 관문으로 채택: 계측 오버헤드와 Development 코드 경로가 섞인다.
- 원인이 불명확한 광범위 최적화: 사용자 지정 중단 조건과 작은 PR 범위를 벗어난다.

## 검증

분석기 회귀 검사는 경계33/100ms, 정확히20% 증가, 반복별 밀도 누락, 설정 불일치, Development·프로파일러·포커스 무효화를 확인한다. 실제 uncapped3회와 capped3회, Development 원인 조사 결과는 별도 보고에 남긴다. 이 ADR이나 분석기 테스트만으로 새 네이티브 실행·원인 확정·성능 통과를 주장하지 않는다. 번호는 병합 직전 main에서 다시 확인한다.
