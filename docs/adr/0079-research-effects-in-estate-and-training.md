# ADR0079 · 연구 효과를 영지 생산·훈련 계산에 반영 (제안)

상태: **제안 — Core 변경 필요 부분은 사용자 결정 대기**. 2026-10-31. 연결 [#606](https://github.com/hyunlord/bs-mobile/issues/606). 선행: [ADR0077](0077-authoritative-slg-server.md), [ADR0078](0078-server-domain-command-transactions.md), [GDD17 §5](../design/gdd/17-slg-research-proposal.md). 모든 수치는 [가설]이다. 이 문서는 코드·데이터·Core를 바꾸지 않는다.

## 1. 현재 사실 (코드 읽기)

- 연구 분야(#591)는 완료 노드와 동종 합산 → `sharedCaps` 1회 clamp 값을 **조회만** 한다. 어떤 계산에도 쓰이지 않는다.
- 영지 생산은 Core `AccountEstate.Produce`가 site별 `PerMinute × ParentLevelPermille(+분기 보너스)`를 `Remainder`(분모 60×1000) 고정소수점으로 누적하고, `StorageSeconds`·`StockCap` 상한을 적용한다. 입력은 r8 설정뿐이며 **외부 보너스 입력이 없다**.
- 건설 시간은 Core `Start`가 `step.Seconds × (1000 − 분기 감소) / 1000`으로 정한다. 연구 보너스 입력 없음.
- 보관 시간은 Core `StorageSeconds`(곡창 단계·분기, `MaximumSeconds`)이다. 연구 추가초 입력 없음.
- 훈련 시간은 서버 `TrainingHandler`(#590)가 `ceil(base × 1000 / (1000 + min(bonus, cap)))`로 계산하며 서버 보너스 입력이 이미 있다(현재 0).
- 공통 writer 순서는 `EstateApplication.Apply`(Core 영지 전진) → 분야 Advance(연구 완료 정산) → … 이다. 따라서 지금 구조에서는 연구가 구간 중간에 완료돼도 **그 구간 전체가 Core의 한 번 전진**으로 계산된다.

## 2. 결정 제안

### 2.1 효과 스냅샷을 공통층으로
연구 분야가 완료 시각과 함께 **효과 변경 이벤트**(`domain`, 새 applied 값, 유효 시작 UTC)를 낸다. 공통 writer가 계정별 "유효 효과 표"를 유지하고, 다른 분야(훈련)와 Core 호출에 **읽기 전용**으로 넘긴다. 분야끼리 서로의 상태를 직접 읽지 않는다(ADR0078 경계 유지).

### 2.2 효과 변경 시각별 생산 분할 (ADR0078 검증 항목)
writer가 이번 요청의 전진 구간 `[t0, now]` 안에서 효과가 바뀌는 시각 `t1 < t2 < …`(연구 완료 시각, 서버 사건 순서)를 먼저 구한 뒤 Core `Advance`를 **구간별로 나눠** 호출한다: `Advance(t1)` → 효과 반영 → `Advance(t2)` → … → `Advance(now)`. Core는 이미 임의 시각까지의 전진을 지원하므로 분할 자체는 Core 변경 없이 가능하다. 생산 나머지(`Remainder`)는 구간 사이에 그대로 이어져 **소급 재계산·이중 계산이 없다**(GDD17 예: 1시간 10개 + 다음 1시간 10.5개 = 20.5개 → 정수 20 + 나머지 보존, 21개로 소급하지 않음).

### 2.3 영역별 반영 방식
| 효과 | 반영 지점 | Core 변경 |
|---|---|---|
| M1 훈련 속도 | `TrainingHandler`가 작업 **시작 시** 유효 효과 표에서 `training.speedPercent`를 읽어 고정(시작 snapshot) | **불필요** |
| E1~E3 생산 속도 | `Produce`의 permille에 `min(cap, 연구 합계)`를 더하는 **opt-in 입력** | **필요** |
| A1 건설 속도 | `Start`의 시간 식에 `ceil(base/(1+min(30%,합계)))` 입력, 시작 snapshot | **필요** |
| A2 보관 시간 | `StorageSeconds`에 `+600×레벨`, `MaximumSeconds`(18000) 상한 유지 | **필요** |
| M2/M3/영웅 판 안 효과, A3 행군 | 출정 snapshot(ADR0077 §10) | 판 규칙·리플레이 형식 쪽, 별도 |

Core 변경이 필요한 3개는 **입력이 없을 때 기존 경로와 바이트·해시가 같은 opt-in 입력**(예: `AccountEstateBonuses` 인자, 기본 0)으로 제안한다. 기존 r8/v6 저장·리플레이·골든 해시는 바꾸지 않는다. 이 변경은 Core 규칙 변경이므로 **구현 전에 사용자 승인**이 필요하다.

## 3. 검증 계획 (구현 시)
- 분할: 같은 총 시간을 (a) 효과 없음, (b) 중간 완료, (c) 완료 시각 정확히 경계, (d) 두 연구 연속 완료로 나눠 생산량·나머지가 손계산과 같고, 구간 수와 무관하게 효과 없는 경우는 기존 한 번 전진과 결과가 같음.
- 상한: 생산 20%·건설 30%·훈련 30%·보관 18000초에서 증가분 0 경계, 소급 지급 0.
- snapshot: 진행 중 훈련·건설 작업은 시작 때 값 유지, 연구 완료가 남은 시간을 다시 계산하지 않음.
- 역사: 효과 입력 없는 경로의 기존 골든·영지 테스트 불변.

## 4. 거절한 대안
- **서버에서 생산 보너스를 따로 누적:** Core의 site별 `StoredSeconds`·`StockCap`·넘침 폐기 규칙을 서버에 복제하게 되어 두 규칙이 갈라진다. Core가 규칙을 소유한다는 경계(AGENTS.md)에 어긋난다.
- **연구 분야가 Core 상태를 직접 수정:** 분야 처리기의 순수성·영지 정산 순서와 충돌한다.
- **완료 시점부터가 아니라 요청 시점부터 적용:** 접속 빈도에 따라 생산량이 달라진다.

## 5. 다음 단계
1. 사용자 결정: Core opt-in 입력 3개(생산·건설·보관)를 추가할지.
2. 결정 전 진행 가능: 2.1 효과 표 + 2.2 구간 분할 골격(효과 0, Core 무변경) + M1 훈련 연결(#590 병합 후).
