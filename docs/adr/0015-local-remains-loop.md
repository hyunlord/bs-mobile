# ADR 0015: 처치 잔재를 위치에 보존해 나중에 심은 작물과 연결한다

- 상태: 채택 — R3 구현 계약, 실행·측정 결과는 별도 검증 전
- 승인: [기본 A안 #32](https://github.com/hyunlord/bs-mobile/issues/32), [구현 #62](https://github.com/hyunlord/bs-mobile/issues/62)
- 검증: [잔재 고리 런북](../runbooks/verify-remains-loop.md)

## 문제와 범위

사용자는 새싹 변경·개척 기사를 기본 영지·영웅 각 하나로 선택했다. 기존 처치 처리는 가장 가까운 기존 농지에 거리 제한 없이 비옥도를 지급해, 농지가 없을 때의 처치를 보존하지 못한다. 선택 A안의 최소 고리는 **처치 위치의 잔재 → 근처 농지 비옥도 → 실제 성장 → 수확**이다. 영웅이 잔재를 들고 이동하는 운반 능력·고유 능력·Unity 화면은 이 결정의 구현 범위가 아니다.

## 데이터와 시간 계약

활성 기본 ID는 `core:sprout_march`·`core:frontier_knight`다. Core는 이 문자열로 분기하지 않는다. 영지의 선택적 `remainsLoop` 객체가 공통 메커니즘을 켜며 필드는 `capacity`, `lifetimeTicks`, `absorptionRadius`다. 모두 양의 정수이고 상한은 1,000,000이다. 명시적 null은 거부하고 생략은 기존 동작을 뜻한다. 처치당 비옥도와 성장 보너스는 동결한 기존 `world.farms` 값을 재사용한다.

R3 시작값은 **보관 1,000개·수명 900틱·흡수 반경 600 world-unit**이다. 수명은 현재 30Hz에서 30초다. 보관 상한은 상태의 무한 증가를 막고, 유효기간은 처치 이후 파종을 연결하는 유한한 창을 만들며, 반경은 지도 전체 최근접 지급을 지역 상호작용으로 제한한다. 세 값은 [#62](https://github.com/hyunlord/bs-mobile/issues/62)의 초기 계약이며 적정 재미·최적 성능·R2 관문 통과를 입증한 보정값이 아니다. R2 결과를 맞추기 위한 정책별 강화나 추가 수치 보정을 하지 않는다.

1. 실제 적 사망마다 해당 위치에 잔재 하나를 보관한다. 생성 시각은 완료 틱 `world.Tick + 1`, 만료 시각은 생성+수명이다. 활성 모드에서는 기존 농지 직접 지급을 함께 실행하지 않는다.
2. 잔재는 독립 순번을 사용한다. `World.AllocateId`와 RNG를 소비하지 않아 부수적으로 기존 entity ID·난수 순서를 밀지 않는다.
3. `EstateSystem.Tick` 시작에 이미 존재하는 잔재를 순번대로 처리한다. `world.Tick >= expiresTick`이면 **먼저 만료**시킨다. 그 외에는 반경 이내 최근접 농지로 한 번 전달한다. 거리 동률은 농지 ID로 정한다.
4. 전달은 사망 다음 simulation tick보다 빨라질 수 없다. 해당 틱의 앞선 도구 성장에서 새로 심은 농지도 받을 수 있다. 농지가 없거나 범위 밖이면 만료까지 보관한다.
5. 상한에 도달하면 **새 잔재를 거부**하고 폐기 수를 센다. 이미 보관한 잔재를 바꾸지 않는다. 성숙 농지도 받을 수 있으며 비옥도는 수확 뒤 다음 작물 주기에 남을 수 있다.
6. 비옥도 소비·추가 성장량은 실제 성장 코드가 적용한 양만 센다. 성장 정지·성숙 대기 중 허위 소비를 기록하지 않는다. 비옥도를 소비한 작물 주기의 수확을 세되, 그 수확량 전부가 잔재 덕분이라고 귀속하지 않는다. 수확·파괴에서 해당 주기 표식을 정리한다.

## 보존식과 증거

`Created`는 수용한 잔재 수, `Dropped`는 상한 때문에 거부한 추가 사망 수다. 항상 `Created = Absorbed + Expired + Active`, 잔재 생성 대상 사망 수는 `Created + Dropped`다. `FertilityTransferred`는 실제 농지 증가량, `FertilityConsumed`는 실제 소비량, `GrowthBonusApplied`는 실제 추가 성장량이다. 잔여·파괴된 농지 비옥도가 있을 수 있으므로 전달량과 소비량을 무조건 같다고 검사하지 않는다.

선택적 결과와 시간 표본에 생성·흡수·만료·폐기·활성 수, 비옥도 전달/소비, 성장 보너스, 비옥도 사용 주기 수확을 기록한다. 0틱·정상 표본 틱·실제 종료 틱을 포함하고 결과 조회는 상태를 바꾸지 않는다. 작은 결정론 fixture에서 농지 생성 전 처치부터 실제 수확 식량·XP까지 연결하고 비활성 대조보다 성장 단계가 빨라지는지 검사한다. 전체 리그의 집계 수확을 인과 증명으로 대체하지 않는다.

## 역사 fixture와 활성 데이터

`bcaa00f763ec6950707635569befb558e8de1731`의 역사 데이터는 `core/tests/SowSiege.Tests/Fixtures/phase0-r2/`에 파일별 매니페스트와 함께 보존한다. 원본 데이터는 **243파일·376,167bytes**이며 매니페스트·안내문 크기를 포함한 값이 아니다. 과거 고정 해시·역사 동작 검사는 이 명시적 fixture 루트를 읽고 golden 기대값을 바꾸지 않는다. 활성 콘텐츠 검증과 새 잔재 검사는 현재 `data/`를 별도로 읽는다.

활성 `data/`는 새 기본 ID·프로필·기본 참조·궁합·순환 참조를 일관되게 이관하되 기본 영웅/영지는 각 하나다. 더미 ID도 데이터만으로 같은 잔재 계약을 사용할 수 있어야 한다. 역사 영지·World·결과의 선택 필드는 null일 때 직렬화에서 제외해 과거 해시 형태를 유지한다. 동결 tuning 비교의 허용 범위를 임의로 넓혀 ID 차이를 숨기지 않는다.

## 기각한 대안과 남은 관문

- 농지가 없는 처치를 즉시 버림: 이후 파종과 처치 위치의 관계를 만들지 못한다.
- 전역 최근접 지급 유지 또는 직접 지급과 잔재 전달 병행: 지역성을 잃거나 비옥도를 중복 지급한다.
- 영웅 ID별 예외·공유 entity 순번·추가 RNG: 콘텐츠 독립성과 과거 실행 비교를 손상한다.
- 영웅 운반·새 UI까지 확장: 최소 고리보다 큰 별도 구현이며 이번 결과로 검증할 수 없다.

집중 테스트·역사 golden·더미·전체 CI와 동일한 R2 A/B 조건의 재실행이 남는다. 실행 성공과 밸런스 관문은 별개이며 원본 S4 및 R2 실패를 유지한다. 측정 결과는 후속 R3 보고서에 기록한다.
