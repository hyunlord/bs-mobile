# ADR0084 · 야간 대기열의 main C05 상시 단계(경보)

상태: 승인 — 사용자 결정 2026-11-02. 날짜: 2026-11-02. 연결: [#636](https://github.com/hyunlord/bs-mobile/issues/636).
번호: 작성 시 main의 최대 번호는 0081이다. 0082·0083은 열린 #628·#627이 쓰고 있어 0084를 쓴다. 병합 전 다시 확인한다.

## 맥락

PR마다 C05 3:3 관문(AGENTS.md #200 계약)은 그 PR과 merge base를 비교한다. 병합 뒤 main에 쌓이는 누적 비용은 따로 보지 않는다.
#382 이후 p95 증가(#422)처럼, PR 하나하나는 20% 안이어도 main에서는 누적될 수 있다.

## 결정

야간 측정 담당 대기열에 "main C05 상시 단계"를 둔다.

- **측정:** 그날 밤 시점 최신 main head의 C05 benchmark Release를 uncapped, 1600×900으로 유효 3회 잰다. 유효성은 다른 C05 측정과 같은 규칙이다.
- **비교:** 직전에 측정한 main의 3회와 `tools/check-wave-regression.mjs --contract benchmarks/wave-c05/contract-v2.json`으로 밀도별 통합 p95를 비교한다.
- **판정은 경보다:** 어느 밀도든 +20%를 넘거나 판정 JSON이 없으면 night 로그에 `MAIN REGRESSION`을 남긴다.
  - 아침 보고 맨 위에 "main 회귀"로 적는다.
  - 두 측정 커밋 사이에 main에 병합된 커밋을 first-parent, 커밋 순으로 함께 적는다.
  - 되돌리기나 병합 차단은 하지 않는다. PR 단위 C05 관문은 그대로다.
- **위치와 건너뛰기:**
  - 첫날 밤(2026-11-02)은 대기열 맨 끝에서 기준선만 기록한다. 비교 대상은 없다.
  - View·Core PR이 main에 처음 병합된 다음 날 밤부터는 대기열 맨 앞(FP01 앞)에서 돈다.
  - 직전 측정 이후 main에 View·Core 변경이 없으면 건너뛴다. View·Core 변경은 `core/src/`, `data/`, `unity/Assets/`(Tests 제외)의 변경으로 본다.
- **기록:** 측정한 main 커밋은 `$MV/mainc05/history.tsv`에, 실행·판정 출력은 `$MV/analysis-mainc05/`에 남긴다.

## 결과·비용

- 하룻밤 대기열에서 C05 6회 안팎의 시간을 더 쓴다. 3회 측정에 실패와 대기가 더해진다.
- PR 측정 순서를 앞에서 밀어낸다. 그래서 View·Core 변경이 없는 날은 건너뛴다.
- Mac uncapped 추세일 뿐이다. 기기 성능 판정(#98)을 대신하지 않는다.
- 실행 간 편차가 있다. FP01 기준선에서는 한 실행의 느린 꼬리가 통합 p95를 크게 바꾼 사례가 있었다. 그래서 경보는 원인 조사의 시작점으로만 쓴다.

## 거절한 대안

- **main 회귀를 병합 차단 관문으로 쓴다:** 원인 PR을 특정하기 전에 다른 작업을 막는다. 사용자 결정에 따라 경보로 둔다.
- **매일 무조건 측정한다:** View·Core 변경이 없는 날은 같은 결과를 다시 재는 것이라 대기열 시간을 낭비한다.

## 검증

- `node tools/check-docs.mjs`가 통과했다.
- 첫 기준선 기록은 2026-11-02 밤 night 로그(`mainc05`)로 확인한다. 이 ADR만으로 성능 관문을 통과했다고 보고하지 않는다.
