# ADR 0055: 정상 속도의 지연 회복 틱을 여러 표시 프레임에 나눈다

- 상태: 승인 — 기존 사용자 끊김 개선 지시 범위의 구현, 성능 관문은 미완료
- 날짜: 2026-10-12
- 관련: [#223](https://github.com/hyunlord/bs-mobile/issues/223), [PR235](https://github.com/hyunlord/bs-mobile/pull/235), [ADR0048](0048-continuous-presentation-and-live-capture.md)
- 대체 범위: ADR0048의 지연 후 틱 스케줄링 부분만. 표시60fps·보간·계측 경계와 역사 기록은 유지한다.

## 맥락

같은 프로세스의 Development 반복에서 최대658.9129/649.4870ms 지연과 뒤따른28/25틱 몰림을 관찰했다. 선택한 실패 프레임의 GC 증가량은0이다. 첫 등장만의 비용이라는 근거는 없으며 큰 최초 지연의 원인은 미확인이다. 기존 사용자 지시는 확인된 원인을 고치되 실패와 미확인을 보존하는 것이다. 이번 변경은 긴 지연 뒤 회복 계산이 한 표시 프레임에 몰리는 이차 현상만 대상으로 한다.

## 결정

정상 속도 `Speed == 1`에서는 표시 프레임마다 `Advance`를 최대1회 실행한다. 누적된 시간 빚은 버리지 않고 다음 표시 프레임으로 넘긴다. 실행한 틱만큼만 누적 시간을 차감한다. 프레임마다 빚을 지우거나 빠진 틱을 생략하지 않는다.

동일한 기록 명령을 재생할 때 명령 순서·Core 규칙·상태 해시 계약은 유지한다. 벽시계상 실행 시점은 달라질 수 있다. 실시간 사용자가 입력을 바꾸는 시점까지 과거 실행과 같은 명령 스트림이 된다는 주장은 하지 않는다. 오프라인 렌더·사전 재생·빠른 디버그 속도의 기존 경로는 보존한다.

벤치마크는 A의 `legacy-unbounded-catch-up`과 B의 `one-advance-per-render-frame-debt-preserved-v1`을 설정 출처에 명시한다. 변경된 스케줄링을 같은 설정이라고 숨기지 않는다. 동일 입력·해시는 별도로 검증하고, 각 반복의 최대 지연과25ms 초과 비율을 각각 판정한다.

## 결과·비용

지연 이후 계산이 한 프레임을 추가로 길게 만드는 현상을 제한하지만, 가장 먼저 발생한 수백ms 지연을 없애는 수정은 아니다. 부채가 쌓이면 회복 기간 동안 시뮬레이션이 벽시계보다 뒤처질 수 있다. 변경 전후 실제 전경 Release 계측이 필요하며 #223과 초안 PR 상태를 유지한다.

## 거절한 대안

- 누적 시간을 버리거나 틱 생략: 입력 재생과 진행 계약을 바꾼다.
- 제한 없이 한 프레임에 회복: 이미 관측된28/25틱의 추가 계산 몰림을 유지한다.
- 최초 지연을 GC·첫 등장·OS 탓으로 확정: 현재 증거로 원인을 특정할 수 없다.

## 검증

구현은 `ef86f6a`, 최종 검증 빌드는 `8f446e5`다. Node 검사17개와 Unity pacing25/25가 통과했다. 실제 카드 제안·선택을 생성한 동일 명령 fixture에서 기존 배치와 새 배치의 최종 상태 해시가 일치한다. 오프라인30틱/60프레임 및 정상 속도 부채 보존도 검사했다. 이는 실제 Release 성능 통과를 대신하지 않는다. Release 비교는 전경 유지 조율로 미완료다. [선택 실패6프레임](../metrics/stutter-223-diagnostic-samples.csv)은 각 동일 프로세스 반복의 최대 간격 상위3개를 보존하며 Development 자료를 Release 합격 근거로 사용하지 않는다.

번호는 원격 main의 최신0054 다음0055로 확인했다. #126·#98·#224·1b 보류와 사용자 시각 승인 대기는 변경하지 않는다.
