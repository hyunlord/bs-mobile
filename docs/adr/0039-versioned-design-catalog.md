# ADR0039: 실행 계약을 보존하는 개정별 설계 카탈로그

- 상태: 형식은 사용자 승인; 로스터 자체는 needs-decision
- 날짜: 2026-10-10
- 근거: [#135](https://github.com/hyunlord/bs-mobile/issues/135), [카탈로그 계약](../design/designed-v1-catalog-contract.md)

## 문제와 결정

기존 `designStatus`는 실행 프로필 선택과 연결돼 있다. 실행 중인 레코드를 `designed-v1`로 바꾸거나 새 메커니즘을 기존 runtimeProjection에 적으면 기존 로더를 깨거나 미구현을 구현된 것으로 보이게 한다. 사용자 요청은 실행 변경 없이 설계와 데이터를 갱신하는 것이다.

별도 `data/system-design-v1.json`을 제안 설계 정본으로 둔다. 각 레코드는 동일 콘텐츠 ID 체계와 `designed-v1` 상태를 쓰고 개정+ID로 식별한다. 기존 기록을 개정한 것은 sourceId로 계보를 남기며 제안 로스터 내부 참조와 현재 실행 풀 참조를 구별한다. 스키마와 의미 검사를 기존 CI에 통합한다. 실행 프로필·계수는 바꾸지 않는다.

후속 실행 레코드는 문서화된 designRef로 구현 대상 설계를 가리킨다. 현재 D3에서는 실행 로더에 이 필드를 넣지 않는다. 링크와 실제 동작 증거는 별도이며, 나중에 구현자가 필드를 추가할 때 strict 스키마·참조 검증도 함께 도입한다.

## 대안과 한계

기존 레코드의 상태·성장·발동 필드를 직접 교체하는 방법은 승인되지 않은 실행 변경과 로더 개편을 유발하므로 채택하지 않았다. 문서에만 로스터를 적는 방법은 기계 판독과 수량·참조 검사가 불가능해 채택하지 않았다. 별도 카탈로그는 중복된 동일 ID의 문맥 구분이 필요하므로 원천과 개정 식별을 계약으로 명시한다.

새 설계 JSON도 기존 전체 데이터 출처 해시에 포함된다. 출처 해시가 달라지는 것과 게임 상태가 달라지는 것을 구별하고 해시 알고리즘은 유지한다. 이 카탈로그는 사용자 승인·구현·실기 증거가 아니다. Lattice 도구는 별도 세션의 책임이다.
