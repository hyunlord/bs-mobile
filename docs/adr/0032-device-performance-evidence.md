# 0032 — 실기 성능 진단과 관문 측정의 분리

- 상태: 승인 — 1단계 B M4 구현 범위
- 날짜: 2026-10-09
- 연결: [#98](https://github.com/hyunlord/bs-mobile/issues/98)

## 맥락

적의 최고 개체 수와 판 후반 p95만으로 지속된 적500+ 장면의 성능을 증명할 수 없다. 프레임의 남은 시간을 GPU·GC로 추정하면 병목 원인을 잘못 판단할 수 있다.

## 결정

1. 기존 `frames.csv`의 모든 렌더 구간과 의미를 유지한다. 사전 선언한 시작 틱에 도달한 첫 행부터 누적60000ms를 넘기는 행 전체까지 연속 검사한다. 모든 행에 적≥500,1배속,일시정지·중단·부분 구간 없음이 필요하다. nearest-rank p95≤16.7ms를 적용하며 유리한 구간을 다시 찾지 않는다.
2. 선언은 실제 session/build/source/data/seed/device와 결합한다. 수집 전에 외부 기록에 선언 파일 해시를 남기며 분석기는 같은 바이트를 요구한다. JSON 시각이나 분석기 통과 자체는 사전등록 시점을 증명하지 않는다.
3. 성능 관문은 프로파일러·Deep Profiling을 끈 상태에서 수행하고 리플레이·프레임 기록을 유지한다. 화면 녹화 여부도 선언한다. 해당 플래그는 선언 증거이며 기존 CSV가 독립 측정한 사실로 표현하지 않는다.
4. 병목 진단은 별도 Development 실행의 정적 ProfilerMarker와 최대10초 목표의 Unity raw trace를 사용한다. 실제 길이·중단 이유·빌드 출처·파일 해시를 보존한다. 스톨 때문에 길어지면 실제 시간을 보고한다. 모든 스레드의 원본 샘플을 내보내며 포함 관계의 시간을 합산하지 않는다. GC.Alloc 메타데이터 부재는0바이트가 아니다. CPU 프레임 시간은 GPU 시간이나 표시 지연이 아니다.
5. 출현10배는 기존 Core의 기록 가능한 명령만 사용하는 명시적 진단 옵션이다. 개체 상한·체력·전투 규칙은 바꾸지 않는다. 무적·출현 조작 판은 정상 완주3판과 분리한다.
6. 사용자 APK는 `FoundationBuild.AndroidRelease`로 Development 옵션 없이 만든다. 개발 메뉴·진단 캡처·fixture는 제외하며 정상 플레이 기록은 유지한다. 최종 전달 APK 자체를 설치해 관문을 확인한다.

## 결과와 비용

raw trace와 전체 샘플은 클 수 있으므로 로컬 분석에 보관한다. 공개 원자료는 실패와 선정 표본만이며 CSV로 재생성할 수 있는 결과를 중복 업로드하지 않는다. 진단 실행과 프로파일러 없는 성능 판정은 각각 시간이 필요하다. 물리적 접기/펼치기는 #83 대기다.

## 거절한 대안

- 낮은 적 수·느린 프레임을 제거한 구간: 요구한 연속 장면을 증명하지 못한다.
- 별도 자체 CPU/GC 계측 CSV 시스템: Unity 프로파일러가 제공하는 기능을 중복 구현한다.
- `GC.GetAllocatedBytesForCurrentThread`를 Android 근거로 사용: 설치된 IL2CPP 구현에서 지원되지 않는다.
- Development APK 검사만으로 사용자 Release 검증을 대신하기: 컴파일 조건과 실행 경로가 다르다.

## 검증

분석기의 경계·실패 보존을 Node 테스트로 확인한다. 실제 raw 생성·Editor 가져오기·원인 판정, 폴드7 성능·정상3판·녹화는 별도 실기 증거가 필요하다. 이 ADR은 관문 통과 보고가 아니다.
