# ADR 0044: 원본 입력을 보존하는 네이티브 고밀도 회귀 검사

- 상태: 승인 (2026-10-10 사용자 #169 결정)
- 날짜: 2026-10-10
- 연결: [#169](https://github.com/hyunlord/bs-mobile/issues/169), [#183](https://github.com/hyunlord/bs-mobile/issues/183)

## 맥락

자연 플레이에서 높은 적 밀도를 기다리면 입력·카드·성장 경로가 달라져 비용 비교가 어렵다. C05에는 400~800개 이상인 구간과 14400틱 Quit 종결 해시가 있는 원본 입력이 남아 있다. 과거 CSV가 더 긴 구간까지 존재하더라도 재생 증거의 범위를 확장하지 않는다.

## 결정

원본 C05 입력 바이트와 당시 데이터 커밋을 고정한다. 별도 생성된 벤치마크 카탈로그를 명시적 실행 인자로만 사용한다. 일반 실행의 정본 프로필은 변경하지 않는다. 7200틱 이전은 비측정 준비, 이후 120프레임은 렌더 준비이며, 지정한 세 구간은 정상 30Hz 입력과 실제 Mac Release 렌더링으로 측정한다. 원본 헤더·명령·종결 해시를 다시 쓰지 않는다.

후보 검색용 공간 인덱스·Id 사전·해석 캐시는 비직렬화 내부 상태다. 거리/Id, Id 단독, 목록 순서, 젖은 대상 우선 등 기존 연산별 순서를 보존한다. 넉백은 즉시 인덱스에 반영하고 중첩 검색 버퍼를 분리한다. 두 실제 Core 대상 DLL에서 과거 27000틱 기록과 C05 종결 해시를 검사한다.

프레임 전체 시간은 Update 진입 간 시간으로 렌더링과 대기를 포함한다. 시뮬레이션·스냅샷·표현 준비 CPU 구간은 따로 측정한다. 지연된 FrameTimingManager 결과는 별도 시계열이며 현재 밀도의 GPU 시간으로 붙이지 않는다. 지원하지 않는 수치는 미측정이다. 타이밍 지원 설정은 소스에 고정하고, 명시적 수집은 벤치마크 경로에서만 실행한다.

포커스 이탈·일시정지는 영구 표시하고 실패 자료를 보존한다. 분석기는 이를 유효 표본으로 채택하지 않는다. 동일 기기·설정·입력·화면에서 전후 각각 3회, 밀도별 모든 반복의 p95 ≤16.7ms를 관문으로 사용한다. 실패를 숨기거나 스폰·밸런스를 바꾸지 않는다. 성능은 1b 시작 조건에서 제외되며 사용자 직접 플레이 소감이 여전히 필요하다.

## 결과와 비용

작은 원본 재생 표본을 저장소에 유지하고 과거 데이터는 Git에서 복원한다. 전체 성공 CSV·재생성 가능한 표를 Release에 중복 업로드하지 않는다. 현재 콘텐츠 성능과 고정 역사 입력 회귀는 별도 주장이다. 기기·품질·OS가 달라지면 새 기준 쌍이 필요하다. Fold7 검증을 대신하지 않는다.

Unity가 빌드 중 생성하는 URP 런타임 목록은 빌드 전 원본과 비교하여 해당 목록만 달라졌을 때 복원한다. 다른 작성 내용이 바뀌면 실패하며 소스 무결성 검사를 생략하지 않는다.

## 거절한 대안

- 밀도를 올리기 위한 스폰 조정: #126 보류 및 동일 규칙 조건 위반.
- 헤드리스 실행만으로 성능 통과: 렌더 비용을 측정하지 못함.
- 공간 격자 순서 그대로 적용: 기존 공격 결과와 역사 해시를 바꿈.
- 포커스 이탈 프레임 제거: 느린 프레임을 숨기는 표본 편향.

## 검증

집중 회귀 검사·원본 재생 두 DLL 교차 검사·CI·네이티브 전후 측정을 각각 구별한다. 실제 결과와 미달 비용은 #169 및 후속 보고에 기록한다. ADR 자체는 성능 통과 증거가 아니다.
