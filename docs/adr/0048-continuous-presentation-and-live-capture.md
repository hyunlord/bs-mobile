# ADR 0048: 결정론 틱과 연속 표시·실시간 녹화를 분리한다

- 상태: #200 사용자 지시 구현
- 날짜: 2026-10-10
- 관련: [#200](https://github.com/hyunlord/bs-mobile/issues/200), [ADR0047](0047-state-driven-fallow-kingdom.md)

## 맥락

사용자는 Mac의 계산 비용 여유와 별개로 영주·적·무기의 움직임이 끊겨 보인다고 판정했다. 황금 1분은 그림뿐 아니라 입력 반응과 부드러움도 보여야 한다. 기존 30fps 동기 화면 읽기 녹화는 새 관문의 증거가 아니다.

## 결정

이전/현재 스냅샷의 안정 ID로 움직이는 wave 그림을 보간한다. 방향은 최단각으로 연결하며 생성·제거·활성화 교체·리셋을 이전 개체와 섞지 않는다. 궤도 파편은 기존 활성화와 순번으로 대응하고 표시 각도만 연속화한다. 실제 타격 사건의 위치와 대상은 고정한다. 걷기·공격·피격의 절차적 표현은 렌더 시간으로 진행한다.

영주 표시는 현재 입력을 사용해 제한된 범위에서 예측하고 새 정본 위치로 보정한다. 같은 표시 좌표로 카메라를 이동한다. Core 상태·충돌·사건에는 예측 좌표를 넣지 않는다. 소프트웨어 입력 표본→렌더 제출/프레임 완료 지연을 기록하며 이를 물리 입력→광자 지연이라고 부르지 않는다.

Mac 일반 실행은 `vSyncCount=1`, `targetFrameRate=-1`, 모바일은60fps다. 동적 화면 주사율을 전제로 실제 간격을 기록한다. 기존 C05의 명시적 프레임 설정은 비교 계약이므로 따로 유지한다. [Unity vSync 계약](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/QualitySettings-vSyncCount.html)에 따른다.

실시간 녹화는 미리 할당한 RenderTexture/픽셀 버퍼와 비동기 GPU 읽기를 사용한다. 인코딩·파일 쓰기는 worker로 옮기며 실제 프레임 시각·오디오 시각·누락·오류·큐 포화를 기록한다. 누락 프레임을 복제하거나 틱 이미지를 생성해60fps라고 보고하지 않는다. [Unity 비동기 화면 캡처](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/ScreenCapture.CaptureScreenshotIntoRenderTexture.html)를 사용한다. OS 화면 기록·손쉬운 사용 권한은 요구하지 않는다.

## 할당·회귀 관문

Update/그리기0B가 기본 기준이다. 반복 문자열·LINQ·열거자·임시 버퍼를 제거하고 풀을 준비한다. 전체Update와 Core적용·스냅샷·표현수락·HUD·그리기·기록을 별도로 측정한다. immutable Core 스냅샷·이벤트·녹화 worker의 기존 할당을 제외하고 전체0B라고 표시하지 않는다. 남는 비제로 경로는 관문 미달로 기록하고 원인과 추적 이슈를 남긴다.

Core/View PR은 같은 C05 무상한3회 기준과 비교한다. 밀도별 통합p95가20% 초과 증가하면 실패하거나 명시적 사유를 PR에 남긴다. 누락·다른설정·중단은 사유로 면제할 수 없다. 기존 역사 판정은 변경하지 않는다. `tools/check-wave-regression.mjs`가 새 정책을 적용한다.

## 검증 경계

기능·결정론 CI와 표시 계약 테스트는 안전망이다. 실제 Mac60fps 실시간 영상·직접 플레이에서 사용자만 '끊김 없음'을 판단한다. #126 수치·경제, #98 Fold7과1b는 계속 보류한다.

## 2026-10-11 후속 결정: 고른60fps와 오프라인 검토 (#218)

[사용자 검토 #218](https://github.com/hyunlord/bs-mobile/issues/218)에 따라 위 Mac 기본 `vSyncCount=1` 결정과 실시간 녹화 판정 요구를 대체한다. 30Hz Core는 유지하고 Mac 표시 기본은60fps다. 현재 화면 주사율을 조회해60Hz는1,120Hz는2(59.94/119.88 포함)로 동기화한다. 모니터·주사율 변경 때 다시 계산한다. 60에 가까운 정수 분할이 불가능하거나 주사율을 얻지 못하면vSync0/target60으로 내려가며 이를 하드웨어60Hz 동기화와 동일한 증거로 주장하지 않는다. 모바일은target60, C05 명시적capped/uncapped계약은 그대로다.411마리재생은 일반 실행과 같은 표시정책을 쓴다.

표시 관문은 녹화를 끈411마리동일재생에서 프레임p5–p95 16.0–17.4ms,25ms초과≤0.2%다. 이전120Hz증거는보존한다. 검토영상은Time.captureFramerate=60의 오프라인입력재생으로 명시하며 실시간부드러움증거로사용하지않는다. 최종판정은캡처없는계측과사용자Mac직접플레이다.

C0534–44%회귀는 누적변경이라는사유만으로닫지않는다. FrameTimingManager의main/render/GPU가용성·시간연결을확인하고같은입력3회로원인또는측정기여도를남긴다.830ms표본도재현확인대상이다.

### #218 구현 검증 기록

깨끗한 `52cea1f` Mac Release에서 120Hz→60fps 분할과 역사 입력 해시 보존을 확인했다. 411마리 재생의 p5/p95는16.5975/16.9731ms이나25ms초과0.551%, Core p95 8.6926ms, Gen0 1.5197회/초로 성능 관문은 미달이다. 60Hz 외부 모니터는 계약 테스트만 통과했으며 실측하지 않았다. C05는 개체 발밑 표시의 화면 구성 기여0.202~0.280ms를 분리했지만 전체20%회귀를 해결하지 못했다. [상세 결과](../review/smooth60-218.md)의 실패와 사용자 직접 플레이 대기를 유지한다. 오프라인 검토 영상은1460장의 연속 고정60fps이며 성능 증거가 아니다.

### #218 끊김 후속: 호출 위치에 근거한 할당 제거

Development 호출 스택은 할당 위치를 찾는 진단이며 그 프레임 시간을 Release 합격 판정에 쓰지 않는다. 411마리 입력의 스냅샷·오디오·카운터 집계에서 확인한 반복 할당을 먼저 제거한다. 관측된 기존 긴 프레임8개는 모두1틱이므로 두 틱 몰림을 원인으로 가정해 스케줄러를 바꾸지 않는다.

내부 이중 버퍼의 빌린 필드는 적 목록과 카운터다. 카운터는 ordinal 순서와 조회를 유지하며 다음 같은 버퍼의 캡처까지만 유효하다. `WaveSnapshotBuffer.Detach`로 두 필드를 모두 복사한 뒤 공개 속성·구독자에게 전달한다. 작업물은 모든 표시 필드와 시간에 따른 상태가 같은 경우에만 immutable 레코드를 재사용하고, 배열은 계속 독립 소유한다. 캐시는 규칙·상태 해시 codec에 포함하지 않는다. 무조건 새 레코드·트리를 만드는 대안은 측정된 반복 할당 때문에 채택하지 않는다.

411마리 입력730틱의 .NET 스냅샷 할당은 평균57,995→12,998B이며 최종 해시는 동일했다. 이는 전체Update0B나 Mac GC관문 통과가 아니다. 남은 배열·열거자·첫 사용 캐시 할당과 네이티브 재측정은 별도로 남긴다. PR은 사용자 Mac 플레이 전까지 초안으로 유지한다.

### 표시 대기 수정 후보: Metal Display Link

동일 Development 입력의 기존 Mac 표시 경로에서 계측된 긴 프레임16건은 Update 뒤의 표시 완료 대기9–12ms와 별도 FPS 대기4–6ms가 겹치지 않는 시간 구간으로 이어졌다. vSync0/target60만으로 바꿔도 긴 FPS 대기가 남았다. Metal Display Link 경로에서는 같은 진단 구간의 일반 플레이 지연이 관측되지 않아 `metalUseMetalDisplayLink=1`을 수정 후보로 선택한다. 기존60fps 분할 설정과 Core 입력·해시는 바꾸지 않는다. Unity의 [Mac 플레이어 설정](https://docs.unity.com/en-us/engine/6000.6/manual/platform-specific/apple-mac/player-settings-mac-os)에 있는 지원 설정이며 새 플러그인을 추가하지 않는다.

이는 아직 합격 결정이 아니다. Development 표본은 프로파일러 종료 I/O로 긴 프레임을 만들었으며, Metal 경로의 평상시 p95도17.61–17.68ms로 기존17.4ms 상한을 넘었다. 깨끗한 Release의 A=65983e2/B후보 ABBA 비교에서 긴 프레임과 실제 표시 주기를 각각 판정한다. 진단용 환경변수로 성공 실행을 골라 배포 설정의 증거로 대체하지 않는다.

### #218 최신 사용자 결정: Part 1 계측 후 PR #219, 이어서 Part 2

이 결정은 앞의 **PR #219를 사용자 Mac 플레이 전까지 초안으로 유지**하라는 운영 조건만 대체한다. Part 1 결과를 보고한 뒤 #219를 ready로 전환할 수 있으며, 필수 CI·코드 검토와 저장소 병합 조건은 그대로 지킨다. 선행 PR이나 base 가지의 별도 승인·검증 조건까지 면제하지 않는다. ready 전환은 성능 관문 통과 또는 사용자 플레이 승인이라는 뜻이 아니다. Part 2는 Part 1이 main에 반영된 뒤 그 main에서 새 가지로 시작한다. #126·#98·1b 보류는 유지한다.

새 비교의 A는 `65983e2`, B는 확정된 수정 후보다. 각 fixture에서 **A B B A A B B A**, 각 버전4회로 측정한다. 411마리 재생과 **capped C05의400–599/600–799/800+**를 포함하며, 앞서 계획한544 기준 각3회 비교를 이번 결과로 대체하지 않는다. 역사 결과는 보존한다. 설정·입력·해시·실제 바이너리·실행 순서와 전경 상태를 기록하고, 중단 실행을 좋은 프레임만 골라 되살리지 않는다. 결과가 아직 없는 항목은 대기이며 이 결정 자체가 통과 증거가 아니다.

긴 프레임 원인 조사는 Development 전용 `--diagnostic-long-frames`로 수행한다. Core 세부 단계, 화면 갱신·SpriteBatch·HUD·효과 관련 ProfilerRecorder 관측, 포커스·일시정지·창 변경·첫 적/효과·성장/경험치 등의 사건을 함께 기록한다. Recorder 집계는 관측값이며 동일 프레임의 호출 스택을 제공하지 않는다. 스택과 중첩 경로는 별도 raw Profiler 자료에서 얻는다. 미등록 카운터·미측정 단계는 unavailable로 남긴다. 긴 장을 게임 밖 시간이라는 이유만으로 OS 문제로 확정하지 않는다.

이 계측은 Release에서 실행 조건을 끄는 것에 그치지 않고 컴파일에서 제거한다. Unity Development 빌드는 명시적인 Core `fine-diagnostics` 변형(`SOWSIEGE_FINE_DIAGNOSTICS`)을 사용하며, 일반 Core와 Release에는 새 세부 계측을 포함하지 않는다. 변형 식별자와 DLL 출처를 남기고, Development 프레임 시간을 Release 관문으로 쓰지 않는다. 첫 등장 비용을 주장하려면 같은 프로세스 안에서 같은 상황을 반복해 첫 회와 이후 회를 구분한다. 앱 재시작 사이의 비교만으로 첫 사용 효과를 확정하지 않는다.
