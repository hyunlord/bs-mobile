# ADR0070: quality job 제한 30분과 npm ci 3분 제한·1회 재시도

- 상태: 승인 — 2026-10-22 사용자 결정
- 날짜: 2026-10-22
- 연결: [#350](https://github.com/hyunlord/bs-mobile/issues/350), [ADR0038](0038-docs-only-ci.md)
- 번호: main 최대 0068, 열린 PR #323이 0069를 쓰므로 0070.

## 맥락

- 필수 `quality` job의 제한은 20분이었다. 2026-10-22에 최근 성공 9회를 재 보니 전체 관문이 실행 기계에 따라 8.6~16.0분(중앙값 15.5분)이었다. 느린 기계에서는 여유가 약 4분뿐이었다.
- 같은 날 PR #323의 두 실행에서 `tools/check.sh`의 `npm ci --ignore-scripts`가 7분씩 멈췄다. 다른 실행은 모두 2초 이내였다. 첫 실행은 20분에 취소됐고, 다시 돌린 실행은 19.2분으로 겨우 통과했다.

## 결정

1. `quality` job의 `timeout-minutes`를 30으로 올린다.
2. `tools/check.sh`의 `npm ci --ignore-scripts`는 한 번에 3분까지만 기다린다. 실패하거나 3분을 넘기면 `npm cache clean --force` 뒤 한 번만 다시 시도한다. 두 번째도 실패하면 관문이 실패한다.
3. 시간 제한은 `perl`의 `alarm`으로 건다. macOS에는 `timeout`이 기본으로 없어서, 로컬에서도 같은 스크립트가 돌게 했다.

## 결과·비용

- 느린 기계에서도 정상 실행이 제한에 걸리지 않는다. 대신 정말로 멈춘 실행은 최대 30분 뒤에 실패한다.
- `npm ci` 정체는 최대 약 6분(3분 두 번)으로 묶인다. 패키지를 실제로 받지 못하면 재시도 뒤 실패한다.
- 정체의 원인은 확인하지 못했다. 패키지 파일은 바뀌지 않았다.

## 거절한 대안

- **교차 검증을 병렬 job으로 나누기, 반복 횟수 줄이기:** 시간을 줄이지만 워크플로가 복잡해지거나 결정론 검증이 약해진다. 사용자가 하지 않기로 했다.
- **제한만 올리기:** `npm ci`가 다시 멈추면 30분 중 7분 이상을 그대로 잃는다.

## 검증

- `bash -n tools/check.sh`, 시간 제한·재시도 모의 검사, 실제 `npm ci` 1회.
- 필수 CI가 바뀐 `check.sh`와 30분 제한으로 돈다.
- 런북: [ci-scope.md](../runbooks/ci-scope.md) "시간 제한" 절.
