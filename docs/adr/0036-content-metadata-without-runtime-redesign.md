# ADR0036: 설계 메타데이터와 실행 계약의 구분

- 상태: 승인된 D1 정리 범위. 신규 게임 메커니즘 승인 아님.
- 날짜: 2026-10-10
- 근거: [Phase2B v2](../design/09_ASTRA_GOAL_bs-mobile_phase2b-system-design_v2.md), [#133](https://github.com/hyunlord/bs-mobile/issues/133)

## 문제

Lattice가 종류별 데이터 구조를 읽을 때 콘텐츠 종류와 진화 조합 종류, 설계 의도와 실제 효과, 콘텐츠 참조와 의미 enum을 구별할 수 있어야 한다. 현재 자료에는 풍부한 설계 설명과 별개의 제한된 실행 투영이 공존한다. 이를 일률적으로 ‘구현됨’으로 합치면 실제 기능을 과장한다.

## 결정

콘텐츠는 `id`, `name`, `kind`, `tags`, `designStatus`, `concept`, `effect.trigger/benefit/cost`로 공통 설계 의미를 표현한다. 종류별 구조와 현재 실행 수치는 유지한다. `kind`는 콘텐츠 종류이고, 기존 진화의 조합 유형은 `evolutionKind`로 분리하여 Core에는 기존 유형을 그대로 전달한다. 중첩 메타 장원의 기존 실행 효과 enum은 `manorEffect`로 분리하고 Core의 `Effect`에 투영한다.

설명 전용 메타데이터는 host에서 엄격하게 검사한 뒤 기존 Core 정의로 투영한다. 알 수 없는 필드·잘못된 타입을 허용하여 검사를 우회하지 않는다. `runtimeProjection.effects`에는 실제 처리하는 효과만 담는다. projection이 없거나 비었다는 이유만으로 기본 공격·적 행동까지 미구현으로 판정해서는 안 된다. 현재 프로필의 override·선택 여부·Core 소비 경로도 함께 확인한다.

ID 참조는 이름이나 배열 순번으로 대체하지 않는다. 다만 `enemy.target`, `tool.growth.target`, `effect.target` 같은 대상 분류 enum, `chapter.index`의 순서, `challenge.target`의 수치 목표는 콘텐츠 ID 참조가 아니다. 효과의 `subject`와 조건의 `value`도 operation/condition 유형에 따라 ID·enum·태그가 갈린다. 이 경계를 [런타임 처리표](../design/runtime-operations.md)와 스키마/참조 검사에 명시한다.

## 보존 관문

- 실행 계수·레벨 성장표·프로필 선택과 순서·기존 ID를 유지한다.
- 기존 데이터와 정리 데이터에서 결정론 상태 해시 및 리그의 게임 결과를 비교한다. 출처를 제외한 게임 결과가 다르면 D1 완료로 판정하지 않는다.
- JSON 바이트·스키마·host 소스가 바뀌므로 데이터/소스 출처 해시는 바뀔 수 있다. 이를 숨기거나 과거 해시를 덮어쓰지 않는다. 프로필 파일을 그대로 보존한 경우 프로필 해시는 유지되어야 한다.
- 새로운 메커니즘, 난이도·경제 보정과 Core 규칙 변경은 하지 않는다.

## 후속 설계의 경계

D3의 `designed-v1`은 설계 제안의 지위다. 실제 동작이 그 설계와 같다는 선언이 아니다. 제안 로스터와 역사 전체 풀의 수량을 구분하고, 현재 런타임 투영과 제안 메커니즘을 별도로 검증한다. 게임 구현은 사용자의 로스터 검토 이후 별도 작업이다. Lattice 뷰어·MCP는 다른 저장소의 담당이며 이 ADR은 도구 제작을 승인하지 않는다.

## 입력 호환 범위

현재 저장소 콘텐츠는 스키마에서 공통 필드를 필수로 검사한다. 개별 콘텐츠 host 로더는 역사 테스트 카탈로그를 위해 `kind`가 없는 옛 형식과 옛 진화 subtype을 제한적으로 읽을 수 있다. 따라서 CLI 로딩 성공만으로 D1 메타데이터 완전성을 증명하지 않으며 CI의 스키마 검사가 함께 필요하다. 반면 중첩 메타 카탈로그의 원시 JSON은 새 메타데이터와 `manorEffect` 형식으로 이행해야 한다. 이 입력 파일 이행은 플레이어 저장·리플레이 코덱의 변경이 아니다. 기존 저장과 Core 카탈로그의 값은 그대로 유지한다.
