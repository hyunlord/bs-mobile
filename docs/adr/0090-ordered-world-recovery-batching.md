# ADR0090 · 순서를 보존하는 월드 복구 DB 일괄 처리

상태: **제안 — 구현·새 성능 측정 NOT_RUN** · 2026-11-04 · [#699](https://github.com/hyunlord/bs-mobile/issues/699).
출시 전 개선 대상이다. 사용자는 설계 초안 PR 작성을 요청했으며, 이 문서는 설계 승인이나
30초 목표 달성을 뜻하지 않는다. [#697](https://github.com/hyunlord/bs-mobile/pull/697)의
실측·서버 구현 위에 문서만 쌓는다. 번호는 최신 main과 열린 PR의 ADR 최대 번호 0089를
확인한 뒤 선택했다. Core·Unity·리플레이·게임 수치는 변경하지 않는다.

## 1. 관측 사실과 목표 가설

[정본 실측](../metrics/world-operations-20261104.md)의 소스는 `613baa4c`다.
실제 1천 행군을 자원지 하나로 발령하고 서버 시각을 30일 이동한 뒤 도착·귀환·고갈·재생성을
복구했다. DB 연결 한도는 100, 풀별 상한은 4였다. 각 설정 1회인 로컬 실측이다.

| 사건 선택 상한 | 1천 행군 복구 | 행군/초 | 확정 사건/초 |
| --- | ---: | ---: | ---: |
| 1 | 23.715초 | 42.17 | 84.38 |
| 32 | 18.871초 | 52.99 | 106.03 |
| 128 | 19.938초 | 50.16 | 100.36 |
| 512 | 19.263초 | 51.91 | 103.88 |

확정 사건은 각 실행 2,001개다. 사용자가 지적한 초당 약 50건은 **행군 완료 기준**이며,
사건 처리 수와 구별한다. 현재 상한은 호출당 반복 횟수만 제한한다. `RecoverBatchAsync`는
사건마다 후보 조회, 계정/분야 읽기, 여러 원장 쓰기, 커밋을 반복한다. 왕복 비용이 개선
후보라는 코드 근거는 있지만, 전체 시간의 몇 %인지 아직 프로파일링하지 않았다.

**[가설] 1만 행군을 30초 이내에 복구한다.** 아래 고정 workload·같은 기기에서 독립 3회
모두 만족하는 것을 제안 검증 목표로 삼는다. 확정된 출시 SLA나 이미 통과한 CI 기준이 아니다.
행군 기준 최소 약 333.3개/초이며, 사건 수는 생성된 실제 원장을 세어 별도 보고한다.
1천 행군 결과를 1만 행군 실측으로 환산하지 않는다.

## 2. 대안과 권고

| 안 | 장점 | 비용·판단 |
| --- | --- | --- |
| 사건별 커밋 유지, 한 사건 안의 SQL만 묶기 | 복원 경계가 그대로이며 먼저 실험하기 쉬움 | 매 사건 커밋·후보 재조회가 남음. 비교 기준/1차 실험으로 보존 |
| **제한된 연속 사건 묶음: 선조회 → 순차 계산 → 묶음 저장/커밋** | 반복 읽기·쓰기 왕복과 커밋 횟수를 함께 줄일 수 있음 | ADR0085의 사건당 원자성을 묶음당 원자성으로 바꿈. 승인 후 검증할 권고안 |
| 전부 SQL 저장 프로시저 또는 사건 병렬 실행 | 서버 왕복 감소 가능 | 공통 분야 규칙 복제 또는 사건 순서 변경 위험. 이번 설계에서는 채택하지 않음 |

배치 크기를 늘리거나 기존 await 호출을 병렬로 감싸는 것만으로 일괄 처리라고 하지 않는다.
전체 backlog를 단일 거래로 묶지 않으며 DB 연결 수 증가·durability 약화로 목표를 맞추지 않는다.

## 3. 변경하지 않을 계약

- 전역 선택 키는 **(dueAt, sequence, entityId ordinal)**이다. 앞 두 값이 같을 때의 기존
  entityId 비교까지 유지한다. SQL 후보 정렬과 C# 비교가 같은 순서를 내는지도 검사한다.
- 서버 UTC highwater와 고정된 배치 cutoff를 쓴다. 과거 도착·귀환 deadline을 현재 시각으로
  밀지 않는다. 기존 sequence는 재번호하지 않는다. 새 sequence는 실제 논리 전이 순서로
  기존 저장소에서 발급한다. rollback된 sequence 예약의 빈 번호는 허용하되 상대 순서는 보존한다.
- 월드 행 → 필요한 연맹 행(UUID 순) → 계정 행(UUID 순) → 활동/행군 행 순서다.
  이미 계정 잠금을 가진 상태에서 더 앞선 잠금을 추가하지 않는다. 외부 writer는 같은 장벽을 쓴다.
- 계정별 분야 Advance, 버전 증가, 원장·outbox·명령 receipt, 지갑/보관함 Credits 순서는
  사건별 정본과 같다. 여러 사건의 보상을 먼저 합산해 상한·보관함 순서를 바꾸지 않는다.
- 직접/자동 전투의 Core 계산은 거래 밖에서 수행하고 계약·revision·snapshot을 재검사한다.
  전투 커밋과 귀환 커밋은 논리적으로 별개이며 하나의 전투 완료로 합치지 않는다.
- 일반 writer는 선행 due 사건이 남으면 503 `world-recovery-pending`을 받는다. 아직 확정하지
  않은 배치를 성공 응답·이벤트 전달·보상 지급으로 노출하지 않는다.

## 4. 권고 알고리즘

1. 월드 잠금을 잡고 UTC highwater/cutoff를 고정한다. 행군·채집·재생성의 통합 후보 조회로
   가장 이른 K개와 **그 다음 미포함 사건 F 하나**를 읽는다. F는 이번 거래에서 넘어가지 않을
   순서 경계다. 미포함 due 사건이 없으면 경계는 무한대다. 조회·원장 크기에도 상한을 둔다.
2. 후보의 공격자·수비자·채집권 소유자와 필요한 연맹/계정/목표를 수집해 고정 순서로 잠근다.
   계정 payload·분야 상태·보관함·원장 다음 ordinal을 묶어서 읽고, 거래 안의 작업 상태를 만든다.
   다른 트랜잭션의 상태를 전역 cache로 재사용하지 않는다.
3. 최소 키 사건 하나만 계산한다. 변경되거나 생성된 due 사건은 작업 상태의 우선순위 큐에
   즉시 반영한다. 이미 소멸·변경된 후보는 entity와 현재 event revision으로 무효화한다.
   **처음 가져온 K개를 고정 배열처럼 끝까지 실행하지 않는다.**
   0거리 귀환처럼 동일 entity가 같은 정렬 키로 다시 전이할 수 있으므로 키만으로 중복 제거하지
   않는다. 상태/revision과 사건 ordinal로 새 전이를 구별한다.
4. 새 사건의 키가 F보다 이르면 기존 후보보다 먼저 처리한다. 예를 들어 A 도착(10)이 귀환(12)을
   만들고 B 도착(20)이 대기 중이면 A 도착 → A 귀환 → B 도착이어야 한다. 큐 최소가 F 이상이면
   이 묶음을 끝내고 다시 조회한다. 따라서 미포함 사건을 넘어 진행하지 않는다.
5. 다음 사건이 미리 읽지 않은 계정·목표·다른 저장소 상태를 요구하면 **그 사건을 적용하기 전**
   현재까지의 연속 prefix만 flush/commit하고 다시 조회한다. 검증 중 의존성이 발견되면 해당
   사건의 임시 변경을 되돌린 뒤 경계를 자른다. 잠금 순서 역전이나 stale read를 허용하지 않는다.
   prefix가 비었으면 발견한 의존성을 포함해 제한적으로 재계획하거나 같은 순서의 단건 경로로
   전환한다. 같은 빈 후보를 무한 재조회하지 않으며 단건으로도 진행할 수 없으면 fail-closed한다.
6. 이벤트 전이 함수를 기존 분야 처리기·공통 writer와 공유하도록 준비/계산/저장 단계를 분리한다.
   단계별 규칙·검증을 복제하지 않는다. 계정의 최종 payload 저장은 합칠 수 있지만 중간 버전,
   resource/domain/world 원장, held FIFO, outbox는 논리 사건별 행과 순서를 모두 보존한다.
7. 기존 DB 드라이버의 명령 묶음·배열 입력 등으로 변경 행을 묶어 저장하고 영향 행 수·version을
   검증한 뒤 한 번 커밋한다. 서로 의존하는 결과는 단계 사이에서 읽는다. 값에 의존하는 명령을
   무조건 한 전송에 넣거나, SQL 명령 수 감소를 프로토콜 왕복 감소로 간주하지 않는다.
8. 사건 수·접근 계정 수·예상 변경 바이트·경과 시간 중 하나의 운영 상한에 도달하면 다음 사건
   전에 종료한다. flush/commit 시간도 별도 측정한다. 시간 상한은 DB 명령을 중간 커밋하는
   하드 실시간 보장이 아니다. 배치 종료 뒤 잠금을 반환하고 취소 확인·실행 양보를 한다.

K·계정/바이트/시간 상한은 운영 설정 후보이며 게임 콘텐츠 수치가 아니다. 기존 128을
일괄 거래의 최적 크기로 자동 승계하지 않는다. 먼저 16/32/64/128 후보를 측정한다.
현재 측정 하네스의 1천 행군 입력 상한은 후속 구현 PR에서 1만까지 명시적으로 확장해야 한다.

### 전투·지원하지 않는 활동의 경계

다음 최소 사건에 Core 계산이 필요하면 앞선 prefix를 먼저 커밋한다. 해당 전투는 기존
거래 밖 계산·revision 확인 경로로 넘기며, 더 늦은 사건을 대신 확정하지 않는다. 계산 중
변경이 생기면 다시 가장 이른 사건부터 판정한다. CAS 패배·재시도도 실제 작업량에 센다.
전투 완료와 귀환을 같은 새 묶음에 넣지 않아 기존 두 커밋 경계를 유지한다.
순수 준비/계산으로 분리하지 못한 활동은 같은 순서 위치에서 기존 단건 경로로 처리한다.
단건 fallback 시간도 총 복구 시간에 포함하며 그 비중을 공개한다.

## 5. 원자성·재시작·오류

이 안은 [ADR0085](0085-world-march-account-recovery-barrier.md)의 **사건별 transaction**을
지원되는 연속 prefix의 **묶음 transaction**으로 부분 대체하는 제안이다. 원자성 변경 승인이
필요하며, 현재 구현은 그대로다. 이벤트 한 개마다 crash 직전까지 진행이 보존되던 경계가
작은 묶음 단위로 바뀌므로 rollback 재작업량과 잠금 시간이 늘 수 있다.

- commit 전 crash/취소는 묶음 전체를 rollback한다. 재시작하면 이전 확정 prefix 다음부터
  DB의 원장·deadline을 다시 읽는다. 별도 checkpoint를 원장보다 앞서 기록하지 않는다.
- commit 성공 직후 응답 유실은 저장된 상태·원장 식별자로 판정한다. receipt 없는 새 UUID로
  같은 정산을 다시 만들지 않는다. 실제 중복 반납·지급·ordinal 충돌을 검사한다.
- 결정적 오류가 있는 사건은 건너뛰거나 시각을 바꾸지 않는다. 필요하면 제한된 prefix 크기로
  재현해 실패 사건 앞까지 확정하고 동일 위치에서 fail-closed한다. 무제한 재시도는 금지한다.
- deadlock/serialization/낙관적 검증 실패는 제한된 재시도로 전체 미커밋 묶음을 다시 읽는다.
  취소는 재시도하지 않는다. 이전 묶음의 확정 진행은 보존한다.
- 새 스케줄러와 단건 경로는 같은 world lock으로 직렬화한다. 롤백 시 마지막 확정 경계에서
  기존 사건별 경로를 선택할 수 있도록 영속 원장 형식을 우선 유지한다. schema가 필요해지면
  후속 PR에서 최신 main 번호·혼합 버전 동작·복귀 가능성을 별도로 검토한다.

처리량은 완료 행군/총 복구 초와 확정 사건/총 복구 초를 함께 기록한다. 중단·누락·실패한
